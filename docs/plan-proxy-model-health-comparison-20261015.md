# 代理模型巡检与账号／线路对照实施计划

日期：2026-10-15（Asia/Shanghai）。阅读基线：`f8e4517`，对应 `v2.10.7-go` 的导入初始化修复。

**状态：计划稿，尚未实施。** 本轮只新增本文，不修改业务代码、运行配置、账号数据或发布流程，不运行本地自动化测试，不发起真实模型探测。实现应在 `v2.10.7-go` 完成后、用户确认开始时另开工作分支。

## 1. 目标与结论边界

用户观察：同一个住宅出口曾稳定使用数小时，之后多个账号通过它访问模型均返回 405。此现象是线路关联的重要线索，但本轮没有对生产环境复现，不能直接写成供应商已确认封禁出口 IP。

本功能回答三个问题：

1. 这条代理当前能否完成一次 `glm-5.3-flash` 的最小模型请求？
2. 出现 405/3012 时，证据更支持线路相关、账号／身份相关，还是尚不能区分？
3. 是否已满足严格代理淘汰标准，还是只能暂避、等待或人工核查？

成功标准是对照结论和处置正确，不是承诺 405 消失。固定代理仍有初始化出口与业务出口分离、可控路由等价值，但不意味着固定住宅出口永久不触发上游限制。

1. 现有模型派发要求账号的真实绑定与出口快照一致，不能简单改一个账号副本的 `ProxyURL` 来跨线路测试。
2. 现有 `MarkRiskControl` 同时做账号冷却和业务换线；探测需要冷却，但不能因此改动业务绑定。
3. 现有手动流测每次生成新会话；定时重试若身份不一致，不能冒充“同条件只换代理”的对照。

## 4. 首版范围与默认行为

### 4.1 探测配置

| 项目 | 首版建议默认值／契约 |
| --- | --- |
| 总开关 | 关闭；管理员完成配置后明确启用 |
| 处置模式 | `observe`，只产生探测结论；可明确切换为 `auto_retire` |
| 目标模型 | `glm-5.3-flash`，首版不扩展任意模型矩阵 |
| 请求模板 | 固定版本的最小短请求，例如“只回复 OK”；无工具、无历史对话；保留真实业务必需的 system 与身份注入 |
| 输出与思考 | `max_tokens=16`、`effort=low`，沿用当前已使用的合法请求形态 |
| 正常巡检间隔 | 30 分钟，加入约 ±20% 错峰；允许配置，但不改变冷却要求 |
| 最近成功免测 | 目标线路最近 30 分钟有同目标、同模型的可信完整业务成功，可跳过本轮；未过期的异常待核查任务不因此静默取消 |
| 并发 | 默认 1，首版最多 2；同一线路、同一探测账号不重叠 |
| 单次 HTTP 时限 | 30 秒；读体与完整流同样受限 |
| 一次诊断预算 | 最多 8 次真实模型 HTTP，最多使用 2 个明确选择的探测账号；所有参考请求也计入 |
| 一次诊断总期限 | 20 分钟，包含首次等待；不能因反复遇到冷却无限续期 |
| 正式对照证据窗口 | 10 分钟；两个合格对照轮次必须同时在该窗口内 |
| 参考成功新鲜度 | 每轮目标请求之前 2 分钟内取得，且之后没有同范围的参考失败 |
| 请求预算 | 默认滚动 24 小时全局 200 次、单探测账号 100 次；单目标每小时最多启动 1 次异常诊断 |
| 目标范围 | 初始为空，管理员选择目标；支持明确选择“全部启用代理”，不因升级自动全池探测 |
| 直连对照 | 默认不允许；必须单独启用，且只用于符合资格的探测账号 |

预算是实际出站次数，不是“任务数”。输出上限不限制输入开销，固定 system 也消耗 token；后台展示实际探测用量，不能宣称最小回复等于零成本。预算不足时明确显示本轮覆盖不足，不能把未检测线路标绿。参考线路也纳入单线路并发和反复失败退避，不能成为无限复测的热点。

### 4.2 探测账号

- 管理员显式选择少量已获额度的 JWT 账号作为探测专用账号，不自动征用全池账号，不为检测自动注册、领取或导入新账号。
- 完整账号／代理交叉诊断至少配置 2 个符合资格的账号；不足时仅开放单路观察，不能显示“账号与代理已区分”。
- 探测专用身份与运行开关分离：确认设置时明确告知这些账号退出普通同步／异步模型选号；停用巡检不会自动将它们放回业务池，返回业务池需要显式解除专用身份。
- 初始化未完成、仍受托管固定出口约束、停用、归档、失效、冷却中、额外隔离期内、模型禁用或目标模型额度不可确认可用的账号均不派发。
- 不自动解除 2.10.7 的托管或固定绑定。如果现有账号全被托管，应先由管理员另行明确准备符合资格的探测账号。
- 账号凭据只留在现有账号存储。新任务只保存账号引用和代次，不另存 Token 副本。

### 4.3 参考线路与出口身份

- 至少明确选择一个参考代理；目标本身及其规范化 URL 别名不能作为自己的对照。
- 增加可选的人工“出口组”标识，标记明确共用同一家庭公网出口的多个代理配置；同组不得充当彼此的独立线路对照。
- 参考线路的完整成功必须现测或有符合本轮条件的有效记录，“网络测活成功”不够。
- 自动淘汰对照要求目标与参考被管理员明确标为不同出口组；信息不足可观察，但不产生主动探测的永久删除决定。不同组是管理员声明，不伪称已由供应商验证。
- 首版不新增外部查 IP 请求，不根据代理名称、端口或认证用户名推断真实出口 IP，也不根据一次查 IP 结果批量封禁同 IP 下全部配置。
- 家庭公网地址变化不自动解除既有严格禁止记录；仍经人工复核和原有解除流程处理，不通过改组名／重导入绕过。

## 5. 调度与对照流程

### 5.1 日常巡检

1. 读取一次版本化策略，公平轮转到期目标；合并该目标已经排队或运行的任务。
2. 检查近期真实业务成功、目标代次、严格禁止状态、探测账号资格及预算。
3. 可以免测则记录 `skipped_recent_success`；缺账号、参考条件或预算时分别记录原因，不合成为网络失败。
4. 取得 Store 探测许可后，用一个最小请求检查目标。成功记录 `healthy_recent`；405/3012 记录 `suspect` 并进入有界诊断；其他错误按原始类别展示。
5. 已有完整业务 405/3012 也可以提升该线路的诊断优先级，但队列去重、次数上限、资格与冷却不变，不能每个业务失败都触发一套探测。

### 5.2 异常诊断

记目标线路为 T，参考线路为 R，探测账号为 A、B。

1. 一次诊断创建独立 `diagnosis_id`；为每个账号冻结该诊断的模板、模型、协议档案、设备与会话。每次真实 HTTP 都使用新的 request ID，头与正文身份必须一致。
2. 首次 T 上的失败只触发怀疑；账号正常进入本地风控冷却，**不立即绕过冷却去 R 重试**。
3. 在总期限和冷却允许时，开始正式轮次：先 `A → R`，完整成功后再 `A → T`。参考失败时本轮不再拿 A 扫其他目标。
4. 若 R 成功、T 返回完整 405/3012，登记一组成对证据；下一轮须等待账号可调度，且不得在五分钟内立即重复同一账号／目标组合。
5. 第二轮重新执行 `A → R → T`，不能沿用五分钟前的参考成功。保持账号凭据版本、设备、会话、内容和协议一致。
6. 两轮可比、两次 T 失败、两次新鲜 R 成功，才可能形成主动探测的线路淘汰证据。日常筛查中没有参考前置的失败不能冒充其中一轮。
7. 若 A 在参考线路也失败，可以在剩余预算内用 B 做 R／T 对照；最多到 B，不继续从账号池抽 C、D、E。
8. 没有可用账号、参考不可用、截止时间到、证据过期或预算用尽时，结束为 `inconclusive`。已有失败和冷却不清零，也不因为任务结束重开一套即时诊断。

**时序示例**：日常 T 失败 → 等待账号冷却 → 正式第一轮 R 成功／T 失败 → 再等至少五分钟及实际冷却 → 正式第二轮 R 成功／T 失败。两个正式轮次必须位于同一个十分钟有效窗口。若配置的冷却更长导致无法满足，宁可没有自动淘汰结论，不扩大窗口或缩短冷却凑条件。

因此，“每三十分钟巡检”与“十分钟严格证据”不矛盾：前者发现线索，后者是另一个受预算限制的诊断阶段；不能把相隔三十分钟的零散失败拼成当前严格决定。

## 6. 结果分类与处置

| 观测组合 | 展示结论 | 自动动作 |
| --- | --- | --- |
| T 完整成功 | 最近一次最小模型请求成功 | 记录时间和用量；不解封已退役线路或账号 |
| T 只有一次 405/3012，或没有参考成功 | 待核查 | 开启有界诊断；不永久删除 |
| A 在 T 的两个正式轮次失败，每轮在 R 成功，且无反证 | 线路相关证据成立 | `observe` 只记录“达标未执行”；`auto_retire` 经门禁立即进入严格退役事务 |
| A 在 T、R 均 405；B 在 T、R 均完整成功 | 更偏账号／身份相关 | 不删代理；保留 A 的现有冷却与原始证据，不新增“探测判定永久封号”规则 |
| A 在多线路失败，B 只在 R 成功、T 也失败 | 可能存在混合因素 | 不把 A 或 T 单独认作唯一根因；仅在后续独立满足线路规则时处置 |
| 参考组也普遍失败，没有可信成功锚点 | 全局／参考异常，无法归因 | 暂停主动扩散；不清空代理池 |
| T 在同一有效比较范围内有完整成功和失败 | 混合结果 | 保留给复核，不由本主动规则删除 |
| 普通 405、401/403、429/3009、额度不足、验证码、超时、取消、断流 | 对应具体错误，或无法确认 | 不混入 405/3012 的删除计数；不通过反复求解／换号扩张探测 |

全局保护使用已经获得的证据：当选定账号／参考线路不能提供健康锚点时暂停普通目标的主动对照，默认退避 30 分钟，之后只做有预算的参考复核。不能为了证明“全局故障”额外扫遍账号和代理。此状态不是供应商全站故障的因果断言，不取消既有严格禁止，也不拦截原本正常的业务请求。

## 7. 证据契约与防误判

### 7.1 成功和失败的定义

- 线路失败证据只接收真实模型端点的 `HTTP 405 + JSON 业务码 3012`，且错误体完整读取、未超限、归属目标正确；单有 `blocked` 文案仍可触发账号风控保护，但不能补足线路证据。
- 成功必须是实际上游 2xx、合法完整模型消息和有效终态／用量。SSE 缺消息 ID、缺结束事件、错误事件、半截流、仅收到响应头均不算；JSON 也不能把业务错误对象当成功。以协议完整性判断，不要求输出逐字等于 `OK`。
- 使用真实成功／失败状态，不使用交付层统一 HTTP 200；禁止隐式跟随重定向，不允许一个派发许可访问第二个目标。
- 对照的固定条件包括 provider、目标 origin／path／method、模型、模板版本、内容语义摘要、协议档案；同账号线路对照还包括凭据代次、设备和会话。

### 7.2 探测与真实业务分组

- 新增 `source=business|model_probe`、探测模板版本、诊断／轮次引用；同一 HTTP 去重，同一轮内部重试不算第二轮。
- 既有十分钟业务规则和阈值不变。探测的固定小模板不能冒充两种业务内容，也不能把不同模板版本、会话或凭据混在一起。
- 主动规则建议版本为 `proxy-model-probe-3012-v1`：至少两个符合第 5 节的正式成对轮次；它比既有同账号规则多要求每轮新鲜参考成功，不降低门槛。
- 固定探针的成功不能用于否定复杂真实请求的失败。反过来，目标同范围内近期完整的真实业务成功可作为阻止主动永久删除的额外反证。
- 参考线路在成功后又失败，旧成功不得继续证明它健康。不同出口组的声明被修改，当前诊断失效，不能沿用旧证明。
- 证据容量丢失时暂停新决定，不能删掉反证后宣称没有成功记录。进程重启终止未完成诊断，不从展示历史重建删除证据。

### 7.3 两种模式

- `observe`：保留实际观测和探测账号冷却，只展示判断，不因探测改变业务代理分配、触发永久删除或改派。既有业务严格规则继续独立运行。
- `auto_retire`：有效待核查证据可让自动新增绑定暂避该线路；达到主动规则后立即走严格淘汰。不能用单次待核查直接阻断全部既有业务绑定。
- 新永久决定还必须通过总门禁 `strict_proxy_enabled`；关闭它不会解除既有禁止记录、冷却或恢复事务。
- 从观察模式切换到自动处置，不回放历史“达标”结论立即删代理，必须取得新模式代次下的新鲜完整对照。

## 8. 与 2.10.7 固定代理语义的兼容

1. 探测账号的跨线路请求是一次性的受控出站，不修改持久 `ProxyID`／`ProxyURL`，不解除任何业务账号的人工或初始化路由意图。
2. 未获配额、初始化中以及托管固定出口账号不能被临时借作跨代理探测账号。
3. 固定业务节点达到严格退役条件后，托管账号进入既有等待状态；**不能自动退到取额池、其他代理或直连**。普通自动代理账号继续使用原有改派／等待规则。
4. 不新增“测试成功就迁移全部账号到该线路”逻辑；更换默认业务代理仍不自动迁移既有固定账号。
5. 探测中的手工改绑、停用、归档、改凭据、代理 A→B→A 或策略改变使旧回写失效，不能覆盖新设置。
6. 领取结果、初始化进度和已有的“补入初始化”功能不受探测开关影响；不为检测重新领取或刷新真实账号资格。

## 9. 实现拆分

### 9.1 一个深 Module（模块）承担巡检行为

新增 `internal/modelprobe`，将资格规划、单次请求、成对诊断、截止时间和结构化结果放在一个 Module 内。对调度和管理端提供小的 Interface（调用契约），例如“请求一轮检查、查询结果、停止任务”，不让两个调用方各自拼重试循环。

时钟与模型 HTTP 发送位置是内部 Seam（可替换位置）：生产用真实时钟／受控 HTTP Adapter（具体接入实现），测试用可推进时钟／本地 HTTP 代理 Adapter。测试从相同 Interface 观察结果，不靠改私有切片伪造删除成功。

### 9.2 Store 是准入和处置的权威

- 新增模型探测许可：仅接受显式探测角色、有效策略和当前凭据／线路代次；把允许的目标、模型及出站路由封装在不可由外部任意拼造的许可中。
- 与正常派发、严格退役共用锁和路由许可计数。已获许可请求可收尾；退役后不再发新许可。
- 探测许可另查账号冷却、额度和初始化状态，不借 `AcquireRawProxyDispatch`、`nil` 账号或自定义客户端绕过模型检查。
- 在正常同步／异步的选号与最终派发处排除探测专用账号，防止已排队的旧账号快照继续抢占；已经合法出站的旧业务请求允许正常完成，不取消或重放。
- 原子预扣出站预算并登记 attempt ID，迟到完成幂等回写；失败请求同样消耗次数，防止超时重试无限免费。
- 提取共享“风控观测＋阶梯冷却”，业务路径继续组合原有自动换线；探测路径只更新自身健康，不执行业务换线。不复制一套阈值算法。
- 探测成功仅按完整成功规则记录健康和用量；不从探测流程自动恢复 invalid、清除未到期冷却或解除严格禁止。
- 退役继续复用现有严格日志／SQLite 事务／恢复路径；持久记录包含实际规则版本和探测来源，不冒称人工删除。

## 10. 存储、管理端和展示

### 10.1 存储与生命周期

- 复用 SQLite，设置和探测角色使用带版本的专属状态；新增小型尝试历史／预算记录，迁移幂等且默认关闭。账号导出格式不夹带诊断凭据。
- 判定证据仍是有界短窗口；展示历史保留七天、最多一万条，可裁剪，但不能参与重新凑证据。
- 请求预算与历史展示分别保留：清理历史不能重置滚动 24 小时预算；重启也不补发已经登记派发而结果未知的请求。
- 进程关闭取消未出站任务，在途请求正常取消／收尾；重启把旧 running 标为中断，不恢复半组对照，不立即全量扫代理。
- 总开关关闭或策略代次改变，撤销未出站任务；旧结果只能结算已发生用量，不能提交新版本下的健康／删除决定。
- 证据不完整、SQL 写失败和严格删除恢复失败都必须可见；不得输出“已删除”但实际事务未完成。

### 10.2 管理端契约

沿用现有管理员鉴权；建议新增以下独立端点，具体路由在实施时与现有注册表复核：

- `GET/PUT /admin/api/proxies/model-probe/settings`：整体校验配置、账号角色、目标和参考组；设置变更原子提交。
- `GET /admin/api/proxies/model-probe`：摘要、覆盖率、剩余预算、全局暂停原因。
- `POST /admin/api/proxies/{profile_id}/model-probe`：异步入队，返回任务标识；与定时入口共享资格、预算和去重，不允许手动请求绕过总开关。
- `GET /admin/api/proxies/{profile_id}/model-probe/history`：分页展示轮次和结果。

旧 `/stream-test` 的连通性语义和响应兼容保留；新模型巡检不以其 `ok` 判断成功。新预算覆盖本模块定时／手动模型巡检，不冒称覆盖所有既有人工模型请求。

后台同时展示“网络连通性”和“模型可用性”，避免一个绿色图标混淆两者。模型列展示最近成功／失败、原始 HTTP／业务码、证据轮次、参考是否有效、等待原因、规则和处置模式。账号与代理 URL 去敏；不展示 Token、完整请求正文或错误正文中的敏感信息。

没有检测、因预算跳过、证据过期都显示未知或待测，不能继承过期绿色。可以显示绑定账号数帮助理解共享出口压力，但不据此断言上游阈值。

### 10.3 功能回退

- 优先在新版本关闭探测总开关，停止新任务和新主动决定；保留探测角色、预算、账号冷却及既有严格禁止记录。
- 需要取消自动删除时切回 `observe`；已经提交的严格退役不回滚，仍走原有人工解除流程。
- 旧二进制不认识探测专用角色。若确需回退到 2.10.7，先在新版本明确停用这些账号，或解除专用角色并复核其业务绑定；不能直接删表／降级，让探测账号悄悄进入业务池。
- 不以删除新状态、重置预算或导入旧备份绕过严格禁止。数据库迁移兼容不等于路由语义可以无操作回退。

## 11. 回归测试与验收矩阵

全部自动化在 GitHub Actions Ubuntu 执行；本地仅阅读、修改、格式化、差异检查。前端本地构建只用于生成必须提交的 `frontend/dist`。测试使用隔离 SQLite、合成 JWT、本地 HTTP／TLS 代理及可推进时钟，不读运行 `data/`。

必须覆盖：

1. 两轮 R 成功／T 405 的正式对照成立；观察模式不删除，自动处置模式只删除 T 的同身份配置，并有正确规则来源。
2. A 在 T／R 失败、B 在两者成功，显示账号相关而不删路由；混合因素与所有参考失败均不误归因。
3. 普通 405、仅风控文案、401/403、3009、验证码、超时、取消、CONNECT 失败均不补足线路证据；直连参考失败不污染账号原绑定代理，也不存在删除“直连线路”的决定。
4. 2xx 错误 JSON、缺消息 ID／usage／SSE 终帧、截断错误体、重定向、目标不匹配均不能冒充成功／有效失败。
5. 同一 HTTP 重报、同一轮内部重试、模板／模型／设备／会话／凭据不匹配不能累计；不同出口组未确认或实际声明同组时不自动淘汰。
6. 目标有矛盾成功、参考后来失败、容量裁剪、三十分钟间隔失败均不能凑成有效删除证据；探针成功不覆盖真实复杂请求的失败。
7. 冷却、静默期、未知额度、模型禁用、初始化和固定代理保护均在真实发送前生效；无合格账号时零出站。
8. 不修改探测账号的持久绑定，不借用托管固定账号；固定节点淘汰后账号等待而不是直连／取额池；普通账号原有改派规则不变。
9. 定时与手动同时触发只派发一次；全局／账号预算原子执行，参考请求和失败请求计数，时间推进、重启与历史清理不能重置预算。
10. 停机、关闭开关、切换观察／自动处置、修改角色／出口组、代理或凭据 A→B→A，旧结果不能作用于新版本。
11. 用量独立标记为探测，但实际消耗正确累计；不虚增业务请求统计，不因失败丢失已确认的用量。
12. SQL／严格恢复介质故障不出现半套删除和绑定；恢复后已退役线路不会由订阅、改名或重启自动复活。
13. 新管理端鉴权、非法设置／越权账号、重复入队、分页上限和脱敏；旧流测接口兼容。
14. 前端未知／健康／待核查／账号相关／参考异常／已退役状态、配置确认、预算耗尽、固定节点等待等交互。
15. 2.10.7 的导入、重复导入、补入初始化、到账固定绑定及关闭策略回归全部继续通过。

第一批先提交能在远端变红的真实发送链回归，再实现；不只测试手工拼造的证据数组。新增针对性的重复回归和 race 验证，最终仍以当前 SHA 的完整 `ci.yml` 结果验收，不删除旧断言、缩减覆盖或放宽发布门禁。

## 12. 分阶段实施顺序

| 阶段 | 内容 | 完成标准 |
| --- | --- | --- |
| P0 基线与规格 | 确认 2.10.7 发布门槛，建立隔离分支，冻结角色／对照／模式契约 | 无其他会话改动被带入，关键默认值与用例已记录 |
| P1 远端失败回归 | 本地代理模拟“线路坏／账号坏／全部坏”，暴露手动流测不能等于模型成功的差异 | GitHub Actions 中相应回归明确失败，失败原因与目标行为一致 |

实际启用必须另行明确目标、参考组、探测账号与预算。先用少量目标运行观察模式，核对完整请求次数、归因理由和误报；验证后再明确开启主动自动淘汰。不把生产试用当成 CI 的替代，也不在实现期间擅自操作真实账号和服务器。

## 13. 本次不做

- 不保证住宅出口永不被限制，不推测供应商每个 IP 允许多少账号。
- 不通过账号／代理大规模轮换寻找可用身份，不绕过冷却、额度或初始化保护。
- 不自动迁移全部固定业务账号，不扩展免费套餐领取策略。
- 不把探测小请求成功当作长上下文、长流或其他模型的保证。
- 不自动解封严格退役线路，不把出口 IP 查询当成供应商因果确认。
- 不实现多副本分布式调度；沿用当前单进程独占数据库范围。
- 不在 Codex 创建周期提醒来代替项目内的巡检调度器；本轮没有启动实现或后台生产探测。

后续如需每出口账号数量、业务并发／请求速率限制或固定业务代理组，应另行设计和确认。这些是容量与路由策略，不能隐藏在检测功能中改变现有业务行为。
