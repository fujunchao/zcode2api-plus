## 一、结论先行

1. **不是「大量账号同时被上游风控」，而是「一个请求被上游风控，网关把它放大成了 67 个账号的冷却」。**
2. 触发源是**一个 278,081 字节的 `GLM-5.3` 流式请求**。同一请求体在 **67 个不同账号、约 50 条不同出口线路上全部被拒（HTTP 405）**；而换号逻辑对「请求级拒绝」天然无效，于是每换一个号就多冷却一个号。
3. 放大器是两层：
   - 网关侧：单请求最多换 **5** 个账号（`MaxAccountAttempts = 5`），每个被拒账号直接吃 **300s 整号冷却**；
   - 上游调用方：同一请求被**连续重放 14 次**（每 6~8 秒一次，形态上是客户端/中转的自动重试），14 × ~5 = **69 次尝试 → 67 个账号冷却**。
4. 结果：全池 **70 个账号**（67 风控 + 3 connection_failed）在 2 分钟内清空，`GLM-5.3` 全线不可用，最早恢复时间 **10:05:22**（北京），故障窗口约 **5 分钟**。
5. `glm-5.3-flash` 未受影响（错误文案为「模型 GLM-5.3 無可用帳號」），符合「按模型冷却」的设计。

**关于「谁错了」的定性：** 上游确实回的是风控文案（走过 `model.IsRiskControlBody` 判定），但它拒的是**这个请求**，不是这些账号。把请求级的拒绝结算成账号级的惩罚，是本次事故的真正缺陷。

## 三、证据链（为什么判定为「请求级」而非「账号级」）

### 证据 1：同一请求体、跨 67 个身份、跨约 50 条线路，全部被拒

14 个 405 请求的 `body` **字节数完全一致（278,081B）**，账号各不相同，线路覆盖 `mihomo-zai-012/017/023/028/038/042/049/094/101/102/111/115/148`、`prx-zai-86` 等。

> 线路 = 出口 IP。67 个不同账号 + 数十个不同出口 IP 在同一时刻被同一套 WAF 规则集体命中，概率上不成立；账号不是变量。

### 证据 2：同一个账号在 9 秒前刚刚成功

| 时刻 | 账号 | 请求体 | 结果 |
|---|---|---|---|
| 02:00:11 | **A** | 252,609B | ✅ 200（输出 6054 tokens） |
| 02:00:25 | **A** | 278,081B | ❌ 405 风控 |

账号 A 在 9 秒前还是健康的、能出流量的。它失败的原因只可能是**被送进去的那个请求**变了。

### 证据 3：对照组——09-23 的 17 次风控全部「换号即成功」

| 时间 | 请求体 | 本 ticket 最终结果 |
|---|---|---|
| 06:02:53 | 44,997B（flash） | 200（attempts=2） |
| 06:12:29 | 184,612B | 200（attempts=2） |
| 06:59:45 | 3,427B（sync） | 200（attempts=2） |
| 07:05:10 | 673,998B | 200（attempts=2） |
| 08:20:18 | 44,254B（flash） | 200（attempts=2） |
| 10:59:46 | 139,095B（flash） | 200（attempts=2） |
| 01:57:41 | 215,599B | 200（attempts=2） |

**17/17 全部换号后成功**。这证明两件事：
- 账号级风控是真实的、日常存在的现象，且当前的「冷却 + 换号」处置**在这个语义下是正确的**；
- 02:00 那次是**唯一一次**「换遍全池都失败」，语义与上述完全不同，却走了同一条代码路径。

### 证据 4：请求体大小不是触发条件

成功请求的 body 尺寸分布：p50 = 163KB，p90 = 456KB，**max = 687KB**；`≥270KB` 的成功请求有 **283 条**（含 280KB~688KB）。278KB 既不超限也不特殊。

> 因此触发条件更可能落在**内容**（该轮新增的 ~25KB，例如超长工具结果/粘贴内容）或该会话被上游标记，而非尺寸。

## 四、放大机制（代码层）

### 4.1 单请求内：换号等于惩罚账号

`internal/gateway/engine.go` 分类链第 8 条：

```go
// 8) 405 + 风控文案：上游风控拦截，冷却整个账号（按连续命中次数递进），
if resp.StatusCode == http.StatusMethodNotAllowed && model.IsRiskControlBody(text) {
    secs, streak, invalid := e.markRiskControl(acc, "上游风控拦截 HTTP 405: "+ErrorPreview(text))
    ...
    return attemptResult{switchAccount: true}   // ← 换个号再来
}
```

外层循环（`runWithAccounts`）：

```go
tried := map[string]bool{}
for range MaxAccountAttempts {          // MaxAccountAttempts = 5
    acc := e.Store.Select(model.ProviderZai, tried, modelName)
    ...
    if res.switchAccount { continue }   // 换下一个账号
}
```

组合起来的语义是：**「这次风控是针对这个账号的，换一个就行」**。当风控实际是针对请求时，这句话变成「把池子里的账号一个个送出去挨打」。单请求上限 5 个，所以一次请求最多烧 5 个账号。

### 4.2 跨请求：调用方重放，账号数乘 14

14 个 ticket 的提交间隔是 6.3~7.8 秒，与上一票的 `total` 耗时基本吻合 → **上游调用方在收到失败后立即原样重放**（典型的中转/客户端自动重试）。请求体字节数完全相同（278,081B），说明是同一份 payload 的确定性重放。

网关侧没有任何「同一 payload 刚刚被判为请求级失败」的短期记忆，于是每次重放都从池子里重新抓 5 个「还没被试过」的健康账号。14 次 × ~5 = 70。

### 4.3 冷却代价

`GLM-5.3` 的 67 个账号全部是 `第 1 次命中风控` → 统一 300s 整号冷却（阶梯首档）。8 分钟内无人能用，且这 67 个账号在 09-23 的零星风控记录被 `MarkSuccess` 清零过，说明它们在事故前都是**健康账号**。

## 六、修复建议（按优先级）

### P0-1 请求级风控熔断（止血核心）

在本次请求的作用域内记录「因 405+风控文案被拒的账号数」。当**同一请求体在 ≥2 个不同账号（且出口线路不同）上收到同一风控信号**时，判定为请求级拒绝：

- 立即停止换号，返回上游原始 405（保留 body 与业务码）；
- **不再对后续账号施加冷却**（早退，见 P0-2）。

判据的合理性：风控是身份维度（账号/设备指纹/出口 IP/请求头）。一个请求若在两个完全不同的身份与出口上都被拒，**身份已不是变量，剩下的只有请求体**。阈值取 2 即可，因为对照组（09-23 的 17 次）全部在第 2 个账号上成功，不会误伤。

单请求消耗上限因此从 5 降到 2，本次事故会从「67 个账号」变成「2 个账号」。

### P0-2 冷却回滚（让误伤可撤销）

若最终判定为请求级，应撤销本轮因**这一个请求**新增的冷却。两种实现：

- 请求作用域记账：本请求内 `markRiskControl` 的账号与旧值入栈，判定为请求级后按记录回滚；
- 或按 `LastError` 语义标记：「该次冷却源于请求级风控」，下一次 `MarkSuccess` 或后台巡检时提前解除。

⚠️ 注意 `store.Update` 是唯一写入口且锁内不可重入，回滚要在锁外逐账号调用。同时**不能**简单地把风控冷却整体改成「不计入状态」——对照组的账号级风控仍需要冷却。

### P0-3 日志补全（否则下次仍然无法事后定性）

`405 风控` 分支的 `[~]` 行目前**不带上游 body**（对比 503 分支带了 `ErrorPreview`）。三种 405 语义（风控 / 计费重复查询 / 缺顶层 system）只靠状态码无法区分。建议：

```go
web.Warn(reqID, fmt.Sprintf("账号 %s 第 %d 次命中风控（HTTP %d，%s），冷却 %d s 后切换下一个",
    acc.Name, streak, resp.StatusCode, ErrorPreview(text), secs))
```

本次由于这条缺失，**只能靠统计推断、无法直接看到上游原文**——只能去后台看那 67 个账号的 `last_error`（应为 `上游风控拦截 HTTP 405: ...`）来确认。

### P1 重放防护

对「同一 payload 哈希 + 同一模型」在短窗口（如 60s）内已被判定为请求级风控的，直接快速失败（返回缓存的 405），**不消耗任何账号**。可把 14 × 5 降到 1 × 1。

### P2 可配置化

`MaxAccountAttempts`（现为常量 5）与熔断阈值建议纳入后台配置，与可配置的 503 退避保持一致。

### 待确认（需要用户侧动作）

1. 在后台查看任一风暴账号的 `last_error` 原文，确认 body 是否含 `unusual activity`；
2. 落盘/抓取那份 **278,081B** 的请求体，二分定位触发内容（该轮新增约 25KB）；
3. 确认调用方（中转/客户端）的重试策略——若要根治「一次坏请求打穿池子」，调用方不应原样重放 N 次。

> 三者相乘 = 67 个健康账号 × 300 秒。
