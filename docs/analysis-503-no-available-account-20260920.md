# 503「無可用帳號」事故诊断（2026-09-20 晚）

**结论先行**：这不是账号-模型绑定错误，也不是额度统计偏差。116 次 503 全部是网关的「**此刻池内无可选账号**」响应（`RunMessages` 中 `Select` 返回空），由两起独立事件触发：

1. **23:31–23:36（GMT+8）**：上游对连续多个账号返回 HTTP 503，每个账号被固定冷却 300s，约 35 秒内整池进入冷却 → `glm-5.3-flash`（连带 GLM-5.3）无号可选。**与额度无关**，用户观察「额度充足」正确。
2. **23:01–23:04（GMT+8）**：GLM-5.3（非 flash）专属——池内某账号该模型每日额度确实用完（HTTP 200 + 业务码 1005），叠加 23:00 起的风控冷却（300s/次）与瞬时限流冷却，池子被清空 4 分钟。

误导来自**错误文案本身**：`no_available_account` 的提示恒为「帳號未提供此模型或額度已用完」，不反映真实原因（冷却中/风控/模型日限），把一次上游抖动包装成了绑定/额度问题的样子。

## 数据来源与口径

- 完整运行日志 1,416 条（v2.3.0-go，2026-09-20 19:17 → 09-21 08:17 GMT+8，日志时间戳为 UTC，导出于 08:24 GMT+8）。
- 请求总计 452：成功 333、错误 119（503 無可用帳號 116 + 客户端主动断流 3）。无其他错误形态。
- 代理线路池 93–108 条，巡检每 ~46 分钟剔除 1–6 条死线（正常衰减；线路名里的数字是线路编号，与 HTTP 429 无关）。

## 事故一：GLM-5.3 池清空（22:44–23:04）

**链路**：

- 22:44 起，每个成功请求的首选账号尝试都收到 HTTP 200 + code **1005**（该账号 GLM-5.3 每日额度用完）→ 引擎按设计标记该模型耗尽并换号 → 次选账号成功。共 23 次 1005 标记。说明池内**至少 1 个账号的 GLM-5.3 日限真实耗尽**（额度按模型独立计量；用户核对的是 flash 的额度，两者互不影响）。
- 23:00 起出现 5 次**风控命中**（各冷却 300s）与多次瞬时限流升级冷却（30/60s）。
- 23:01–23:04：可选池为空 → 48 次 503。期间 23:01:39 仍有一次 297tok 成功，证明池子是「大部分不可用」而非「全部死亡」。
- 23:05 后该模型流量停止（客户端放弃），非恢复。

## 事故二：上游 503 连环冷却（23:31–23:36）——用户报障的直接来源

**链路**（逐请求还原）：

- 23:29:35 的请求在尝试链上先遇瞬时限流（1s 原地重试 → 30s 冷却换号），23:31:48–23:31:52 连续 3 个账号尝试均收到**上游 HTTP 503**，第 4 个账号成功——上游已开始抖动。
- 23:32:14–23:32:23：又一轮请求连续 7 次上游 503。每个 503 → `mark(cooling, 300s)`（固定 `config.CoolingSeconds`，不走递进阶梯）。
- 整池（个位数账号）在 ~35 秒内全部进入 300s 冷却 → `Select` 对 GLM-5.3 和 glm-5.3-flash 均返回空 → 68 次 503（48 GLM-5.3 + 20 flash）。
- 23:36:18 后无新错误；与最早一批冷却（23:31:48 + 300s = 23:36:48）到期吻合，**自愈**。

**关键点**：glm-5.3-flash 的 20 次 503 与该模型额度、绑定毫无关系——是整账号级冷却的连带伤害。上游 503 的来源（z.ai 侧还是代理线路侧）日志不可见（该分支只记状态码不记 body），但 503 同时打在多个不同账号/线路上，更像上游侧抖动。

## 代码对应

- 503 生成点：`internal/gateway/engine.go` `RunMessages`——`Select` 返回 nil 即回 503，文案为**静态字符串**，不含账号状态分解。
- 上游 503 → 冷却：`engine.go` 分支 7（`handleUpstreamError`），固定 300s，`bumpFail` + `mark(cooling)`。
- 1005 → 模型级耗尽：`handleUpstreamJSON`，`markModelExhausted` + `fireRefresh`；刷新后由 `SyncExhaustedModels` 依据余额快照恢复。
- 风控 405：阶梯冷却首档即 300s。
- 瞬时 429（全程 162 次）：1 次原地重试后 30→60→120→300s 递进冷却，均按设计吸收，未漏到客户端。

## 修复方向（按优先级）

1. **503 文案携带真实池状态**（低成本、高收益）：错误体附实时分解，如「5 帳號：3 冷卻中（2×上游503、1×風控，最早 23:36:48 恢復）、1×GLM-5.3 每日額度已用完、1×無此模型」，并给出最早恢复时间，避免中转层在冷却窗口内无效重试轰击。
2. **上游 503 的冷却策略**：固定 300s 会在上游抖动时把整池瞬间清空。可选：首档冷却降到 30–60s 走递进阶梯（与瞬时限流同构）；或对 503 增加 1 次原地退避重试（当前只有过载 529/1305 有）；同时**记录 503 响应体预览**，区分 z.ai 侧 503 与代理线路侧 5xx。
3. **1005 状态可见性**：后台账号卡片展示「GLM-5.3 每日額度已用完（自动恢复）」类模型级状态，别让用户只能从 503 文案反推。
4. **池规模**：个位数账号 + 整账号级 300s 冷却 ⇒ 任何上游抖动都会清空池子。扩账号，或实现「保底账号」（冷却中也允许试最后一个，失败再回 503）。
5. 断流 3 次为客户端主动取消，无需处理。
