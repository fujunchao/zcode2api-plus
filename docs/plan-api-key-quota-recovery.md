# API Key 模型额度恢复与 ZCode 3.14.5 声明同步

## 目标与边界

- 修复上游 `apiKey` 账号的某模型被标记耗尽后，即使额度恢复仍永久被正常调度排除的问题；这里的 API Key 不是本网关入口密钥。
- 默认客户端声明从 `3.14.4` 同步到 `3.14.5`；不修改模型协议、验证码分工或官方 Coding Plan 重置接口。
- 作为 `v2.9.9-go` 补丁发布。主仓库之外的独立 `zcode-switch` 及其已有修改不在本次发布范围。

## 方案

1. 保留正常选号接口和 JWT 余额刷新。只有正常候选用尽，普通网关才尝试取得一个 API Key 模型恢复探测租约；异步池仍只使用 JWT。
2. 探测复用用户正在请求的模型和正文，不主动生成请求、不调用计费/重置接口。账号需已启用、未归档、未失效、没有未到期冷却，目标模型不得人工停用。
3. 耗尽标记在探测期间继续存在；同一账号/模型只有一个在途租约。仅完整成功响应可以解除目标模型标记；错误事件、断流、取消、普通失败均保留标记。
4. 等待依次为 5 分钟、15 分钟、1 小时、6 小时（封顶）。发送前先持久化下一次探测时间，进程重启不会造成密集重试。没有历史时序的旧记录首次观察后等待 5 分钟；有可信额度失败时间的旧记录据此计算首个窗口。
5. 恢复状态由 store 内部独立持久化，不改变既有 Account JSON 键集合。租约绑定凭据、出站身份及模型失败代次，迟到成功不能覆盖新凭据、新失败或账号保护状态。
6. 成功恢复后只移除目标模型标记；若目标模型遗留旧额度快照的零余额，改为数值未知，不伪造正余额、不影响其他模型。

## 验证接缝

沿用影响分析中已约定的公开接缝：网关 HTTP 请求、`Engine.RunMessages`/受控时钟，以及 Store 的账号快照、持久化重开和恢复租约接口。依赖仅为隔离 SQLite 与本地 HTTP 替身，使用合成凭据。

- 第一条回归先在旧实现上经 GitHub Actions 观察失败：额度错误后立即重试被限制，推进时钟且上游恢复后应重新成功调用。
- 随后逐项补充：单模型隔离、正常候选优先、并发单飞、失败退避、重启、旧记录、身份变化、迟到结果、冷却/风控/人工停用、流式错误与取消。
- 版本头、配置查询与 UA 继续统一从配置派生；环境变量显式覆盖保持有效。
- 本地仅编辑、格式化和差异检查；所有测试、静态检查、编译和竞态检测由当前提交的完整 CI 执行。

## 发布

只向 origin 推送工作分支。先确认最终 SHA 的完整分支 CI 成功，再更新主分支并推送真实版本标签。发布工作流必须通过复用的完整 CI，随后核对五个平台附件及 GHCR 的版本/latest 多架构镜像；不放宽门禁或以旧提交结果替代验收。
