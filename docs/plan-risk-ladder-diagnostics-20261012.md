# v2.9.18：恢复阶梯冷却与出站诊断

## 目标与边界

恢复默认 `300,900,3600` 秒的阶梯冷却：每档到期可再次参与选号，连续超档置为失效，成功调用清零连续计数。`LastRiskControlAt` 保留为观测记录，不再默认导致额外 24 小时排除。

- `ZCODE_RISK_SILENT_HOURS` 默认改为 `0`；显式大于零仍表示管理员额外开启的本地隔离策略，日志和页面明确区别于上游封禁事实。
- 不自动复活失效/停用/归档/额度耗尽账号，不重置用户设置的冷却阶梯，不批量修改运行数据。
- 保留同请求多账号失败后的停止换号与重放保护；保护阈值不是供应商原因诊断。
- 修复 `3009` 及同族并发码的分类与同步/异步处置，保留原始业务码，避免普通 429 的整号冷却。

## 实施顺序

1. 在现有 Store、Messages HTTP、异步票据接口补合成回归，先推工作分支观察远端失败。
2. 恢复默认阶梯；覆盖冷却内不调用、到期恢复、成功归零、超档失效、人工恢复与显式额外隔离。
3. 扩展实际发送边界的诊断：调用前账号状态/风险时间/模型额度及快照时间；最终模型、推理参数、system 分块摘要与官方固定块匹配情况。摘要与上游尝试共享标识，不消费 HTTP 请求体或响应流。
4. 纠正 `history_blocked` 和“上游标记未解除”的语义，保留兼容字段；诊断不得包含 JWT、认证值、用户正文、工具 schema 或敏感标识原文。
5. 同步/异步回归覆盖并发码、参数/正文保真、跨尝试快照一致性与脱敏；所有自动化检查由 Ubuntu GitHub Actions 执行。
6. 必要时在本地仅生成必须提交的前端 dist。当前提交完整分支 CI 通过后更新默认分支并发布 `v2.9.18-go`；发布再通过完整复用 CI，最后核对五份二进制与 amd64/arm64 镜像。

## 验收与发布

- 阶梯冷却与额外隔离不再混淆，默认首次风控不再整号隔离 24 小时。
- 已有真实日志只用于理解错误形态，回归全部使用隔离目录、合成凭据和本地 HTTP 服务。
- 不根据 `history_blocked` 推断账号被封次数，不根据本地隔离窗口声称上游仍被封。
- 不用模型请求成功代替当前提交 CI，也不绕过发布门禁。
- 已显式设置 `ZCODE_RISK_SILENT_HOURS=24` 的部署仍会启用该策略；要恢复纯阶梯应设为 `0` 或移除此覆盖。已有人工设置/历史保护形成的实际 `CoolingUntil` 不擅自改写，需在界面明确显示并由管理员处理。
