# 故障分析 v3：glm-5.3-flash「固定 ~300 s 断流」引发客户端的 5 分钟重试循环

- 分析对象：容器日志包 `zcode2api-logs-20260921T131404Z-redacted.zip`（697 行，覆盖 2026-09-21 02:57 → 13:13 UTC，即本地 10:57 → 21:13）
- 症状（用户视角）：代码编辑器客户端在长思考时**每约 5 分钟断一次连接，然后从头重新思考**，反复多次
- 对照前作：`docs/analysis-flash-30min-stream-cut.md`（2026-09-19，同一链路、同类现象，当时的时长墙是 **1800 s**）

## 1. 结论（先看这段）

1. **服务端（本项目）看到的是「上游在自己的响应体中途把连接关掉」**，报错形态是 `流传输中断: unexpected EOF`——chunked 响应没有正常收尾，而请求上下文仍然存活。**这是上游侧的动作，不是本项目、也不是下游客户端。**
2. **这个切断有固定时长墙：约 300 秒，而且与模型相关。** 本次日志中 15 次切断的实测耗时是 **301.4–307.9 s**（另 1 次 281 s），全部发生在 `glm-5.3-flash` + `stream` 上，跨 4 个客户端会话、跨越 1 小时 37 分钟，与账号无关（期间无任何账号级动作）。**决定性反例：11:32:24 → 11:40:43 有一条 `GLM-5.3` 的流跑了 499 s 并成功交付 31,386 token，与 flash 的多次切断完全时间重叠。** 所以墙不是「链路整体坏了」，而是与模型/路径绑定。
3. **它对 flash 是当天中途新增的**：同一个容器在当天早些时候跑通过 8 次超过 300 s 的 **flash** 长流（378 s / 408 s / 413 s / 443 s / 465 s / 468 s / 542 s / 559 s，产出 13k–21k output token）。**flash 最后一次成功超过 300 s 的流结束于 11:26:35 UTC，此后 15 次 flash 长流无一成功。**
4. **数据一直在流，直到被切断的那一刻**——所以这不是「空闲看门狗」意义上的静默卡死。客户端记录的 reasoning 增量在 5 分钟窗口内有 1 万–1.4 万个 chunk，末尾几个 chunk 的到达间隔是 0–100 ms。
5. 客户端的「重新思考」是它自己的重试策略：把这类失败归类为 `TRANSPORT`，**最多重试 5 次、500 ms 起指数退避**，而每次重试都是**原样重放整个请求、从零重新思考**。于是一次需要 5 分钟以上思考的模型调用会稳定失败 5 次、白烧 25 分钟，然后才报错。
6. 关键放大因素：**中途截断在本项目的错误分类里落进「final」出路——不换号、不冷却、不写任何账号状态**。所以调度层对这件事完全无感，客户端的 5 次盲重试可以反复落到同一条问题路径上，没有任何自愈。

## 3. 客户端侧证据：15 次切断 ↔ 15 次重试，一一对应

本次可访问到编辑器在 WSL 侧的会话记录（`session.v3.jsonl`，zstd 压缩的逐事件流），其中包含 `llm/retry` / `llm/retry-started` / `assistant/attempt` 事件——即「重新思考」的原始记录。

### 3.1 客户端把这件事定义为什么

```
failure = { message: 'Anthropic stream ended before message_stop', code: 'TRANSPORT' }
policyKey = ["normal", 5, ["EMPTY_RESPONSE","RATE_LIMIT","SERVER","TIMEOUT","TRANSPORT"], 500, 10000, 0.1]
maxRetries = 5
delayMs = 505 / 1052 / 1814 / 3984 / 8423   ← 实测退避序列（500 ms 起、×2、上限 10 s、带 10% 抖动）
```

要点：
- 客户端的判据是 **「流在 `message_stop` 之前结束」**，归类 `TRANSPORT`（连接级），**不是它的超时**（它另有 `Model request timed out.` 这一类）⇒ 又一次证明是链路被掐，不是客户端主动定时。
- **最大重试次数 5，且是原样重放**：每次重试重新发送完整上下文（本例 input 42k–68k token）、从零重新思考。这就是用户看到的「断联 → 重新思考」。
- 一次调用需要 >5 min 思考时，行为是确定的：**失败 5 次、每次 5 分钟、然后放弃**。

`b3c2a925` 是关键对照：**同一个请求、同一个模型、同样 `max` 思考档，只要这一次的思考+输出能在 300 s 内结束，就一切正常。** 说明墙是纯粹的时长限制，不是内容/尺寸问题。

### 3.3 `unexpected EOF` 与 `context canceled` 的区分

客户端主动放弃（用户停止、父会话抢占、上层超时）在服务端呈现为 `context canceled`（本次 3 次，耗时 268/186/33 s，不规则）。而 300 s 一族是 `unexpected EOF`（chunked 体被截断、上下文仍存活）。**同窗口内两种形态并存，正好互为内部对照：下游断开 ≠ 上游掐断。**

### 3.4 排除了「空闲超时」

每次被切断的尝试里，reasoning 增量 chunk 数是 10,464–13,969，末尾 12 个 chunk 的到达间隔是 0–100 ms。数据一直在流，直到被切断。一个「多久没数据就断」的看门狗不会触发。

## 4. 归属：三段排除法

链路（本机下载的日志包 → 输出到浏览器/编辑器）：

```
编辑器客户端(DSH) → 前端中转(New API) → 本项目网关 → 出口线路 → z.ai
```

| 段 | 是否可能 | 依据 |
| --- | --- | --- |
| 本项目网关 | **否** | 代码里不存在 300 s 量级的超时。上游客户端只有 Dial 30 s / TLS 10 s / `ResponseHeaderTimeout` 120 s / IdleConn 90 s，**没有整体 `Client.Timeout`**（否则报错会是 `context deadline exceeded`，不是 `unexpected EOF`）；HTTP 服务器刻意 `WriteTimeout=0`。唯一的 300 s 是 asyncpool 的 ticket 超时，而 `>>>` 日志行只由 sync `RunMessages` 产生——**本次全部请求都是 sync `/v1/messages`，ticket 超时无关**。 |
| 下游（编辑器 / 前端中转） | **否** | 下游断开会让请求上下文结束，走的是 `context canceled` 分支；本次 15 次都是 `unexpected EOF` 且上下文存活（§3.3）。前端中转若掐断，本项目看到的是客户端断开，而不是「上游把响应体截断」。 |
| 上游（出口线路 或 z.ai 边缘） | **是** | 排除法剩下的唯一位置，与前作 1800 s 的结论一致。 |

**尚不能把范围收窄到「出口线路」还是「z.ai 边缘/模型服务端」**，但已有倾向：

| 线索 | 读法 |
| --- | --- |
| 墙**只切 flash，不切 GLM-5.3**（499 s 的 GLM-5.3 与 flash 的切断时间重叠） | 倾向 **z.ai 模型侧/路由侧**的时长上限。线路是账号级属性（同一账号同时服务两个模型），线路故障不会只挑 flash。 |
| 墙出现在两次代理巡检（11:22:43 → 12:08:34）之间，期间没有任何线路被移除或改派 | 若是线路问题，只能解释为「某个未变动线路自身有 300 s 上限」；可这批线路当天早些时候跑通过 559 s 的 flash 流。 |
| 当天 flash 从「≥559 s 正常」变成「300 s 必切」，中途无本项目改动、无重启 | 像上游侧的一次**滚动变更**（收紧 flash 的单请求时长上限）。 |
| 09-19 同类现象的墙是 1800 s，也是 flash | 同一模型、同一量级的固定时长墙，只是数值变小 ⇒ 与「模型级上限」这一假设自洽。 |

仍无法排除的版本：**flash 的请求恰好被调度到了某种带 300 s 上限的出口路径**（例如某类线路/某段 NAT 对长连接的处理），而 GLM-5.3 的长流恰好没走那条路径。这需要 P1b 实验才能定论——**这也是本次分析唯一没被证据钉死的环节。**

## 5. 本次暴露的两个观测盲区（不修就没法定论）

### 5.1 请求开始时不记录出口身份
`engine.RunMessages` 只打模型名与 stream 标志，**不打账号、不打线路**。于是「是哪个账号走了哪条线失败」完全不可查——这正是前作 `analysis-flash-30min-stream-cut.md` §6 P0 就提出、但一直没落地的项。
**（2026-09-21 已补：诊断行带 `acc=` 与 `route=`，见 §6 P2。）**

### 5.2 中途截断不更新账号状态
15 次切断在账号维度**零痕迹**：没有 `连接失败，切换下一个`，没有冷却，没有 `last_error`。日志里看不出这几分钟里是同一个账号在反复挨打还是每次不同账号。
（这是刻意设计的结果：响应头已经发出、无法换号重试，只能走 `final`。但它同时意味着**没有任何机制据此绕开问题路径**。）
**（2026-09-21 已补：`Account.StreamTruncateCount` 累计留痕，**刻意不驱动状态机**——责任归属未定前冷却账号＝把上游的墙变成对账号的集体惩罚；判定路径见 §4.1。）**

## 6. 行动清单

### P1 对症（今天就能做，不需要改本项目）
300 s 是时长墙，**唯一的杠杆是把单次调用的时长压到墙以内**：

1. **把该工作流的思考档从 `max` 降到 `high` / `low`**。本次 5 分钟里绝大部分在思考（1 万个 reasoning chunk），这是最直接的杠杆。客户端设置里 `agent-default-model.reasoningEffort` 与 provider 的 `reasoning: max` 都要改。
2. **大产出拆轮次**：把「一次输出整个章节」改成多次 `Edit` 递增写入，单次调用控制在 ~1.5–2 万 output token 以内。
3. **该环节换 `glm-5.3`（非 flash）**，或把长输出任务拆成多个子任务并行（本例已在用子代理，可再细化）。
4. **调客户端重试策略**：现在是「原样重放 5 次」。对这种固定时长墙，重放内层参数不变 ⇒ 命中同一堵墙的概率不变。应改为「失败后降档/换模型再试」，或直接调小 `maxRetries`，避免白烧 25 分钟。

### P1b 归属实验（决定性，一次就能定论）
发一组 **2×2** 的请求，每个都必然超过 300 s（同一 prompt、同一账号各发一次）：

| | `__direct__`（直连） | 一条出口线路 |
| --- | --- | --- |
| `glm-5.3-flash` + 高思考档 | A | B |
| `glm-5.3` + 高思考档 | C | D |

判读矩阵：

- **A 与 B 都 ~300 s 收尾，C 与 D 都能跑完** ⇒ z.ai 的 **flash 模型级时长上限**。本项目只能适配（降档/拆轮次），并在文档里把它记成已知上游约束。
- **A/C 正常、B/D 被切** ⇒ **出口线路的连接存活上限**：把长流账号改派到直连或已验证的长流线路，并给 `proxy-health` 加流式探测。
- **A 也 ~300 s** ⇒ 与线路无关，直连同样被切；此时再看 C（同链路跑 glm-5.3）是否正常，即可判断是「模型级」还是「账号/出口 IP 级」。
- **只有 B 被切** ⇒ 单条线路问题，直接剔除该线路即可。

旁路复核：不经本项目直接 `curl -N` 打 z.ai 编码端点，观察是否同样 ~300 s 收尾（可同时验证是不是本项目引入的）。

### P2b 调度加固（注意别把上游的锅扣到账号上）
- 给「上游中途截断」加**账号级 / 线路级计数**（保留 `json:"-"`，不动 34 键契约），**连续 N 次（建议 3 次）** 再冷却 / 换线；单次就冷却会把 z.ai 侧的时长墙变成对账号的集体惩罚（与 405 那次的教训同类）。
- 把 `proxy-health` 的普通 GET 探测升级为「带凭据的短流探测」：能否在 N 秒内收到首个增量、流能否走到 `message_stop`。现有探测**结构上抓不到**「能连上、能协商、但流在中途被掐」这一族。

### 副作用记录
15 次被切断的尝试，上游其实已产出 1 万–1.4 万个 reasoning chunk，但因为没拿到终值（`UsageCollector.UsageComplete` 为假），按现行口径**不计入账号用量**；同时客户端每次重试都要重发 42k–68k input token 的上下文（部分可命中 prompt cache）。这类浪费在长流被掐的场景里是系统性的，值得在面板上单独暴露一个计数。

## 7.与前作（1800 s）的关系

两次现象的**根因结构相同**（本项目 ↔ z.ai 之间的固定时长上限），但：

| | 2026-09-19 | 2026-09-21 |
| --- | --- | --- |
| 墙 | 1800 s | ~300 s |
| 服务端报错 | 上游干净收尾但无 `message_stop`（`!enc.finished`） | `unexpected EOF`（chunked 体被截断） |
| 客户端路径 | OpenAI 转译端点 | 原生 `/v1/messages` |
| 客户端反应 | 报「写入失败 / Tool call ended without a terminal event」 | `TRANSPORT` 分类 + 5 次指数退避盲重试 |
