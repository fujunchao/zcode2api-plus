# 导入初始化缺口修复计划

日期：2026-10-15（Asia/Shanghai）。基线：`b08b623` / `v2.10.6-go`。

## 复现与根因

- 新增真实后台导入回归 `TestNewAccountInitializationImportRegistersBeforeDispatch`，只使用隔离 SQLite、合成 JWT 和本地测试代理。
- 测试提交 `776e08f` 的 [CI 38702403876](https://github.com/fujunchao/zcode2api-plus/actions/runs/38702403876) 明确失败：导入成功且创建的是 JWT，但初始化任务为 `<nil>`。
- `Store.ImportAccounts` 调用 `AddAccountWithIdentity` 时没有初始化选项；`handleImport` 收尾只有 `AutoAssignProxies`。上一版把整条导入路径当作备份恢复而排除，这与现在使用导入来添加新账号的需求不符。
- 不是取额代理失效或轮询算法的问题。只唤醒工作者也不够，因为根本没有持久任务。

## 本次行为

1. 策略开启时，新导入的 JWT 在账号创建事务内登记初始化；原有停用模型设置也在首次入库时保存，避免第二次更新中断刚开始的任务。
2. HTTP 导入唤醒现有初始化工作者，完整复用“查询 → 候选轮询 → 确认到账 → 固定绑定”。CLI 导入登记相同任务，后续 `serve` 恢复执行。
3. 重复导入不登记或重置任务，不覆盖已托管账号的初始化进度；API Key 与策略关闭时保持原导入路径。
4. 用户确认：对已经导入的未取额账号提供手动补入入口，不自动扫描老账号。

## 手动补入

- 账号页勾选一条或多条记录，选择“补入初始化”，明确确认将接管这些账号的代理路由。
- 新增受管理员鉴权保护的批量补入入口；服务端在锁内重新检查账号，而不是信任前端的余额或“新号”标记。
- 只接受启用、未归档、可管理且无历史使用/成功领取/已分配额度证据的 JWT；已有任务不重建，冷却或上游等待不清零。
- 登记任务不等于认定上游有资格。工作者仍先进行真实额度核验，未知结果不领取、不放入业务调度。
- 同批合格账号、任务和严格代理意图单事务提交，失败不发布半套内存状态；逐项报告不合格/已有任务/不存在等结果。
- 旧版本没有可靠的“来自导入”标记，因此入口不会冒称能自动识别所有漏处理记录，只处理管理员明确选中的账号。

## 实施及验证顺序

1. 先推送最小失败回归（已完成），确认缺口。
2. 修复导入创建选项、初始元数据原子性与工作者唤醒，覆盖导入完整取额及重复导入。
3. 先补手动补入失败回归，再实现校验/事务及账号页确认入口。
4. 补充策略关闭、API Key、已领取/有用量、重复请求、存储失败、批量和重新打开数据库的保护测试。
5. 更新导入结果提示、使用指南及版本说明；前端本地构建只生成需要提交的 `frontend/dist`。
6. 最终提交完整 CI 通过后推送默认分支并发布 `v2.10.7-go`；发布再次复用完整 CI，最后核对 5 个二进制、amd64/arm64 镜像与 `latest`。

不在开发机运行自动化测试，不读取运行 `data/`，不操作真实账号或生产服务器；已有无关未跟踪文件保持不动。
