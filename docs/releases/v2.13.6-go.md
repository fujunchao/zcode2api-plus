# v2.13.6-go

修复线上「领取优惠」一直失败：可领套餐号改从营销触达（marketing/touch）获取，`billing/preview` 已停投。

- **套餐发现换源**：上游现在只在 `GET /api/v1/marketing/touch` 的 delivery 里投放活动套餐（`buttons[].action.type=claim_zcode_plan` 的 `args.plan_id`），`billing/preview` 恒返回 `code=0` 且没有 `data`。此前链路永远取不到套餐号，从未真正发出 `POST /billing/claim`，服务端只看到「上游无投放套餐」。
- **新增营销触达客户端**：四项身份头（Authorization / X-Device-Mid / X-Client-Language / X-ZCode-App-Version）、`seq` 后置自增、15s 超时、经账号线路出站；解析 banner 与 popup 两种投递形态及三处 `zcode_plan` 元数据。
- **预览与自动领取同一来源**：`ClaimablePlans` 以营销触达优先、`billing/preview` 仅作回退；后台「刷新资格」、入池自动领取与每日定时领取因此看到同一份套餐。
- **成功回执**：领取成功后 `POST /api/v1/marketing/touch/action {campaign_id, action_type:"confirm"}`。`campaign_id` 必须在领取前取得——账号领到活动后上游立刻撤下该投递，事后反查必然落空，故由发现阶段透传给领取函数。
- **无投递不再借用 1005**：营销触达「0 条」是瞬态（实测同账号十几分钟后又能看到投递），落长冷却会把可领账号锁一小时；改为可重试语义，并保留 `app_version`/凭据诊断日志，用于区分「上游没有活动」与「伪装身份漂移」。
- 补充回归：preview 恒空 + 营销触达有投递的端到端发现/领取/回执、两种投递形态、`seq` 与四头形态、无投递语义、回执失败不阻断、回退语义与「领后投递为空」。

无需手工数据库迁移。领取冷却仍优先采用上游给出的 `ends_at`；「本账号当前没有可领活动」只落短冷却。

二进制：Linux amd64/arm64、macOS amd64/arm64、Windows amd64。
镜像：`ghcr.io/fujunchao/zcode2api-plus:2.13.6-go` 与 `latest`。
