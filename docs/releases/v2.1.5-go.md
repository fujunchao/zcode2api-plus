# v2.1.5-go

修正账号用量的计入判据：编辑器类客户端收到 `finish_reason` 就断开连接时，一笔已经确定的用量不再被整笔丢掉。

## 修复

### 客户端提前断开不再吃掉整笔用量

zcode 编辑器这类客户端拿到 `finish_reason` 就立刻关闭连接，**这是它的常态行为**——运行日志里那一大片 `流传输中断: context canceled` 大多来自它，并非故障。

但账号 token 的计入判据此前是「交付有没有报错」，于是这类正常断开会让整笔用量作废。线上实测因此漏计过一次 **57,352 output token** 的生成（该次请求在同一时段被记为「客户端取消」，管理面板的 token 数会系统性偏低）。

- **新判据**：以上游是否交出终值为准。收到带非空 `stop_reason` **且**含 `output_tokens` 的
  `message_delta`（或非流式 JSON 解析出 `usage`）即认定用量完整，此后即便交付因客户端断开
  而失败，仍照常累计。
- **两个条件必须同时成立**：只看 `stop_reason` 会在 `usage` 缺失时把 output 记成 0；只看
  `usage` 又会把中途的增量更新当成终值。判定刻意偏保守——判不出「完整」时沿用旧的
  「不计入」，只会少算、不会算错。
- **半截流行为不变**：缺少终值的断流（没见到 `stop_reason`）仍旧不计入。
- 同步路径（`gateway.finishDelivery`）与 async 票据路径（`asyncpool.forwardSSE`）同口径，
  契约写入 PLAN §5.7。

## 验证

- **反向验证**：把计入分支临时短路后，新增用例立即失败（账号 `TotalOutputTokens:0`），改回即通过——用例确实守得住这条回归，不是「写了就算数」。
- 新增用例：`TestUsageCollectorUsageComplete`（5 个子例）、`TestAbortedDeliveryStillCountsFinalUsage`（含「半截流不得计入」反例）、`TestMidStreamFailureAfterFinalUsageStillCounts`。
- `go build ./...`、`go vet ./...` 干净；`go test -count=1 ./...` 全绿。本机 `internal/captcha` 的符号链接用例仍因开发机沙箱把 symlink 降级为零字节文件而失败（既有的环境问题，与本次改动无关）；`-race` 由 CI 覆盖。

## 升级

```bash
docker compose pull && docker compose up -d
```

升级后无需任何配置变更。历史少计的用量不会追溯修正，从本版本起计入。
