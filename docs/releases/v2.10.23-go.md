# v2.10.23-go

## 单线绑定软上限：把「线路数不足」变成可见指标

v2.10.21 / v2.10.22 解决的是「脏线别打断工作」与「脏线要能清出去」。这一版处理的是
容量视角：**当可用线路不够时，账号会压到少数几条线上**，其中一条变慢或变脏，影响面
就是全池。

### 一个必须说清的事实

原计划把 `ZCODE_PROXY_MAX_BINDINGS_PER_LINE` 当作「分散器」，实施时核对代码发现它
**不可能改变选线结果**：

- `leastLoadedProxy` 本来就选绑定最少的线路；
- 「未超限」的绑定数必然严格小于「已超限」的，所以「先选未超限、否则回落」的两趟
  逻辑与单趟**必然一致**；
- 24 个账号同绑一条线的真实原因是当时**只有那一条线可用**（其余被隔离或删除）。

所以本版把它定位为**容量口径与告警**，并在文档里更正了原验收标准。要真正分散，
只能增加可用线路——代码变不出线路来。

## 行为变化

### 1. 软上限判定（语义等价，口径明确）

`leastLoadedProxy` 增加 `cap` 参数：先在 `occupancy < cap` 的线路里选最少的，全部超限
再回落全量。`cap <= 0` 关闭判定。**任何情况下都不会拒绝分配**，不产生
`auto_pending_proxy`。

### 2. 容量不足告警

当选中的最空闲线路绑定数已达上限：

```
[~] line-cap capacity_short=1 cap=8 bindings=24 candidates=1
```

60 秒限频。这是「线路数不足，该扩池了」的唯一可见信号——此前只能从「24 个号同绑
一条线」的间接现象里猜。

### 3. 改派落点分布

批量改派（删线、隔离改派）结束时记录：

```
[~] proxy-reassign assigned=11 top_targets=p1:6,p2:4,p3:3,+1
```

按绑定数降序、同数按 ID 升序，最多 3 条，其余折 `+N`。删除 10 条线之后账号到底压到
哪几条线上，现在可以直接从日志读出来。

## 配置

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `ZCODE_PROXY_MAX_BINDINGS_PER_LINE` | 8 | 单线绑定容量口径；0 = 关闭判定（不告警） |

## 兼容性

- 无数据迁移；`accounts.data` 键集不变。
- `cap` 默认 8，但选线结果与 v2.10.22 完全一致（见上）；唯一新增输出是日志。

## 回归覆盖

未超限线路存在时（9 / 8 / 3 绑定，cap = 8 / 4 / 0）恒选绑定最少的一条；全部超限时
仍能分配并回落最少；选中线路已达上限时输出 `capacity_short` 且仍返回线路；改派落点
聚合 `p1:6,p2:4,p3:3,+1` 与 `top<=0` 全量输出。

所有自动化验证由 GitHub Actions 执行，分支 CI 与发布工作流复用的完整 CI 均为门禁。
