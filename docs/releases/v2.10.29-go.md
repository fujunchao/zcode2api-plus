# v2.10.29-go

## 深探标定修正，以及一个刻意不做的改动

v2.10.28 的隧道探针跑了 20.4 小时（8221 条记录），给出一批可以离线复核的数据。
本版只做两件事：修正早停下限，给 3009 加一个默认关闭的实验开关。**不切 enforce、不降写入量。**

### 先说结论：探针的「失败」有 22.5% 是判据造成的

`ZCODE_PROXY_DEEP_MIN_BYTES=256KB` 要求对端至少接收 256KB 才算早停合格，但对端
普遍在 80–112KB 或 192–224KB 就主动关闭。用真实流量交叉验证：

| 早停下限 | 真实成功过的线路（81 条）被判定为「好」 |
|---|---|
| 256KB（旧） | **41 / 81 = 51%** |
| 192KB | 67 / 81 = 83% |
| 160KB | 71 / 81 = 88% |
| **128KB（新）** | **77 / 81 = 95%** |
| 96KB | 77 / 81 = 95%（没有增益） |

96KB 与 128KB 的覆盖率完全相同——**128KB 是达到满覆盖的最小值**，这就是本版
选它而不是「再低一点」的理由。

- 改动：`ZCODE_PROXY_DEEP_MIN_BYTES` 默认 `262144 → 131072`；
- 预期：shadow 的 ok 率 8.8% → **29.3%**（725 + 1686 = 2411 条）；
- 边界：只影响 shadow 信号。enforce 仍是 opt-in，删除路径不受影响
  （首轮 `waiting` → 二阶段浅探 `recovered`，删除仍需二段失败 + 对照线）。

## 为什么不同时把 `DeepBytes` 降到 256KB

评审建议过这一步（可省 25% 探针流量）。复核后**不做**：

```
1MiB / 12s ≈ 85KB/s
```

`DeepBytes=1MiB` 与 `DeepBudget=12s` 不是独立参数：满写分支不受 `kbps/ms` 约束，
**写入量本身就是速率底线**，而且正好等于 `DeepMinKbps=85`。降到 256KB 会把底线
压到 `256KB/12s ≈ 21KB/s`（弱 4 倍），并让探针在「突发后卡死」发生前就停止写入。

本次日志里正好有反例：**78 条探针写到 ≥256KB 后耗时仍 ≥8s**，其中只有 12 条速率达标。
它们正是 `probe.go` 注释里点名要抓的「内核缓冲先吞几百 KB、之后对端不读」的线；
降 size 会让它们全部翻成 OK。

要同时保住语义和省流量，正确做法是给满写分支补 `kbps ≥ 85` 再降 size
（回放：2412 条 / 29.3%，与原判据几乎一致）。那是代码语义变更，留 v2.10.30 单独做。

## 3009 并发准入：加实验开关，默认不改行为

10-20 的窗口里 5 条 429 全是 `code=3009 model concurrency limit exceeded`，
分布在 5 个不同账号/线路，同样内容之后都成功。但 `engine.go` 的设计假设是
「模型级准入、换号无用」，而且其中 2 条是同账号延迟后成功的——证据不足以直接推翻。

新增 `ZCODE_BUSY_SWITCH_AFTER`（默认 `0`）：

| 值 | 行为 |
|---|---|
| `0` | 原地重试至预算用尽，原样透传 429（现行为） |
| `N>0` | 原地重试 N 次后换号，不冷却账号，请求级上界仍由 `MaxAccountAttempts` 兜住 |

只改 sync 路径：本窗口 75 条 3009 告警全部来自 sync，async 格式 0 条。
实验期建议看 **p50 延迟 + 每条 429 消耗的账号数**，不要用 p90（7 天样本约 40 条，会抖）。

## 配置

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `ZCODE_PROXY_DEEP_MIN_BYTES` | `131072` | 早停判定下限（256KB → 128KB） |
| `ZCODE_BUSY_SWITCH_AFTER` | `0` | 3009 原地重试几次后换号；0 = 不换 |

## 兼容性与回滚

- 无数据迁移、无 schema 变化；
- 两个开关互相独立：`ZCODE_PROXY_DEEP_MIN_BYTES=262144` 回到旧标定；
  `ZCODE_BUSY_SWITCH_AFTER=0` 回到旧行为（也是默认）。

## 回归覆盖

- 150KB 早停 + 128KB 下限 → OK；32KB 早停 → 失败（下限不是无限放宽）；
- 对端先吞 300KB 再卡死 → 1MiB 判据下失败（锁住「不能只降 DeepBytes」的理由）；
- 3009 开关 0：同一账号重试 3 次、透传 429、账号不冷却；
- 3009 开关 1：重试 1 次后换号成功、使用两个账号、两者都不冷却。

所有自动化验证由 GitHub Actions 执行，分支 CI 与发布工作流复用的完整 CI 均为门禁。
