# v2.0.6-go

账户管理这一层借鉴了 zcode-switch（pjpv/zcode-switch，单账号桌面切换器）里可迁移的设计：
**身份与凭据解耦、每账号独立设备指纹、领取状态落盘**，并让 OAuth 登录本身就能走选定线路。

## 新增内容

- **身份与凭据解耦**：入池判重改为按 `user_id → email → 凭据` 三轮优先级比对，
  而不是只比凭据字节。此前同一个号重新登录时 token 字节变了，会被当成两条记录；
  `user_id` 取自 JWT payload（`sub` 兜底），手动添加、导入、CLI 路径自动获得。
  比对必须分三轮而不是单遍取首个命中——单遍会让列表里靠前的低优先级判据抢先。
- **每账号独立设备指纹**（`virtual_device_mid`）：此前全仓共用一份全局
  `device_mid.txt`，同一台机器上的多个账号等于主动把"同一设备"这个关联线索递给上游。
  取值走 `Account.DeviceMidOr`，缺失时才回退全局值；主请求、额度查询、领取三处注入点
  全部改掉。**升级后首次启动会为存量账号一次性补齐**（幂等，不删除、不合并任何账号）。
- **领取状态落盘**：上游在成功响应与 `1005`（当日名额用完）里都会给出
  `data.plan.ends_at` 作为下次可领时间，此前只取了错误文案、把时间丢掉了。
  现在落到 `Account.claim.next_at`，后台显示倒计时；重启不再把刚领过的账号重领一遍
  （上游 `1003` 虽幂等，但白耗验证码与风控额度）。
- **领取冷却与串行闸门**：冷却只作用于自动路径（手动点按钮始终可强制）；
  批量导入多个账号时不再同时轰验证码池。**刻意不做后台周期重试**——
  长驻服务上加定时领取会持续产生上游流量。
- **登录时即可选定出站线路**：`/admin/api/login/start` 接受 `proxy_id`（线路）或
  `proxy_url`（裸地址），登录、API Key 兑换、随后的额度刷新与领取走同一条线路，
  并在登录成功后写入账号。这是链路问题而不是参数问题：只在登录本身走代理、
  后续直连，等于拿真实 IP 去打上游。

## 使用说明

- 无必填改动；新增三个可调项（默认值即推荐值）：
  `ZCODE_CLAIM_CAPTCHA_COOLDOWN=3600`（验证码不可用／已领过但上游没给时间的冷却）、
  `ZCODE_CLAIM_RETRY_COOLDOWN=600`（其他领取失败的冷却）、
  `ZCODE_CLAIM_PREVIEW_COOLDOWN=60`（「刷新资格」的只读节流，0 关闭）。
- 后台「新增帳號」对话框的授权登入页现在有出口线路下拉；授权链接生成后出口即锁定，
  需更换请取消后重新开始。
- CLI 的 `login` 子命令暂不支持代理（仍直连）。
- 导出格式保持 version 1 不变、刻意不含新字段：设备指纹是机器绑定的，
  跨机搬运反而有害（导入后重新分配更合理）。

⚠️ 升级后存量账号的 `X-Device-Mid` 会变更，上游可能识别为「换了台机器」。
建议升级后先看一轮额度查询是否正常，再放流量。

[客户端兼容说明](https://github.com/fujunchao/zcode2api-plus/blob/v2.0.6-go/docs/client-compatibility.md)

## Docker

```bash
docker pull ghcr.io/fujunchao/zcode2api-plus:2.0.6-go
```

支持 linux/amd64 和 linux/arm64，同时更新 latest；现有数据卷与非 root 运行方式不变。
设备指纹随账号存进数据卷，容器重建后不变。

## 能力依据

- [Z.AI 官方文档](https://docs.z.ai/)

`data.plan.ends_at` 取自官方客户端 billing/claim 与 billing/preview 响应；`1005` 为
当日名额用完、`1003` 为已领取过，均沿用既有错误码表。`user_id` 取自 JWT payload 的
`user_id` 声明（`sub` 兜底），与官方客户端激活事件上报的标识同源。

登录链路确实经选定代理出站这一点由测试保证（假代理侧断言收到 `CONNECT`），
真实线路（http / socks5）在线完成一次完整登录仍待验收；存量账号迁移后上游是否把
`X-Device-Mid` 变更识别为换设备，也需在线观察。
