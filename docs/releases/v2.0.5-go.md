# v2.0.5-go

修正瞬时限流的处理：不再因为一次 429 就把一个健康账号冷却 300 秒。

## 修复内容

- **429 按「限制挂在哪层资源」分成三类**，而不是一律当成账号被限速：
  `code=3010` 是模型并发准入限制，换号无用，账号状态完全不变、只原地等待；
  官方额度／用量上限码族只标记**该模型**耗尽，账号对其他模型仍可调度；
  其余（1302／1305 等瞬时限流）才是这个账号被限速。
- **瞬时限流不再一次 429 就换号**：先对同一账号原地重试一次（约 1 秒，带 ±20% 抖动），
  用尽才标冷却并换号。只给一次是因为池子里通常还有别的账号，换号成本是百毫秒级，
  而每次原地等待都是确定的秒级延迟，且被限流后立刻重试大概率仍然失败。
- **冷却时长改为按连续被限流的次数递进**：30s → 60s → 120s → `ZCODE_COOLING_SECONDS`
  （默认 300s），任意一次成功调用后计数归零。此前无论第一次还是第 N 次都固定冷却 300s，
  而 300s 本是给连接失败、503 这类硬故障设定的值；把「瞬时」的限流按硬故障惩罚会
  让账号池被快速掏空。
- **三类重试的预算拆成独立计数**：验证码刷新、3010 并发准入等待、瞬时限流原地重试。
  此前三者共用同一个循环变量，一次验证码重试就会吃掉 3010 的等待预算，还会让等待时长
  取到错误档位，最坏情况下 3010 直接把 429 原样回给客户端。
- 同一账号在同步路径（`/v1/messages` 与 OpenAI 兼容层）与异步路径
  （`/async/v1/messages`）下现在标出相同状态——两条路径共用同一套标记函数。

## 使用说明

无需改动任何配置，默认行为与旧版兼容，也没有新增必填项。

想调整瞬时限流冷却阶梯的封顶值，仍用既有的 `ZCODE_COOLING_SECONDS`（默认 300）。
预热期（首次被限流）的 30 秒是固定的，不受该变量影响。

日志里会看到两段新文案：限流后先出现「被瞬时限流 429，N s 后原地重试」，
重试用尽后才出现「连续第 N 次被限流，冷却 N s 后切换下一个」。

账号池全部冷却时客户端仍会收到 503 `no_available_account`，只是现在更难触发；
若频繁出现该错误，请检查后台账号状态，而不是只看单个请求的延迟。

[客户端兼容说明](https://github.com/fujunchao/zcode2api-plus/blob/v2.0.5-go/docs/client-compatibility.md)

```bash
docker pull ghcr.io/fujunchao/zcode2api-plus:2.0.5-go
```

支持 linux/amd64 和 linux/arm64，同时更新 latest；现有数据卷与非 root 运行方式不变。

## 能力依据

- [Z.AI 官方文档](https://docs.z.ai/)

额度／用量上限码族取自官方错误码表；`code=3010` 为模型并发准入限制。1302／1305 归入
瞬时限流来自既有实现说明与实测观察，其窗口量级（秒级还是分钟级）仍待在线验证——
若是分钟级，则原地重试意义有限，正确杠杆是继续缩短冷却而非追加重试次数。

客户端回归使用本地模拟上游；生产账号的在线行为仍以实际 Z.AI 端点为准。
