# v2.10.18-go

## 到期门槛：先用「下周就作废」的额度

原选号第 4 层只按**剩余多少**排序，与「什么时候作废」方向相反：一个号有 10M 长期池，
会排在 9M 但两天后到期的号前面，后者没用完就整批作废。

本版在 promo 层之前插入一道**到期门槛**：

- 持有「窗口内到期、且不会自动刷新」额度列的账号优先，默认窗口 3 天。
- **只收窄候选，不按到期排序**：并列组内仍然轮询。`zcode-pool` 的「按到期升序 + 取前 4 个」
  会把流量压到少数账号，这里刻意不照搬。
- 「不会自动刷新」的判定：`period` 含 `one_time`，或 `period_start`/`period_end` 跨度 > 36h。
  **日额度（跨度≈24h）不算**——它次日刷新，没用完不等于浪费，抢它只会打乱轮询。
- 到期时刻优先取 `expires_at`（更像套餐/活动结束），缺失回落到 `period_end`；
  秒/毫秒/微秒/纳秒按量级归一，识别不了一律跳过（宁可少提一个号，也不误判长期池）。
- 已经过期、但快照仍显示有余额的列不参与：额度其实已作废，提上去只会白打一次上游。

## 与 promo 层的关系

两层都保留，顺序是：**到期门槛 → promo → 剩余最多组 → 轮询**。

- `one_time` 里也有 20 天后才到期的，它不紧急，不该压过「套餐 2 天后结束」；
- 但没有更急的账号时，promo 仍然优先——这一层没有被削弱。

## 配置

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `ZCODE_SELECT_EXPIRE_FIRST_DAYS` | `3` | 到期窗口（天）；`0` = 关闭，回到 v2.10.17 行为 |

同规格账号（同一套餐、同一周期）整体在窗口内时，门槛是 no-op，行为与旧版完全一致；
只有「一部分账号的额度下周就没了」时才会体现差异。

## 观测

- `no_available_account` 的结构化 details 在存在时输出 `expiring_soon`（可用账号中持有
  窗口内会作废额度的数量）。
- 诊断行 `deadline_hit`（上一版）与本版门槛互不影响。

## 兼容性与回滚

- 无数据迁移、无接口变更、无前端改动。
- `ZCODE_SELECT_EXPIRE_FIRST_DAYS=0` 立即回到旧的选择顺序，不需要回滚镜像。
- 若上游 `expires_at` 的语义与预期不符（例如实际是「周期内剩余时间」），
  表现是「多提了一批账号」而非 503；关闭开关即可恢复。

## 回归覆盖

窗口内到期优先于剩余更多、到期压过 20 天后的 `one_time`、无更急账号时 promo 仍优先、
全池都在窗口内时仍逐个轮转、日额度不触发门槛、开关为 0 时行为不变、已过期与无余额不参与、
毫秒时间戳归一、相对秒数不被当作绝对时间戳。

所有自动化验证由 GitHub Actions 执行，分支 CI 与发布工作流复用的完整 CI 均为门禁。
