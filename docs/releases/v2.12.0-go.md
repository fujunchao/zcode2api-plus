# v2.12.0-go

## 验证码浏览器生命周期治理：空闲不再空转，常驻不再无限涨

### 一、背景

2026-11-06 在服务器上发现 `zcode2api` 容器 109% CPU / 1.379 GiB 内存，容器内一只 Chromium
从 11-03 拉起后跑了 3 天，单进程 RSS 1.5GB、CPU 30%。取证结论（见
[服务端取证](../findings/server-forensics-browser-20261106.md) 与
[代码审计](../findings/browser-lifecycle-audit-20261106.md)）：

| 观测 | 定性 | 依据 |
|---|---|---|
| 浏览器活了 3 天不退 | **设计**（懒启动 + 上游 Python 版同构的「活到进程退出」） | 池里没有任何空闲/次数/时长/RSS 闸门 |
| 空闲期仍每 95 秒解一次验证码 | **缺陷** | 深空闲只把水位压到 1，而 TTL 95s < idleStop 900s，那条 token 必然过期再补；3 天约 2700 次求解、真实消费 **0** 次 |
| RSS 174M→1509M 线性、CPU 3.4%→30.7% | **回收缺口** | 成功路径刻意复用同一页面（省 224KB SDK 重载），页面状态只增不减 |

三代浏览器的 1Panel 历史曲线互相印证：**峰值只跟存活时长相关，与业务量无关**
（32.7h→0.58GiB、41.1h→0.92GiB、72.7h→1.48GiB）。

同时纠正两条误判：容器**没有**内存上限、宿主 `MemAvailable` 实测 1.76~1.95 GiB（不是 `free` 列的 850MB），
3 天零 OOM-kill；真正的代价是 CPU 争抢（PSI cpu some 峰值 64%）。109% 里浏览器只占约三成，
其余是 zcode2api 自身的代理巡检。

### 二、本版改动

按「先止血、再兜底、最后改形态」分三层，每层都能用 env 单独关掉：

| # | 改动 | 默认 | 关闭方式 |
|---|---|---|---|
| A | **空闲停补**：深空闲无条件停止主动补货（原来依赖「桶里还有 token」才停，等于永不停） | 15 分钟 | `ZCODE_CAPTCHA_POOL_IDLE_STOP_SECONDS` 调大 |
| B | **worker 寿命闸门**：存活 6h / 求解 5000 次 / 父进程 RSS 1500MB 任一命中即在两次求解之间重建 | 开 | 三项各设 `0` |
| C | **池级空闲停池**：连续 30 分钟无求解即释放整个浏览器，下次冷启动约 8 秒 | 30 分钟 | `ZCODE_CAPTCHA_BROWSER_IDLE_STOP_SECONDS=0` |
| D | **领取前预热**：定时领取前 2 分钟解一条 token 入桶，抵消冷启动 | 120 秒 | 固定提前量，随 C 生效 |
| E | **CPU governor 改 cgroup v2 口径**：原来读 `/proc/stat` 是整机口径，容器 109% 在 4 核机上只算 27%，永远碰不到阈值 | 开 | `ZCODE_CAPTCHA_CPU_GOVERNOR=false` |

配套的三处泄漏兜底（机制已证实、本次现场未触发，属防御性修复）：

- `closeWorker` 看门狗超时后**强制 Kill**：rod 的 `Launcher.Cleanup` 只等进程退出、不杀进程，
  旧实现超时后仅打日志，浏览器假死时会留下杀不掉的孤儿，池随后重建一只导致内存翻倍；
- `Connect` 失败路径改为 `Kill` 再 `Cleanup`：原实现会永久阻塞在 `<-l.exit`，factory 永不返回；
- 页面改用 `context.WithoutCancel` 绑定：原来绑的是池的启动超时 ctx（factory 返回即 cancel），
  `Close`/`reload` 走已取消的 ctx 会直接返回 `ctx.Err()`，页面关不掉。

观测补强：

- 新增 10 分钟窗口的**补解汇总日志**——成功 mint 此前完全静默，3 天日志里一条 captcha 都没有；
- `/admin/api/monitor` 的 `captcha` 增加 `idle_stopped`（区分「空闲停补」与「补货失败」）；
- 新增 `captcha_browser` 上报真实池状态（`standby`/`starting`/`online`/`cooling`/`closed`）。
  旧实现只看配置开关，真机出现过「浏览器进程根本不存在，控制台仍显示 online」的假信号。

### 三、效果对照

| 指标 | 改前（实测） | 改后（预期） |
|---|---|---|
| 空闲期求解次数 | 909 次/天，永不停止 | 0 次/天 |
| 单 worker RSS | 3 天线性涨到 1509MB | ≤6h 重建一次，约 300MB 量级 |
| 空闲期常驻内存 | 300MB ~ 1.5GB | 0（30 分钟后释放） |
| 空闲期浏览器 CPU | 3.4% → 30.7% | 0 |
| 首个验证码请求延迟 | 0（池热） | 8s 冷启动（定时领取已提前预热） |

### 四、升级与回滚

- 升级不改变任何接口、配置项与数据结构，无需操作；所有新 env 都有默认值。
- 想恢复旧行为（浏览器常驻到进程退出）：`ZCODE_CAPTCHA_BROWSER_IDLE_STOP_SECONDS=0`
  且 `ZCODE_CAPTCHA_BROWSER_MAX_AGE_SECONDS=0` `ZCODE_CAPTCHA_BROWSER_MAX_SOLVES=0`。
- **设备指纹提示**：每次浏览器重启都会换一次设备身份（随机 `--fingerprint` 种子 + 新建临时
  user-data-dir）。空闲停池默认取 30 分钟而不是 15 分钟正是为此；若观察到验证码通过率下降，
  把 `ZCODE_CAPTCHA_BROWSER_IDLE_STOP_SECONDS` 调大或设 0。

### 五、验证

- 分支 `codex/captcha-idle-stop` 三个提交逐批通过完整 CI（含 `test` / `test-race` / `test-repeat` /
  五平台交叉编译 / `docker` / `sdk-compat` / `newapi-compat` / `frontend`）。
- 新增回归测试 12 项：深空闲停补、深空闲仍可按需求解、worker 三阈值回收、Close 卡死时 Kill、
  RSS 读取、cgroup 采样与配额回退、空闲停池与在途保护、预热不重置空闲计时、预热时刻跨日回绕、
  监控状态机（standby/online/cooling/closed）。
- 原有 `TestTokenPoolIdleShrinkAndStop` 把 `ttl` 从 1h 改成生产默认 95s——正是这个「测试用宽参数」
  把缺陷掩盖了三个版本。
