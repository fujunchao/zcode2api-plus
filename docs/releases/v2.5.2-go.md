# v2.5.2-go

一次**伪装版本号对齐版**。

## 背景

v2.5.1 修好了激活事件与计费请求的出站一致性（同账号同 IP）之后，preview 仍然返回空 plans，
claim 日志恒为「沒有待領取的套餐」。解包本机实装的官方客户端做源码级对照后发现，
激活上报链路里的**事件体与端点完全一致**（16 个字段逐项相同、`/api/v1/event/report` 相同、
`app_launch` + `app_daily_active` 两个事件相同），差异集中在外壳：

| 维度 | 官方客户端 3.14.3 | 本版之前 |
|---|---|---|
| 事件上报请求头 | 11 个（UA / HTTP-Referer / `X-Title` / `X-ZCode-App-Version` / `X-Platform` / `X-Release-Channel` / `X-Client-Language` / `X-Client-Timezone` / `X-Os-Category` / `X-Os-Version` / `X-Device-Mid`） | 仅 `Content-Type` |
| 伪装版本号 | 3.14.3 | 3.11.2 |

完整对照见 `docs/analysis-zcode-client-activation-diff.md`。

## 本次改动

- `config.ZcodeClientVersion` 由 **3.11.2 升至 3.14.3**（对齐本机实装客户端）。
  该常量是伪装版本的唯一来源，一处改动即覆盖全部 10 个上行点：
  `User-Agent: ZCode/<ver>`、`X-ZCode-App-Version`（upstream / quota / claim）、
  URL 参数 `app_version`（billing/preview、billing/balance、client/configs、oauth login）、
  以及事件体的 `app_version`。
- `PLAN.md` 的固定头示例改为 `<ver>` 并注明取自常量，避免文档与代码各写一份版本号。
- 新增两处回归护栏：
  - `internal/config/version_test.go`：UA 必须由常量拼接、版本号须为三段 semver、
    **静态扫描生产代码禁止出现三段版本字面量**（升级漏改会直接变红）。
  - `internal/claim/version_test.go`：哨兵值法——把常量换成哨兵后，
    事件体 / `authHeaders` / `claimHeaders` / `preview` query 四处必须全部跟随。

## 为什么本次只动版本号

把变量收敛到 1 个，便于归因：本次本质是**验证性升级**。

- 若 preview 恢复投放 → 说明上游按 `app_version` 判定投放资格，问题定案。
- 若仍为空 → 说明与版本无关，下一版转入第二项差异：给 `PostActivationEvent` 补齐那 11 个
  伪装上报头（当前它只带 `Content-Type`，是整条链路上最不像官方客户端的一环）。

## 上线验证

**结果（2026-09-23）：有效** —— 只升版本号即恢复投放，preview 返回套餐、claim 成功。
据此，下文「无效」分支里的补头方案与 `session_create` 一并降级为改进项，不再是阻塞项。

升级后任取一个 JWT 账号走一次领取（入池自动领取或后台手动触发）：

- **有效**：claim 日志出现 preview 含套餐并领取成功；`/billing/preview` 的 `data.plans` 非空。
- **无效**：仍报「沒有待領取的套餐」→ 按上文进入补头方案。

注意：若部署侧自行设置过 `ZCODE_CLIENT_VERSION` 环境变量，本次默认值调整不生效，
需同步该变量取值。
