# v2.14.2-go

让 socks4 代理真正可用：握手从「一律 SOCKS4a」改为**本地解析优先、解析不到 IPv4 才回落 4a**。
本版不改变上游身份、模型路由、领取与核销契约。

## 背景

网关对 socks4 的支持一直是全链路的（校验、手写拨号、`DialTunnel`、订阅入库 `Canonical`、
入库复检探针），但生产一条都没进池，原因有两层：

1. 订阅地址带 `exclude_socks4=1`，源头被过滤；
2. 更关键的是**协议语义错配**：本项目对域名目标一律发 SOCKS4a（把域名交给代理解析），
   而 proxy-checker 用 curl 的 `socks4://` 判定可用性——libcurl 对 `socks4` 是本地解析后
   按标准 SOCKS4 连 IP。

2026-11-14 在服务器上用同一批 33 条 socks4 线路做完整 HTTPS GET
（`https://zcode.z.ai/api/v1/client/configs`，10s 超时）：

| 语义 | 成功(200) |
| --- | --- |
| `curl --socks4`（本地解析 = checker 口径） | 22 / 33 |
| `curl --socks4a`（远端解析 = 本版之前的口径） | 2 / 33 |

即：只删订阅参数是白改——入库复检探针走的也是同一份拨号器，会把这 22 条全部判死。
22 条里 `up_kbps>=85` 有 20 条、再排除 `ip_shared` 剩 16 条，上行读数 721–9469 KB/s，
高于现有订阅线路（约 850–1200 KB/s）。

## 改动

- `internal/proxy/client.go`：`socks4Handshake` 增加 `ctx`，域名目标先按握手预算本地解析
  取 IPv4 再发标准 SOCKS4；解析不到 IPv4 或解析失败才回落 SOCKS4a；IPv6 字面量目标直接报错
  （此前会发出装不下的畸形 4a 请求）。解析走新增的 `lookupIPv4` 接缝，测试可替换。
- `internal/proxy/socks4_test.go`：三例回归——本地解析发出 IPv4 而非 4a 标志、无 IPv4 时
  回落 4a 且报文尾部是 `域名+NUL`、IPv6 目标早失败；`timeout_test.go` 跟随签名。
- `internal/adminapi/proxies.go`：删掉「socks4 无标准库支持直接报错」的过时注释。
- 前端：`proxyScheme` 区分 SOCKS4/SOCKS5（此前一律显示 SOCKS5），代理页补 S4 示例与占位文案。

## 升级与回退

- 无需数据库迁移，接口、配置项与数据结构不变；socks5/socks5h/http/https 行为逐字不变。
- 回退到 `2.14.1-go` 即可恢复「只发 4a」的旧行为。
- 部署后建议先验证再放量：

```bash
docker run --rm -v /opt/1panel/apps/local/zcode2api/data:/data:ro -e ZCODE_DATA_DIR=/data \
  ghcr.io/fujunchao/zcode2api-plus:2.14.2-go probe --dry-run
# 期望 client_version=3.18.2、profile=3.18.0、blocks=3
```

## 生产侧配套（本次发版后执行）

1. 订阅地址去掉 `exclude_socks4=1`（保留 `exclude_shared_ip=1&up_min=85`），先 preview 再 import；
2. 挑 1–2 条 socks4 做后台「检测」，再按需绑 1 个账号验证真实对话与领取；
3. 免费线路寿命短，建议配合 `stable=1`（`pass_streak>=2`）收紧来源。

二进制：Linux amd64/arm64、macOS amd64/arm64、Windows amd64。
镜像：`ghcr.io/fujunchao/zcode2api-plus:2.14.2-go` 与 `latest`。
