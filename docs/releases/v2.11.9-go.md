# v2.11.9-go

## 修复：保留客户端 system 的判定过宽，导致切到 3.17.1 后 3012

### 现场

升到 `v2.11.8-go`（默认 3.17.1）后，部分请求 405 / `code=3012 unusual activity`。
出站诊断行显示：

```text
system_source=input system_form=blocks system_blocks=3
system_text_bytes=[35,3065,3810]
official_prefix_match=true official_identity_match=false
```

即：调用者自带 system，**首段命中官方前缀**，但**身份段与本版本档案不一致**，网关仍原样转发。

### 根因

`ShouldPreserveCallerSystem` 在块形态下只比对「块 0 是否以官方前缀开头」，没有校验身份段。
而 3.16.x 与 3.17.1 的块 0 只差几个字：

- 3.16.x：`You are ZCode, an interactive coding agent`（42 字节）
- 3.17.1：`You are ZCode, an interactive agent`（35 字节）

于是同一个下游客户端的 system：

- 默认 3.16.3 时块 0 对不上 → 网关**重建** canonical → 200；
- 默认 3.17.1 时块 0 恰好撞上 → 网关**原样转发**身份段不匹配的 system → 3012。

### 修复

块形态的保留判据改为「**首段 + 身份段逐字节一致**」（`callerBlocksMatchOfficial`）：

- 一致：原样保留（调用者追加的 Environment/currentDate 等块不受影响）；
- 不一致：走既有 fallback —— 重建当前档案的两块 canonical，调用者原文并入 dynamic 块，
  一个字节都不丢。

### 回归测试

- `internal/upstream/preserve_test.go`：前缀对但身份段不同 → 不保留；身份段一致 → 保留；
  官方两块 + 调用者追加块 → 保留。
- `internal/gateway/preserve_rebuild_test.go`：身份段不匹配时重建为本版本档案，
  且调用者原文保留在 dynamic 块；身份段一致时原样保留。

### 升级与回退

- 默认仍是 `3.17.1`；升级后请先用一条真实请求验证，确认日志里
  `official_identity_match` 为 `true` 或 `system_source` 不再是 `input`。
- 如仍有异常：`ZCODE_CLIENT_VERSION=3.16.3` + 重启即可回退，无需换镜像。
