# v2.11.3-go

## Start Plan system 对齐 + 验证码热路径

本版合入 M1/P0-A 与 M2/P0-B 两个已完成里程碑。自 v2.11.2-go 以来没有数据库结构变更；
M1 只影响网关自行补 system 的路径，M2 只影响 JWT 验证码获取与配置缓存。

### 1）Start Plan system 组装对齐

- 网关自行补 system 时固定为三块：
  - block 0：CLI Prefix，**不再带 `cache_control`**；
  - block 1：stable（含现有 2313B Desktop Context），保留 `ephemeral`；
  - block 2：`# Communicating with the user` + 运行时 `# Environment` +
    `# Context management`，保留 `ephemeral`。
- 调用者自带官方三块 system 时原样保留，不重复注入；第三方 system 合并进 block 2，
  不再出现第 4 个 `# Gateway Desktop Capabilities` 块。
- 首条 user 消息合并 `currentDate` system-reminder（string 转两个 text block，数组前置
  一个 block）；已有 `# currentDate` 时跳过，不新增独立 user 消息。

### 2）验证码 token 池

- `internal/captcha` 新增预求解 token 池：
  - 按 `sceneId|region|prefix` 分桶；token 一次性，取走即删除，TTL 默认 95s；
  - 后台 refill（默认 min=2 / max=6、1s 节拍）；池空最多 2 路并发 solve 竞速，
    多余成功结果回填池子；
  - 同一 `certifyId`（解析不出时按 token 摘要）只允许 mint 一次，避免并发重复；
  - 配置键变化自动清空旧桶；`Manager.Close` 停止 refill 与在途 mint。
- 配置缓存默认由 10 分钟改为 **1 小时**（`CAPTCHA_CONFIG_CACHE_TTL` 可覆盖）；
  成功才写、失败保留 last-good 且 30s 退避，不再因配置接口短暂故障误开/误停验证码。
- 拿不到 token 仍返回 503 `captcha_required`，绝不裸发；3007/响应头/F001 挑战重试
  逻辑未改。
- 新增 CPU governor：Linux 读 `/proc/stat`，其他平台用标准库 `runtime/metrics`
  进程 CPU 时间折算；高负载降低 refill 并发与池目标；空闲 120s 缩到 1 条、
  900s 停补（保留 1 条唤醒）。
- 指标：`/admin/api/monitor` 新增 `captcha` 对象（`pool_size`、`take_total`、
  `empty_take_total`、`mint_total`、`mint_fail_total`、`wait_p50_ms`、`wait_p95_ms`）；
  请求 `[#]` 诊断行尾部增加 `captcha_wait_ms / captcha_pool_size / captcha_empty_take /
  captcha_mint_fail`，不打印 token。

## 配置

| 变量 | 默认 | 说明 |
|---|---|---|
| `ZCODE_CAPTCHA_POOL_ENABLED` | `true` | JWT 验证码预求解池；false 退回逐请求求解 |
| `ZCODE_CAPTCHA_POOL_TTL_MS` | `95000` | 池内 token TTL（毫秒） |
| `ZCODE_CAPTCHA_POOL_MIN` / `MAX` | `2` / `6` | refill 目标水位与上限 |
| `ZCODE_CAPTCHA_POOL_EMPTY_SOLVE` | `2` | 池空并发 solve 路数（1–2） |
| `CAPTCHA_CONFIG_CACHE_TTL` | `3600000` | 上游验证码配置缓存（毫秒） |
| `ZCODE_CAPTCHA_CPU_GOVERNOR` | `true` | 按 CPU 占用缩放 refill |
| `ZCODE_CAPTCHA_BROWSER_WORKERS` | 代码默认 `1`；compose 默认 `2` | Chromium worker 数 |

Docker 部署建议：至少 **2 CPU / 2 GB 内存**，每个额外 Chromium worker 再预留
0.5–1 GB；`docker-compose.yml` 已给出 `deploy.resources.limits` 注释示例。

## 升级与回滚

- 无数据库迁移；`/data` 与账号库结构不变。
- 验证码回滚：
  - `ZCODE_CAPTCHA_POOL_ENABLED=false`：关闭 token 池，回到逐请求求解；
  - `CAPTCHA_CONFIG_CACHE_TTL=600000`：配置缓存回到 10 分钟；
  - `ZCODE_CAPTCHA_BROWSER_WORKERS=1`：降低 Chromium 并发与内存占用。
- system 组装未实现单独的 `ZCODE_SYSTEM_PROFILE` 开关；如需回滚请回退镜像/版本。
- 首次上线后观察 `captcha.wait_p95_ms`、`empty_take_total`、`mint_fail_total` 与
  Docker CPU/内存；staging 再补池热 p95 <200ms 与 24h soak 记录。

## 回归覆盖

- captcha：池热一次性、空池 2 路竞速、并发唯一 token、TTL、配置切换清池、
  重复 certifyId、`Manager.Close`、空闲缩容/停补、CPU governor、last-good 与 env 覆盖。
- gateway/async：池空失败 503 且上游零调用、并发 JWT 唯一 token、诊断字段顺序。
- upstream：三块 system 结构、block cache 布局、dynamic 标题、currentDate 不重复、
  官方 system 原样保留。
- 完整 `ci.yml`：`go test ./...`、`-race`、分组重复回归、frontend、SDK/NewAPI 兼容、
  Windows 代理日志、交叉编译与 Docker 构建；发布工作流复用同一套 CI。
