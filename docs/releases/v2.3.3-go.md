# v2.3.3-go

一次很小的补丁，起因是准备做「300s 墙归属」实验时发现：**v2.3.2 引入的诊断行里，async 的出口字段
会给出与实际不符的线路名**——那个实验正是靠读 `route` 判定的，读反即结论反。

本次不发功能、不改请求处理逻辑、不改任何账号状态机。

## 一、修正 `route`：async 恒直连

`internal/asyncpool` **从不套用 `acc.ProxyURL`**：`p.client()` 构造的是只设了
`ResponseHeaderTimeout` 的裸 `http.Transport`，其 `Proxy` 为 nil ⇒ 既不走账号线路，
**也不吃环境代理**（已实测；零值 `http.Client` 才会吃环境代理）。

而 v2.3.2 的 async 诊断行沿用了 sync 的 `Store.ProxyLabel(acc)`，于是「账号绑了线路」时
会打出一条**本次并未使用**的线路名。现在 async 硬编码 `route=direct`。

守卫用例 `TestAsyncDiagRouteIgnoresAccountProxyLine`：账号已绑定线路，仍须报 `direct`、
且日志中不得出现该线路名。（将来若给 async 补上线路支持，这条用例会红——那时应连同
`PLAN.md` §5.6 的出口说明一起改，而不是放宽断言。）

**为什么值得单发一版**：`route` 是判定「墙在出口线路还是在上游模型侧」的唯一读数。
sync 走线路、async 直连，这组对照是缺失的那个 2×2 里最便宜的一半：
async 撑过 300s ⇒ 线路侧；async 同样在 ~300s 断且 `maxgap` 很小 ⇒ 上游侧。

## 二、async 池的三个开关进了 docker-compose

`ZCODE_ASYNC_ENABLED` / `ZCODE_ASYNC_TICKET_TIMEOUT` / `ZCODE_ASYNC_MAX_RETRIES` 此前**没有**在
`docker-compose.yml` 的 `environment:` 里被引用，而应用只认进程环境变量（compose 不会自动透传
`.env` 里的键）⇒ 想调也调不到。现已补上，默认值与代码默认一致，行为不变。

⚠️ 顺带提醒 `ZCODE_ASYNC_TICKET_TIMEOUT` 的真实语义：它是**整票的墙钟寿命**
（`deadline = createdAt + timeout`），**不是空闲超时**。到点即向客户端投递
`type: ticket_timeout` 的错误事件并中止后台任务。sync `/v1/messages` 没有总超时，
但 **async 上的长思考请求若不调高它，必然被截断**——那是设计使然，不是上游故障。

## 三、记录一个移植缺口（本次未修）

Python 版建 async 客户端时是收 account 参数的（隐含按账号生成带代理的 client），Go 版把该参数
丢掉了，于是 async 失去了线路支持。影响有两条：

1. 诊断行只能报 `direct`（见上）；
2. 若部署环境必须经线路才能连上上游，async 会整条不可用。

**未修**，因为它会改变已发布行为，且当前「恒直连」正好充当上面的归因实验的直连臂。
缺口已记入 `PLAN.md` §5.6，待单独决策。

## 兼容性与升级

- 直接替换二进制；**无数据迁移、无接口变更**；
- 唯一的配置面变化：compose 新增三个 async 变量，默认值与原先一致，不设也不影响行为；
- 未改前端，`frontend/dist` 无需重建；
- 日志形态不变（`[#]` 诊断行字段集不变，仅 `route` 的取值对 async 更如实）。

## 已知未决

300s 墙的**归属**（出口线路 vs 上游模型侧）仍未定论——v2.3.2 提供判定手段，本版修正了其中一处
会误导判读的读数，真正的结论仍待一次真机长流验证。判定矩阵见
`docs/analysis-flash-5min-stream-cut-20260921.md` §4.1。
