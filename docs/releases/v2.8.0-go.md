# v2.8.0-go

账号池批量管理：批量新增、批量删除、批量启用/禁用与列表条件查询四个能力，
批量写操作具备事务一致性（整批原子提交）与逐条成败明细。
基线上游 2.0.7 不变；伪装客户端版本仍为 3.14.3。

## 新端点（全部为新增路由，旧端点零改动）

| 端点 | 用途 |
|---|---|
| `POST /admin/api/accounts/batch/add` | 批量新增：`items` ≤500 条（name/secret/email）；判重沿用 user_id → email → 凭据三轮语义，重复项返回既有记录（幂等，不算失败）；`proxy_id` 三态语义与单轮新增一致 |
| `POST /admin/api/accounts/batch/delete` | 批量删除：严格模式（默认）任一 ID 缺失整批拒绝、一个不删；`missing_ok=true` 跳过缺失项并逐条标注 |
| `POST /admin/api/accounts/batch/enable` | 批量启用：转移语义与单账号端点共用同一函数（disabled → active，不越权改写 invalid/归档状态） |
| `POST /admin/api/accounts/batch/disable` | 批量禁用：`Enabled=false` + `Status=disabled` |

### 条件查询（GET /admin/api/accounts，additive 扩展）

新增过滤与分页参数：`keyword`（name/email/id/user_id 子串）、`status`（逗号分隔
白名单）、`enabled`、`mode`、`model` + `model_status`（例如筛「glm-5.3-flash 已耗尽」
的账号）、`proxy_id`（`__direct__` = 未指派任何线路）、`archived`（all/false/true）、
`last_error_kind`、`created_after` / `created_before`（unix 秒）、`sort`、`limit` /
`offset`。

- **不传任何参数时行为与旧版完全一致**（全量、`created_at` 升序）；
- 响应追加 `total` / `offset` / `limit` 三键；`stats` 概览保持全量口径，不受过滤影响；
- `limit` 不传 = 不分页（保持旧量行为），传则 1–500；
- 非法参数一律 400（不做宽容解析——静默忽略会让管理员拿到一个他不知道被窄化过的列表）。

## 事务一致性

批量写操作在**单锁 + 单 SQLite 事务**内完成：预校验（零副作用）→ 事务内逐条落库 →
commit 成功后才应用内存变更。任一条持久化失败整批回滚、内存零改动；进程在
commit 与内存应用之间崩溃也安全——内存态启动时自 DB 载入，DB 是真相源。

批量上限 500 条/次；启用/禁用的字段转移与单账号 `SetEnabled` 共用 `applyEnabled`，
两个入口语义结构性一致、永不漂移。

## 统一响应形态

```json
{
  "total": 3, "succeeded": 2, "duplicated": 1, "not_found": 0, "failed": 0,
  "ids": ["…"],
  "items": [{"index": 0, "id": "…", "name": "…", "status": "ok", "message": ""}]
}
```

`items[].status` 取值 `ok` / `duplicate`（仅新增）/ `not_found`（删除、启停）/ `error`。
校验失败（凭据为空/超长、条目超上限）与严格模式缺失为 400 并附全部坏项明细；
持久化失败为 500（此时零改动）。空数组序列化为 `[]` 而非 `null`。

每次批量操作在日志记一条 `batch` 汇总（总数/成功/重复/缺失/失败/耗时）；
逐条明细只进响应体不进日志，避免刷屏。

## 兼容性

- 不新增 Account 持久化字段，`accounts.data` 的 JSON 键集契约（与 Python 版互读）不变；
- 旧端点（`POST /admin/api/accounts`、`DELETE /admin/api/accounts`、
  `POST /admin/api/accounts/{id}/enabled` 等）行为零改动；
- 收尾链路（线路自动分配 → JWT 额度刷新 → 入池自动领取）与单轮新增共用同一实现。

## 上线验证

1. 批量新增混入重复凭据：响应应逐条标注 `ok/duplicate`，池内只落新建账号，
   新账号各自持有独立设备指纹；
2. 严格删除混入不存在 ID：应 400 且一个都不删；`missing_ok=true` 时才删存在项；
3. `GET /admin/api/accounts?status=disabled` 与
   `?model=glm-5.3-flash&model_status=exhausted` 应返回正确子集，
   `stats.total` 仍为全量口径；
4. 无参数 `GET /admin/api/accounts` 与升级前一致（除新增 total/offset/limit 三键）；
5. 非法过滤参数（如 `status=nope`、`limit=501`）应 400。
