# v2.10.17-go

## 请求级总预算：最坏等待从 450 秒压到 240 秒

v2.10.16 给单次尝试加了 90 秒首字节预算，但**换号重试会各拿一份预算**：
`MaxAccountAttempts=5`，最坏是 5×90s=450 秒。慢线路上 5.5MB 请求仍可能转圈 7 分半。

本版给整次请求加墙钟总预算（默认 240 秒），并让首字节预算按剩余时间收紧：

- **只判「还能不能再试一次」**：判定点在每轮选号之前与每次出站之前，**不派生 ctx**。
  已经开始的流式交付必须能跑完——掐断长回答比慢更糟。
- **首字节预算取 `min(90s, 剩余)`**：最后一次尝试不会又白等满 90 秒。
- **预算命中不惩罚账号**：返回 `503 request_deadline_exceeded`，`error.details` 带
  `attempts` 与 `deadline_seconds`；账号不冷却、不记失败、不进 `last_error`。
  与 `no_available_account` 刻意分开——池子里可能仍有号，失败原因是「等太久」。
- 诊断行追加 `deadline_hit=1`，可与 `attempts=`、`firstbyte=` 对照判断是「哪一段慢」。

240 秒的依据：实测正常大包首字节 30–65 秒（5.41MB→30.5s、5.42MB→63.6s、5.58MB→42.3s），
两次尝试（首次 + 一次换线）约 130 秒，留一倍余量。

## 配置

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `ZCODE_REQUEST_DEADLINE_SECONDS` | `240` | 单次请求墙钟总预算；`0` = 关闭，回到 v2.10.16 行为 |

与 `ZCODE_UPSTREAM_FIRST_BYTE_TIMEOUT` 独立：把首字节预算设为 0 的部署不会被总预算
悄悄打开看门狗（只在首字节预算 > 0 时才收紧）。

## 兼容性

- 无数据迁移、无接口变更；管理 API 与前端 UI 未改。
- 默认开启后，单次请求最多尝试的账号数不变（5），只是不再允许「每次都等满 90 秒」。
- 返回新错误类型 `request_deadline_exceeded`（HTTP 503）。按 `type` 分支的调用方
  需要知道它不同于 `no_available_account`：前者可以原样重试，后者要等账号恢复。

## 回归覆盖

预算用尽停在第二次尝试前（且账号未冷却）、预算关闭后行为与 v2.10.16 完全一致、
首字节预算被剩余预算收紧、响应头已返回的长交付不被总预算切断。

所有自动化验证由 GitHub Actions 执行，分支 CI 与发布工作流复用的完整 CI 均为门禁。
