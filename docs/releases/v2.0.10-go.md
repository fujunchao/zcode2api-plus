# v2.0.10-go

代理检测不再只看出口 IP：现在同时探测 z.ai 侧入口是否可达，
把「线路活着」与「线路能用」这两件事分开呈现。

## 新增内容

- **z.ai 侧入口可达性探测**：除原有的出口 IP / ASN 查询外，再经同一条
  线路对上游真实入口（`zcode.z.ai`、`api.z.ai`）发一个无凭据请求。
  判据是**能否拿到 HTTP 响应**，而不是状态码是否 200——无凭据请求本就
  该被 401/403 拒，拿到状态码恰恰证明已经到达 z.ai 的边缘。
- **两路并发、结果合并**：出口查询与 z.ai 探测互不依赖，故并发执行。
  单条最坏耗时仍是出口侧的 36 秒，不随探测目标数叠加；三个入口
  （单条测试、測試目前線路、測試全部線路）拿到的字段完全一致。
- **三态判定**：`ok` 表示至少一个入口拿到了非拦截响应；`blocked`
  表示没有可用入口、但响应像 CDN/WAF 拦截页（`Cf-Mitigated` 头、
  拦截页特征串、403 + cloudflare）；`error` 表示全部拿不到响应。
  逐目标的 `status` 与 `blocked` 也一并返回，可区分「主站被拦、
  备援站仍通」这类半可用状态。
- **后台新增琥珀色状态**：出口查得到、但 z.ai 不通的线路不再显示为
  绿色，而是琥珀色并写明「z.ai 不可達／被邊緣攔截」。

## 修复内容

- **「探测成功」被误当成「线路可用」**：批量检测的汇总此前按「探测请求
  成功」计数，于是连不上 z.ai 的线路也会算作正常。现在 `ok` 与汇总都改
  按「线路可用」判定，这类线路计入失败数；前端文案相应改为
  「可用 X／有問題 Y」。
- **探测 UA 可能与生产不一致**：z.ai 侧探测改用生产同款 UA。用自造的
  探测 UA 去打 z.ai 可能被 WAF 直接拦掉，那会把「线路通」误报成
  「线路不通」——等于自己制造假阴性。
- **出口字段改为可选**：当出口查询站被线路的域名白名单挡住、而 z.ai
  仍可达时，返回体里不再保证有 `ip`；前端按「已取得回應 + z.ai 可達」
  展示，不再把这种情况当成失败。

## 使用说明

代理页的三种测试（单条、目前线路、全部线路）现在都会同时给出出口信息
与 z.ai 可达性，无需任何配置：绿色为可用，琥珀色为「线路通但 z.ai
不可达」，红色为线路本身不通。

耗时不变：批量检测按并发 8 路探测，单条最坏约 36 秒（出口查询三个服务
依次 12 秒超时；z.ai 侧并发跑，单目标 6 秒），全量约为
`36s × ⌈N/8⌉`。测试期间按钮禁用。

仍然测不到的三件事：代理是否缓冲 SSE 长流（本项目 `unexpected EOF` 那
一族故障的成因）、请求体大小上限、以及账号级的 429/403——它们都需要带
凭据的真实请求，本次没有为此引入副作用。

[客户端兼容说明](https://github.com/fujunchao/zcode2api-plus/blob/v2.0.10-go/docs/client-compatibility.md)

## Docker

```bash
docker pull ghcr.io/fujunchao/zcode2api-plus:2.0.10-go
```

支持 linux/amd64 和 linux/arm64，同时更新 latest。现有数据卷与非
root 运行方式不变。

## 能力依据

- [Z.AI 官方文档](https://docs.z.ai/)

探测只读取 HTTP 状态码与响应头，不发送任何凭据，也不改变本地代理配置
或账号状态；检测结果不落库，仅用于后台展示。

新增探测已通过单元测试与本地全量测试（三个新用例分别覆盖「可达」、
「被边缘拦截」、「完全不通」；桩服务器同时冒充出口服务、代理与上游
入口，整条链路不触网），但**尚未经过线上真实代理环境验证**：真实线路
被 z.ai 接受的程度、以及琥珀色判定在实际网络下的误报率，仍待在线观察。
