# v2.5.1-go

一次**领取链路修复版**。

## 问题

服务端新账号入池后自动领取体验套餐全部失败：`billing/preview` 恒返回 `code=0` + **空 plans**
（一批新账号无一例外，手动强制领取同样失败），激活事件却全部"成功"。本地真实 ZCode 客户端
登录同批账号可以正常领取——账号本身有资格。

## 根因

激活遥测（`app_launch` / `app_daily_active` 上报 `event/report`）用的是**独立的裸直连客户端**
（`telemetry.eventClient`，只认容器级 `HTTP_PROXY` 环境变量），**不走账号绑定的代理线路**；
而 preview/claim 走 `clientFor(acc)` 的账号线路。于是同一个 `device_mid`、同一个账号，在
`event/report` 与 `billing/preview` 两个端点上**来自两个不同的 IP**。真实桌面客户端这两者
永远同 IP；活动投放资格疑似做这类出口一致性比对，资格信号因此被掐断——正是日志里
「激活全部成功、preview 恒空」的形态。

这是移植 Python 版时的遗漏（§5.9 当年只约定了 claim 计费请求走账号代理，telemetry 一节
没提出站，照抄成了裸客户端）。

## 修复

- 删除包级 `eventClient`；`PostActivationEvent` 首参改为接收客户端。
- `ReportActivationEvents` 改为 `*Service` 方法，经 `s.clientFor(acc)` 出站：**有线路走线路、
  线路无效回退直连并记日志、无线路直连**——与 billing 请求完全同一出口决策。
- 调用点三处对齐：`AutoClaimAllPlans`（入池自动领取）、后台「刷新资格」（handleClaimPreview）、
  手动领取（handleClaim）。
- 回归：`TestActivationEventsUseAccountEgress`（注入假计费客户端，断言两个激活事件**先于**
  preview 经过同一个客户端）；`TestActivationReportingTolerated` 改走零值 Service 的直连分支。

## 上线验证

升级后在服务端入池一个新账号：claim 日志应出现 preview 含套餐并自动领取成功。
若 preview 仍为空——说明上游对机房 IP（线路/服务器出口）一并不投放，此修复无法救，
届时改走「真实客户端完成首次领取后导入服务端」的流程（领取状态与额度跟账号走）。
