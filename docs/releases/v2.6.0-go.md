# v2.6.0-go

一次**行为变更版**：把上游风控的「账号级」与「请求级」两种语义分开处置。

## 背景

2026-09-24 上午，`GLM-5.3` 整池 70 个账号在 2 分钟内被清空，全模型不可用约 5 分钟。

复盘（`docs/analysis-riskcontrol-pool-cascade-20260924.md`）结论：**不是「大量账号被上游风控」，
而是「一个请求被上游风控，网关把它放大成了 67 个账号的冷却」**。

```
一个 278,081B 的请求  →  上游 405 + 风控文案  →  网关按「账号级」结算并换号
                                              →  调用方原样重放 14 次
                                              →  67 个账号 × 300s 冷却
```

关键证据：

| 证据 | 内容 |
|---|---|
| 跨身份复现 | 同一请求体（字节数完全一致）在 **67 个不同账号 + 约 50 条不同出口线路**上全部被拒 |
| 同账号对照 | 某一账号在事发前 9 秒刚用 252,609B 的请求体成功出流量，换成 278,081B 即被拒 |
| 历史对照 | 2026-09-23 全天 17 次零星风控，**17/17 换号即 200**——账号级风控真实存在且换号有效 |
| 排除项 | body 尺寸不是触发条件：成功请求 max 687KB，`≥270KB` 成功 283 条 |

## 本次改动

### 判据（唯一一条）

> 风控是身份维度的信号。同一请求体在 **≥2 个不同账号（且出口线路不同）**上被同一个风控
> 信号拒绝时，身份已不是变量，剩下的只有请求体。

阈值取 2 的依据就是上表的历史对照：账号级风控在第 2 个账号上就已经成功了。

### 改动清单

| 位置 | 内容 |
|---|---|
| `gateway/riskscope.go`（新增） | `RiskScope` 请求级判定范围 + `RiskControlSnapshot` 前像/后像 + `RollbackRiskControl` 回滚 |
| `gateway/classify.go` | `MarkRiskControl` 改为 `MarkRiskControlWithSnapshot` 的薄包装（两者共用同一段锁内逻辑） |
| `gateway/engine.go` | 分类链第 8 条按判定分流：请求级 → 不冷却、不换号、回滚本请求已施加的风控冷却、原样返回上游 405 |
| `asyncpool/pool.go` | 与 sync 同判定：新增 `errRequestLevelRisk`，命中后终止本票而非换号；两条路径共用同一份阈值与 `Mark*` |
| 两处 405 日志 | 补上 HTTP 状态码与**上游 body 预览**（此前只有账号名与秒数） |

### 刻意不改的三件事

- **账号级风控的处置完全不变**（冷却 300/900/3600 递进、超档置 invalid）：换号能解决的那一类，
  继续用换号解决。
- **回滚只回滚风控分支施加的冷却**：本请求内因 503/429 冷却的账号与这次 405 无关。
- **回滚保留 `last_error_kind=risk_control` 这条证据**：判定的是「不该惩罚账号」，不是
  「这次拦截没发生过」；且该字段只在 `Status==invalid` 时才被额度守卫读取，留痕无害。

## 回归护栏

| 用例 | 守什么 |
|---|---|
| `Test405RequestLevelRiskDoesNotCoolPool` | 3 账号同 body → 全 active、阶梯为 0、上游调用停在 2 次、响应为上游原文 |
| `Test405AccountLevelRiskStillCoolsAndSwitches` | **阈值 2 不误伤**：只有 1 个账号被拒时仍按账号级冷却 |
| `Test405RiskControlCoolsAndSwitches`（既有） | 单账号池行为逐字不变 |
| `Test405WithoutRiskBodyDoesNotCool`（既有） | 非风控 405 仍原样透传、不冷却 |
| `Test405RequestLevelRiskInAsyncPool` | async 同判定（第 3 个账号未被试） |
| `TestRollbackRiskControl{RestoresSchedulingFields,SkipsWhenStateChanged,SkipsInvalidUpgrade}` | 回滚的三道边界：正常复原 / 并发改动即放弃 / invalid 不复活 |
| `Test405RiskControlLogCarriesUpstreamBody` | 日志必须带上游 body 预览 |

**反向验证**（回退实现必须变红，否则测试没在守行为）：

1. 阈值置 1 → 两个包的上游调用数断言立即变红（判定退化为「第 1 个账号即请求级」）；
2. `RollbackRiskControl` 改空操作 → 两个包的「不该冷却账号」断言立即变红。

## 影响与兼容

- **接口无变化**：请求 / 响应格式、错误类型、`[#]` 诊断行字段全部不变。
- **日志有一处新增**：405 风控命中行与新增的「风控判定為請求級」行都改成携带上游 body 预览。
  这是**日志内容变化**，按 `[~]` 行做严格匹配的外部脚本需同步；选 `[~]` 而非 `[#]` 正是为了
  不碰被字段级解析的诊断行。
- **线上紧急回退开关**：`gateway.RiskControlRequestLevelThreshold = 1` 即退回逐号冷却的旧行为
  （默认 2）。本版未做后台可配置项（留待有第二个旋钮时一并做）。

## 上线验证

1. 观察 `[~]` 行：账号级风控应仍按 300/900/3600 递进出现（对照组不能消失）；
2. 触发一次请求级风控后，确认出现「风控判定為請求級…回滾 N」且后台对应账号状态未被改动；
3. 24 小时曲线：风控冷却账号数与 `no_available_account` 数量应回到 09-23 的量级
   （全天 ≤20 次风控、无整池事件）。

## 未纳入本版

- **P1 重放防护**：同 payload 短时重放的快速失败（本版已把单次重放的账号代价降为 0，
  但仍会产生一次上游调用）；
- **P2 后台可配置阈值**：需要新增一个设定项（config / store / adminapi / 前端 共 6 处）。
