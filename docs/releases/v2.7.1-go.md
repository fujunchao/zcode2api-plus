# v2.7.1-go

风控两段式模型落地（P1-3 重放防护 + 请求级处置修正）与调用格式第三批对齐。
基线上游 2.0.7 不变；伪装客户端版本仍为 3.14.3。

## 风控：阻止账号标记扩散（核心变更）

上游 405 风控确认为两段式：**内容特征触发 + 账号服务端标记**（标记期内该账号无论发什么都
405，实测持续 ≥14h）。据此修正两个机制：

### 重放防护（P1-3）

同一份请求内容（模型 + body 指纹）被判定「请求级风控」后，60s 窗口内同内容请求**直接快速
失败**（503 `risk_control_cooldown`），不再消耗任何账号。

- 背景：09-24 凌晨一个特征 body 借助换号重试与调用方重放，2 分钟内冷却 67 个账号、整池清空；
  每一次「换号再试」都在把新的健康账号送给上游标记。
- 表跨请求/跨票共享；窗口 `ZCODE_REPLAY_GUARD_TTL_SECONDS` 可调（默认 60，0 = 禁用，应急回退）。
- 快速失败不计失败、不冷却任何账号，`[#]` 诊断行照常输出。

### 请求级风控处置修正：冷却保留

旧语义「请求级 ⇒ 不冷却账号、回滚已施加的冷却」在标记模型下方向相反——每个被尝试的账号
都已被上游标记，回滚本地冷却等于替服务端解封，账号会立即被再次选中再吃一个 405。

- 请求级判定成立时：停止换号（不变）、**保留全部已施加的风控冷却**、判定账号本身也施加
  冷却（它同样吃了 405）、登记重放防护；
- 删除回滚机制（`RiskScope.Rollback` / 快照三字段还原）；
- 账号级分支行为不变：300/900/3600 阶梯递进、超档置失效（对照组保留）；
- 阈值仍是「同一请求内 ≥2 个不同账号」（`RiskControlRequestLevelThreshold`，置 1 = 紧急回退）。

## 伪装格式：第三批对齐（依据官方 CLI 日志与 golden 抓包）

| 项 | 修复前 | 修复后 |
|---|---|---|
| 鉴权头 | JWT 只发 `Authorization`；APIKey 只发 `X-Api-Key` | 两种模式统一**双头同值**：`Authorization: Bearer <凭据>` + `X-Api-Key: <同一凭据>`（官方形态） |
| 重试时的 `x-request-id` | 同一轮次内所有账号尝试共享同一个 id | 每次**上游 HTTP 尝试**换新（官方语义：同一 queryId 的 4 次重试有 4 个 id）；session/trace/query 保持 —— 消除「同一请求 id 出现在多个账号上」的多账号同源指纹 |
| undici 传输层头 | 缺失 | 补齐恒带三项：`accept: */*`、`accept-language: *`、`sec-fetch-mode: cors`（客户端透传不得覆盖） |

刻意不改：`accept-encoding`（对齐需引入 brotli 解压并改流式链路，收益不成比）、HTTP/1.1 头名
大小写形态（h2 协商下 Go 自动与 undici 一致）、同账号重试次数（池化产品形态差异）。

## 与官方一致性的验证方式

- 静态：`ZCODE_BASE_URL` 记录型反代抓官方客户端 golden，与网关出站逐字段 diff
 （方法见 `docs/analysis-client-golden-diff-20260924.md`）；
- 本版新增端到端守卫：换号后 `x-request-id` 必须换新而轮次/会话标识保持；鉴权双头同值；
  undici 三头恒在；请求级判定后恰好 N 个账号保留冷却 + 同内容重放被拦截。

## 上线验证

1. 观察一次请求级风控事件：`[#]` 行 `riskscope=2` 之后，同内容请求应立即出现
   `risk_control_cooldown` 快速失败，且上游调用数不再增长；
2. 账号级风控仍按 300/900/3600 递进（对照组不能消失）；
3. 出站头抽检：`x-api-key` 与 `authorization` 同值出现、`accept`/`sec-fetch-mode` 在列；
4. 风控冷却账号数在事件后应截止在「参与判定的账号」范围内，不再整池扩散。
