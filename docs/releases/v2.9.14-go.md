# v2.9.14-go

收敛伪装客户端在**不同端点之间的格式差异**，并补齐一处激活遥测缺口。
不修改账号选择、重试预算或风控保护阈值；额度与领取的业务语义未变。

## 补齐第三个激活事件

领取前对 `event/report` 依次上报的事件由两个补为三个，与官方客户端一致：

- 新增 `app_login_success`，顺序为 `app_launch` → `app_daily_active` → `app_login_success`。
- 登录事件的 `event_region` 为 `app_profile`、`event_extra_detail` 为 `{"login_provider":"zai"}`；
  其余两个事件仍为 `app` 与空对象。事件体字段数仍为固定 16 个。
- 首个事件失败仍然中止整轮上报，且**不阻断**领取（与既有行为一致）。

## 非模型端点请求头齐平

额度与领取端点此前只带「版本 + 平台」两项来源头，缺另外六项。现在三处
（模型请求、额度、领取）共用同一份来源头集合：

- 新增 `config.ZcodeSourceHeaders()` 作为来源头的唯一产出处，额度与领取的
  `authHeaders` 以它为底，再补 `Content-Type` / `X-Device-Mid` / `Authorization`。
- 补齐 `X-Title` / `X-Release-Channel` / `X-Client-Language` / `X-Client-Timezone` /
  `X-Os-Category` / `X-Os-Version`。
- 非模型端点的 `User-Agent` 仍为裸串 `ZCode/<版本>`（模型端点带 ai-sdk 后缀），
  两种形态刻意分开并各有测试钉住。
- 仍**不发送** `X-ZCode-Agent`——该头只属于模型端点。

## 查询参数 `platform=` 统一

同一个查询参数原先按端点用了两种写法：验证码配置用 `windows-x86_64`，额度与领取用
`win32-x64`。上游对两者都接受，但「同一客户端对不同端点自称不同平台」本身就是破绽。

- 三处查询点统一走 `config.ZcodeQueryPlatform()`，取值 `windows-x86_64`。
- 请求头 `X-Platform` **不变**（仍 `win32-x64`）——官方这两处本就是两种格式。
- 新增 `ZCODE_QUERY_PLATFORM` 覆盖位：留空为默认，设成 `win32-x64` 可**免重编**回退。

## `# Environment` 段默认不再注入

上游服务端只从 system 的第 0 个字节逐字节校验到**身份段末尾**，之后的段落可有可无
（整段删掉照样返回 200；而改动身份段里任意一个字符即返回 `3012`）。据此，模型请求默认
只发送「固定前缀 + 身份段」两块。

- 新增 `ZCODE_UPSTREAM_INJECT_ENVIRONMENT`，默认 `false`；设为 `true` 恢复三段形态。
- 附带效果：`# Environment` 与请求头之间「平台互相矛盾」的可能随之消失——该段不再存在。
- ⚠️ 这是本版唯一**主动偏离官方实测形态**的改动：官方客户端确实发送该段，改后请求在
  **段数与长度结构**上与官方可区分。「上游仍返回 200」**不等于**「与官方不可区分」。
  出现 `405` / `3012` 迹象时，把该开关置 `true` 重启即可回退。

## 回归与发布门禁

- 新增：激活事件顺序与登录事件字段、来源头集合与不可变性、`platform=` 默认值与覆盖位、
  默认不注入 `# Environment`。
- 修订：块数相关断言改为按实际注入块数派生（不再写死 3），头体平台同源守卫显式打开注入
  开关（它守的是「该段存在时必须与头同源」）。
- 继续执行全量测试、竞态检测、SDK/Pi、前端、交叉编译与镜像验证；测试仅使用隔离目录、
  合成凭据和本地测试服务。
- 标签发布继续先复用完整 CI，再上传二进制和推送镜像；不绕过发布门禁。

## 升级

- 镜像：`ghcr.io/fujunchao/zcode2api-plus:2.9.14-go`，以及滚动标签 `latest`。
- 平台：linux/amd64、linux/arm64；二进制仍提供 Linux/macOS 双架构和 Windows amd64。
- 无数据库迁移、无新增必填环境变量；替换镜像/程序并重启即可。
- 两个新开关均可留空使用默认值；需要回退时才显式设置（见上）。

格式对齐的完整背景与阶段划分见
