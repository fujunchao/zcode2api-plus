# v2.1.2-go

一次针对**错误分类**的修复版本：把「拨号 / 响应头超时」从「客户端取消」的误判中摘出来，
让线路故障回到「冷却换号」的正确路径。对外接口、配置项、数据格式与 2.1.1-go
**完全一致**，升级只需重启。

## 修复内容

**拨号超时不再被误判为「请求已取消」**

Go 的 `net.Dialer` 把 `Timeout` 实现为 context deadline，传输层的响应头超时同样携带
`DeadlineExceeded` 错误值。此前的取消判据只看错误值，于是两类**线路/上游故障**——
「代理或上游 30 秒连不上」「上游 120 秒不回响应头」——都会被当成「客户端主动取消」：

- 账号不进入冷却，坏线路留在轮询池里反复被选中；
- 客户端收到的是 502「请求已取消」，与实际原因（线路不通）不符，误导排查；
- 每次命中都要白等完整的拨号超时（30 秒）才失败。

线上日志里这一误判出现了 13 次（同一代理线路失联后持续被轮询命中）。现在判据改为
「请求的 context 是否已经结束」：只有客户端真的断开（或客户端自己的 deadline 到期）
才算取消；拨号 / 响应头超时按「连接失败」处理——冷却该账号并换号重试。

**限流日志的「连续第 N 次」显示修正**

此前打印的是账号副本上的旧值，第一次冷却会显示成「连续第 0 次」；现在改为取写入
返回值（与异步路径的写法一致）。

## 行为变更

- 线路故障（代理不可达、上游不回响应头）时，网关会**冷却该账号并换号重试**，
  客户端可能因此直接拿到成功响应，而不是收到 502「请求已取消」。
- 除此之外没有对外可观察的变化：HTTP 接口、`accounts.data` 的 JSON 契约、导出格式、
  配置项与后台界面功能均不变。

## 验证情况

- 本机：全量测试 14 包（`-count=1`）全绿；gofmt 74 文件 0 不合规。
- 新增回归用例 `TestDialTimeoutCoolsAccountAndSwitches`：模拟携带 `DeadlineExceeded`
  的拨号超时，断言账号被冷却、换号后成功；既有的「客户端断开不冷却」用例继续通过。
- CI：`test`（含 `go test -race -count=1`）、`sdk-compat`、`cross-build`、`docker` 全绿。

**仍未覆盖的部分**（与上一版相同）：

- 本机没有 C 编译器，`-race` 结论全部来自 CI；
- 容器实跑与验证码浏览器路径仍无实机验证。
