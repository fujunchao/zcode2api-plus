# v2.13.2-go

修复 v2.13.1 的一个真实缺口：**new-api 会把 SSE `error` 帧按 `{type, message}` 重建**，v2.13.1 附加的 `error.code` 被整体丢弃，导致可重试语义在真实链路上没有生效。

- 实测（v2.13.1 部署后用演练通道经 new-api 回读）：上游发出
  `{"type":"error","error":{"type":"overloaded_error","code":"overloaded_error","message":"…"}}`，
  客户端拿到的却是 `{"type":"error","error":{"type":"overloaded_error","message":"上游流式响应中断（已转交客户端重试）: …"}}` —— `code` 没了。
- 修复：可重试语义改为**双通道**承载 —— 继续写 `error.type/code = overloaded_error`（直连时命中码表），
  同时在 `message` 前加 `[1312][` 前缀。ZCode 解析 provider 错误码的最后一步正是
  「从 message 取 `^\[(\d{4})\]` 前缀」（1312 → ProviderOverloaded / retryable=true），
  因此即使中间网关重建了帧、丢掉自定义字段，前缀仍能把「可重试」传给客户端。
- 演练通道同步可用于回归：`ZCODE_DRILL_KEY` 非空时，请求体 `metadata.zcode_drill = <key>`
  （或请求头 `X-Zcode-Drill`，直连时）即可让网关产出一段「3 个内容增量 + 断流终态」的 SSE。
  注意：**new-api 会丢弃自定义请求头**，经 new-api 验证时必须用请求体 metadata 触发。
- 其余行为与 v2.13.1 一致（终态策略、预缓冲换号、graceful/abort、熔断参数默认值 2/600s）。

| 變量 | 默認 | 說明 |
|------|------|------|
| `ZCODE_TRUNCATE_TERMINAL` | retryable | retryable / graceful / abort / legacy |
| `ZCODE_TRUNCATE_PREBUFFER_MS` | 12000 | 首个内容增量前的预缓冲预算；0=关闭 |
| `ZCODE_DRILL_KEY` | 空 | 演练通道密钥；空=关闭 |

无需数据库迁移；替换镜像并重启即可生效。v2.13.1 与 v2.13.2 的差异只在断流错误帧的 message 前缀，回滚到 v2.13.1 不会破坏协议。

二进制：Linux amd64/arm64、macOS amd64/arm64、Windows amd64。
镜像：`ghcr.io/fujunchao/zcode2api-plus:2.13.2-go` 与 `latest`。
