# v2.10.28-go

## 隧道吞吐探针（shadow）

浅探针只证明「能连」：对目标根路径发一次 6 秒 GET，能连但大包传不动的线路每次判健康。
2026-10-17 的 5.5MB 请求首字节 283 秒、10-18 的 8.7MB 请求三次 `connection_failed` 各 70 秒，
探针全程绿灯——它看不到「传不动」。

本版给巡检增加一次**隧道裸写**测量：建连后直接往连接里写 1MiB，按写了多少、用了多久判断上传能力。

为什么不能用 HTTP 请求测：`POST 1MB body` 到目标站点时，边缘读完 headers 就回 401/400，
Go 的 transport 会提前中止写入——测到的是对方的拒绝速度，不是链路带宽。必须走裸隧道。

### 判据（对端早关 ≠ 链路慢）

1. 预算内写满 `ZCODE_PROXY_DEEP_BYTES` → **OK**
2. 写错误但已写 ≥ `MIN_BYTES`、用时 < 预算 2/3 且速率 ≥ `MIN_KBPS` → **OK**（对端提前关闭是正常现象）
3. 其余（含撞上写超时）→ **失败**

刻意不用「已写 ≥ 下限且平均速率达标」判 OK：内核缓冲会先吞掉几百 KB，之后对端不读、写阻塞到超时，
平均速率仍然好看——那正是要抓的「传不动」。

### 默认 shadow：只记录，不改任何判定

`ZCODE_PROXY_DEEP_PROBE` 默认 `shadow`：结果随 `Report.Tunnel` 一起入库，并打一行

```
[~] proxy-deep id=proxy-xxx mode=shadow ok=0 bytes=262144 ms=4800 kbps=43 target=zcode.z.ai:443 early_stop=1
```

**不改变 `Report.OK`、不参与删除**。跑满 24 小时后比对「深探失败」与「软失败 / 524」的相关性，
≥80% 再切 `enforce`（只改环境变量，不改代码）。

### 只挂巡检 first 阶段

`checkNetwork` 有四个调用点，只有 first 该深探：

| 调用点 | 深探 | 理由 |
|---|---|---|
| `networkBatch` first | ✅ | 巡检主路径 |
| `networkBatch` second | ❌ | 只复核可达性，first 的隧道结果已入库 |
| direct 直连检查 | ❌ | 没有代理 URL，隧道无意义 |
| `networkPreflight` | ❌ | 每个模型探测租约都会跑，在那里写 1MiB 会把流量与特征放大到每次租约 |

单批 48 条、并发 8、每条最坏 12 秒 ⇒ 最坏 +72 秒；批次 deadline 5 分钟，仍有余量。

## 配置

| 变量 | 默认 | 说明 |
|---|---|---|
| `ZCODE_PROXY_DEEP_PROBE` | `shadow` | `off` / `shadow` / `enforce`；非法值按 shadow |
| `ZCODE_PROXY_DEEP_TARGET` | `zcode.z.ai:443` | 只接受 host:port，不接受 URL |
| `ZCODE_PROXY_DEEP_BYTES` | `1048576` | 写入量 |
| `ZCODE_PROXY_DEEP_BUDGET_MS` | `12000` | 单次预算 |
| `ZCODE_PROXY_DEEP_MIN_BYTES` | `262144` | 早停判定下限 |
| `ZCODE_PROXY_DEEP_MIN_KBPS` | `85` | 速率下限（实测「慢但能用」约 68） |

## 升级与验证

无数据迁移：`networkprobe.Report` 新增可选 `tunnel` 字段（指针 + omitempty），旧记录读出为 nil。

新增 `proxy.DialTunnel`：socks4/5/5h 复用既有 dialer 与握手（含 v2.10.24 的超时预算），
http/https 手写 CONNECT（不用 `http.ReadResponse`，避免它的 Body 语义把隧道字节读走）。

回归覆盖：socks5 与 http CONNECT 的隧道建立、写满判 OK、对端早关判 OK、对端不读判失败、
建连失败立即失败、三种模式（off/shadow/enforce）与非 first 阶段不深探。
所有自动化验证由 GitHub Actions 执行，分支 CI 与发布工作流复用的完整 CI 均为门禁。
