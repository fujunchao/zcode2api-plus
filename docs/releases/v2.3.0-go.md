# v2.3.0-go

两项调度侧的改进：选号从纯轮询改为**剩余额度优先**，以及上游**风控 405** 由「静默透传」
改为**账号级递进冷却**（阶梯可在后台调整）。

## 一、选号：额度优先，并列时轮询

原先 `store.Select` 是纯 round-robin——剩三百万 token 的号和剩一百 token 的号拿到完全
相同的流量份额。

现在的排序是五层，逐层收窄：

1. 可选（`IsSelectable`，含冷却到期判定）
2. 模型分档（`available` 优先于 `unknown`；快照里 `absent` 的直接排除）
3. 未耗尽的一次性优惠额度优先（既有逻辑）
4. **剩余额度更多者优先**（新增）
5. 并列组内按轮询游标分发

「剩余额度」由 `model.Account.UsableQuotaForModel` 计算：每条额度列优先取上游给出的
`available`（现在还能用多少），缺省回落 `remaining`（`total − used`）；同一模型出现在多条
订阅额度里则**相加**。返回值带 `ok`：

- `ok=false` —— 「完全没有数字」，排序中记为最次；
- `0` —— 「已用完」。

两者**必须分开**，否则没有快照的号会被误判成已耗尽。

### 为什么是「最大值并列组 + 组内轮询」而不是「永远取唯一最大值」

额度快照按账号缓存（`QuotaCacheTTL = 15s`），且只在账号被实际使用时才异步刷新。严格取唯一
最大值的话，这 15 秒内**全部流量会压在那一个号上**——正是额度优先本来想避免的事。

保留并列组还有个直接好处：**同规格账号**（同一套餐、剩余量相同，生产环境最常见的形态）会
整体并列，行为与原来的纯轮询**完全一致**。既有的两个选号用例（轮询、优惠额度优先）**一个字
未改即通过**——它们的夹具额度本就恰好相等，正好覆盖了这个分支。

未采纳的方案（按剩余量加权的平滑加权轮询）记录在 PLAN §5.12：它不饿死小号、对快照陈旧不
敏感，但不满足「优先使用剩余更多的账号」。取舍方向取决于更看重「额度多的先用」还是「全局
按比例分摊」。

## 二、风控 405：整号冷却 + 递进阶梯

一线现象：账号被上游风控拦截后，返回的 405 落到分类链最后一条「其余错误」——`fail_count`
加一、响应原样透传，但**账号状态不变**，仍留在调度池里，下一次请求立刻再撞一次。而风控是
会**升级**的，共享同一条出口 IP 的其它账号会一起遭殃。

### 前提：405 在本项目里有三种含义

只看状态码制定规则是危险的，所以判定必须走 body：

| 405 形态 | 成因 | 处置 |
|---|---|---|
| body 含 `unusual activity` / `blocked` / `risk` | 上游风控拦截 | **整号冷却 + 递进阶梯** |
| 计费接口的重复查询 | 幂等，可安全忽略 | 忽略（v2.2.0 已修） |
| body 为空或无风控文案 | JWT 账号缺顶层 `system` 注入时上游即回 405 | 落兜底，**不冷却** |

第三种是**我方请求构造缺陷**，每个账号都会一样地失败——按状态码冷却等于把代码 bug 升级成
对账号的集体惩罚。判据收口为 `model.IsRiskControlBody`（`quota` 里的私有同名实现已删除，
改为调用它），避免安全相关判定出现两份实现。

### 为什么冷却整个账号，而不是被请求的那个模型

风控看的是**身份维度**：JWT 账号、`X-Device-Mid` 设备指纹、出口 IP、请求头与 UA。**模型只是
body 里的一个字段**，风控引擎不会因为换了模型就放行。按模型冷却只是把同一次失败摊到别的
模型上，还拉长了暴露窗口。

### 阶梯与升级点

`RiskControlStreak` 记录连续命中次数，第 N 次命中取阶梯第 N 档；**连续命中数超过档位数时，
账号置 `invalid` 并清空 `CoolingUntil`**，交给人工。默认三档：

```
300s / 900s / 3600s   →  第 4 次命中 → invalid
```

**档位数本身就是升级点**：把设置里的阶梯改成两档，账号就会在第 3 次命中时失效。

风控计数与限流计数**刻意分开**（`RateLimitStreak` vs `RiskControlStreak`）：限流等一会儿真的
会好，风控通常需要换身份。字段用 `json:"-"`，**`accounts.data` 的 34 键契约未动**。

### 三个恢复出口

1. **自动**：`CoolingUntil` 到期后 `IsSelectable` 直接重新为真，无需清除任何字段。
2. **确认**：冷却到期后的**首次成功调用**清零计数（与限流同语义），所以只有「冷却一到期立刻
   又被拦」才会继续升级。
3. **人工**：**换凭据**（`EditAccount` 的 secret 分支）一并清零计数——不清的话，人工救回来的
   账号下一次命中就是「老计数 + 1」，立刻又置 `invalid`，等于人工修复无效。

生效范围：全部模型不可选 + 领取调度自动跳过 + **不覆盖手动 `disabled`**（管理员意图优先）。

### 一处必须加的守卫

`quota` 的成功路径原本会把 `invalid` 刷回 `active`。而**计费接口与消息接口是不同端点**，风控
未必同时命中——不管它的话，**一次额度轮询（15–60s）就会把刚升上去的封禁悄悄抹掉**，升级机制
形同不存在。

守卫是**窄**的：只有 `invalid` 且 `last_error_kind == risk_control` 时早退。它**不驱动阶梯**
（不递增计数、不冷却），只阻止计费路径覆盖请求路径的判决，所以「计费路径不计入阶梯」的口径
没有破坏。对照组测试钉住了边界：凭据失效的 `invalid` 照旧在额度可达后恢复 `active`。

## 三、设置页新增「風控冷卻」

一个字段 `risk_cooling_steps`（逗号分隔的秒数），默认 `300,900,3600`。`ZCODE_RISK_COOLING_STEPS`
只是默认值，后台改动即时生效。

- **严格校验**：非法输入直接 400，而不是静默钳制。丢一档会给出一个「操作员不知道有几档」的
  阶梯，也就是不知道升级点。
- **写入规范化**：去空白、统一逗号、单档钳到 7 天上限，所以回读总是与存进去的一致。
- 读取端解析失败则回退环境变量默认值——一条脏设定不该让服务拒绝工作。

## 四、错误归类新增第 13 项

`model.ErrorKind*` 增加 `risk_control`（计入「帳號故障」聚合筛选）。**字符串一经上线不可改名**
（会落进 `accounts.data`，并成为前端筛选值）。

## 升级注意

- `accounts.data` 键集**未变**（风控计数不序列化）；旧版读取无需迁移。
- 背景：`RiskControlStreak` 与 `RateLimitStreak` 都不落库，**进程重启后归零**——下次从最低档
  重新起算，不影响正确性（重启本身已中断了连续性）。
- 新增环境变量 `ZCODE_RISK_COOLING_STEPS`（默认 `300,900,3600`），仅作后台设定的默认值。
- 后端列表 API 形状未变；账号页与设置页的前端产物已随本版重新构建（`go:embed`）。
