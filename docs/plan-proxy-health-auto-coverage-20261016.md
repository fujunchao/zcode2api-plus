# 代理健康巡检「自动全覆盖 + 账号自动择优」实施计划与记录

日期：2026-10-16（Asia/Shanghai）。基线：`origin/go-rewrite` 的 `7ef13b3`（v2.10.9-go 统一巡检）。

**状态：已在本分支实施**（`codex/proxy-health-auto-coverage`）。先提交会变红的端到端回归（`1aa36d9`、`3549868`），再实现（`4c5f0e8`）；自动化验证全部由 GitHub Actions Ubuntu 执行，当前 SHA 的完整 CI 通过。

> 实施中发现并修正三处：① `DefaultModelProbeSettings` 携带 `HealthVersion=2` 会让全新安装跳过 `migrateNetworkHealthPolicy`，网络巡检不再继承环境默认值；② 新回归最初用默认设置构造保存请求，缺少当前 revision，实际失败于乐观锁而非目标缺口，改为从当前设置派生后才覆盖到目标行为；③ 旧状态 `json.Unmarshal` 到已带默认值的结构时，缺失字段会保留新默认值（`target_mode=auto`），升级部署被误判为「已迁移」——改为从零值反序列化，缺失字段落回零值后再走迁移。

## 1. 背景与已确认决策

用户观察：统一巡检的模型层必须手工勾选目标线路与「探测专用账号」，与「所有节点都应参与测试、账号按近期成功率自动选择」的预期不符。网络层已动态覆盖全部启用线路，模型层是唯一需要人工选择的部分。

三项已确认决策（2026-10-16）：

1. **探测账号：全自动择优**——从全部合格 JWT 账号按近期成功率自动挑选，账号留在业务池，不再需要人工指定任何账号。
2. **全覆盖策略：轮转覆盖**——每轮按预算挑最久未检测的线路，周期内全部线路获得检测；界面显示覆盖率与单线检测周期。
3. **处置门槛：保留出口组人工声明**——未声明出口组的线路在自动处置模式下只观察、不删除。

## 3. 设计（与实现一致）

### 3.1 目标线路：自动全覆盖 + 轮转窗口

- **有效目标集**：`TargetMode=auto` 时为全部「启用且未被严格禁止、未在排除名单」的线路；新增、订阅补充、重新启用的线路自动纳入，停用/删除自动退出并清理 `NextDue` 状态。排除名单在保存时剪除已删除线路，上限 1000。
- **轮转配额**：`Q = max(1, GlobalDailyLimit × IntervalMinutes / 1440)`；单线检测周期 `= IntervalMinutes × ceil(N/Q)`。默认 200 次/24h、30 分钟间隔时 Q≈4；30 条线路的单线周期约 4 小时。
- **窗口调度**（`scheduleAutoRotationLocked`）：以单线周期为长度划分对齐的轮转窗口，每个窗口最多入队 `Q` 条 `source=scheduled` 的运行（含被免测跳过的）；到期线路按 `NextDue` 升序（最久未测优先）补齐，未入队的保持到期、下一窗口优先。排队后 `NextDue = now + 周期 × (100%–120% 确定性错峰)`，下界不低于一个窗口，避免同窗口重复入队。
- **提示优先**：业务 405/3012 提示触发的诊断不受轮转配额限制（仍受总预算与诊断次数限制）。
- **手工模式完全不变**：逐目标间隔 + 80%–120% 错峰。

### 3.2 探测账号：全自动择优

- **候选池**：`probeAccountEligibilityLocked` 复用原资格条件（JWT、未托管、额度已知且 >0、可调度、不在风控静默期），去掉「必须属于专用集合」；初始化与固定出口托管账号仍不可借用。
- **滚动窗口**（"近期成功率"数据源）：每账号最近 20 条结果、24 小时过期、账号数上限 500；随巡检状态持久化，重启只恢复窗口本身，不从展示历史重建证据。记录来源：业务观测 `ObserveProxyOutcome`（5.3f 的完整成功与 405/3012）与探测结果 `CompleteModelProbe`（真实出站才算）。
- **评分顺序**：① 分层——有成功且最近一次非风控（0）＞有成功但最近一次是风控（1）＞无样本（2）＞只有失败（3）；② 窗口成功率降序；③ 距上次被选中（`LastPickAt`）最久者优先，保证并列账号轮转；④ 最近成功时间降序；⑤ ID 定序（确定性、可测试）。只把主账号计入 `LastPickAt`。
- **冻结语义不变**：入队时冻结前 2 名，诊断期间不改选；凭据代次与绑定代次校验保留。
- **自动模式不写 `ModelProbeOnly`**：账号留在业务池；探测消耗 token 额度、405 仍按现有规则冷却该账号，由单账号 24h 预算（默认 100 次）封顶。
- **切换语义**：保存 `account_mode=auto` 即清空 `AccountIDs`（显式释放专用角色）；手工模式与 2.10.9 完全一致。

### 3.3 参考线路：自动挑选

- 仅当 `ReferenceProxyIDs` 为空且 `TargetMode=auto` 时启用自动挑选：排除目标自身、规范路由别名、严格禁止线路；已声明的同出口组不互证；`auto_retire` 仍要求目标与参考双方都有声明且不同组。优先近期（30 分钟）完整业务成功的线路，其余按 ID 定序。
- 手工参考列表优先于自动挑选；`allow_direct_control` 作为最后兜底不变。

### 3.4 自动退役的运行期门槛

- 出口组声明门槛保留：无独立参考时该目标本轮记 `no_reference`，只观察不删除。
- 合格账号不足两个时（入队时冻结不足 2 个），沿用「自动处置至少两个账号」的原门槛：结论照常给出，但记 `insufficient_probe_accounts`、不执行删除。

### 3.5 设置、迁移与兼容

- 新增字段 `target_mode`（auto/manual）、`exclude_proxy_ids`、`account_mode`（auto/dedicated）；`HealthVersion` → 2，迁移幂等。
- 迁移规则：既有持久状态 → `manual`/`dedicated` 并给出可切换提示（不因升级扩大真实请求范围）；全新安装 → `auto`/`auto`。手工模式保留原有全部校验（含专用账号存在性、托管检查、≥2 账号与逐目标参考门槛）。
- 旧二进制回退：新字段被忽略，自动配置在旧版本表现为「未选择目标」→ 巡检不启用，属安全降级。
- 摘要新增 `excluded_targets`、`effective_interval_minutes` 与 `accounts` 视图（自动模式下最多 8 个账号：合格者带名次与近期成功率，不合格者带原因）。

### 3.6 管理端与界面

- 端点形状不变（`/proxies/health/settings`、`/proxies/health`、`/{id}/health-check`、`/{id}/model-probe` 等）。
- 面板：目标区改为「覆盖范围」选择（默认自动）+ 排除名单；账号区改为「账号来源」选择（默认自动）+ 择优只读视图，手工多选降级为高级项；表格在自动模式列出全部启用线路；状态行显示单线检测周期与排除数；确认弹窗仅在手工模式或切换为自动（解除专用角色）时出现。
- 手动网络检查后接续模型检查的条件改为由 Store 统一判定（目标资格在入队时校验）。

## 4. 安全边界与不变量（未放宽）

1. 证据规则不变：两轮成对对照、十分钟窗口、新鲜参考前置、反证与容量保护、严格退役事务与恢复路径全部沿用。
2. 初始化/固定出口托管账号不可借用；不自动注册、领取或导入账号。
3. 网络层不变：动态全量、首轮不删除、复核与参考核查照旧。
4. 探测不改业务持久绑定；探测成功不解除严格禁止、不清除未到期冷却。
5. 存储故障、停机、策略变更的既有保护语义不变。
