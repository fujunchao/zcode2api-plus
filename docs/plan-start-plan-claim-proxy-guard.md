# Start plan 初始额度异常与领取风控联动

日期：2026-10-01；目标补丁版本：`v2.9.1-go`。

## 日志结论与证据边界

来源为用户提供的 `zcode2api-complete-logs-20261001T020251Z.zip`，只作为诊断数据读取，
原始日志和账号信息不入库、不提交。压缩包仅含一个约 56 kB 的容器日志。

- 有 87 条账号级领取记录，其中 31 次明确的 `unusual activity` 风控，涉及 22 个账号。
- 11 个账号曾出现“上游无投放套餐”；其中 7 个后续又领取风控。
- 北京时间 09-30 23:23 出现空投放；10-01 01:46 起出现批量手动领取风控；
  10-01 09:12 起出现 `zcode-v3-start-plan-trust-1001` 自动领取成功与失败交错。
- 这些日志能证明“空投放与领取风控共存”，但空 preview **不等于**余额接口确认未获 Start plan。
  日志未记录领取时的线路 ID、HTTP 状态、业务码及原始 balance，不能断言这 22 个账号
  一定对应 22 条坏代理，也不能证明代理是唯一原因。

## 可复现反馈回路

命令：`go test ./internal/adminapi -run '^TestMissingStartPlanClaimRiskPurgesProxy$' -count=1`。

最小场景：新 JWT 账号绑定命名代理 → balance 成功返回空 plans/balances →
领取响应模拟 `HTTP 405 / code 3012 / unusual activity` → 断言问题代理删除、账号改派。
修复前已实际运行并失败：`无 Start plan 且领取风控后，问题代理仍留在代理池`。

核查结论：领取路径之前仅保存错误与冷却，不调用代理移除；HTTP 状态/业务错误缺少统一的
结构化风控标记。`LastCheckedAt` 在失败时也更新，不能用它加空 Quota 推断从未获额度。

## 处置条件

1. 正常解析且业务成功的 balance 必须显式包含 plans 和 balances 数组。
2. plans 为空；余额为空或所有明确总配额、已使用、可用、剩余值均为零。
   有订阅、总配额为正但剩余为零、字段缺失/null、未知余额形状都不满足。
3. 账号没有成功模型调用或成功领取记录，避免误伤已领取后用尽的账号。
4. 领取链路收到明确风控：业务码 3012，或失败 HTTP/业务响应包含风控文案。
   3007 验证码、1003 已领取、1005 名额耗尽等已知错误不按文案误删。
5. 有效额度证据绑定原代理 ID/URL 和凭据摘要；处置时再次核对当前状态。
   查询失败会废弃旧证据，换线/换凭据后旧证据不再匹配，进程重启须重新查询。

这是按用户要求新增的运维淘汰规则，而不是对上游风控原因的确定性诊断。

## 实施计划与落点

- [x] `model/quota`：加入不序列化的有效空额度观测；保持数据库结构和账号 JSON 契约不变。
- [x] `claim`：保留结构化风控和 HTTP 状态；自动领取遇到风控即停止本轮剩余套餐。
- [x] `store`：锁内核对证据和当前绑定，复用代理熔断事务删除问题线路并改派全部绑定账号。
      优先空闲、其次最少绑定；补位排除与问题线路相同 URL 的配置，无可用候选则清掉旧地址并回报直连。
- [x] `adminapi`：后台入池自动、定时和手动领取共用结果处理；先保存领取冷却再淘汰。
      批量中的后续账号重新读取快照，不继续使用刚被删除的共享代理。
- [x] 日志/UI：输出代理移除与改派数量；管理响应增量返回 `risk_control`、`http_status`、
      `proxy_removed`、`proxy_reassigned`、`proxy_direct_fallback`，前端如实提示。
- [x] 完成本地全量测试、静态检查和前端构建。

发布门槛：推送后等待 CI（含 Linux 竞态检测、SDK 和前端一致性检查）通过，再发布 `v2.9.1-go` 标签。

范围限于服务器后台领取链路；不自动重领，不直接操作线上数据库，不追溯删除日志里提到的代理。
CLI 独立登录领取流程不在本次服务器后台策略范围内。

## 回归矩阵

覆盖真实 HTTP 领取、自动领取、批量换线；查询失败/未知/已用尽不删；领取错误分类；
所有关联账号的共享改派；无候选直连；并发只删一次；管理员改派、换 URL、换凭据、
迟到结果和后续正额度保护；事务失败回滚与重启后证据归零。
