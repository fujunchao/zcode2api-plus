## 二、改动 1：深探早停下限 256KB → 128KB

**为什么是 128KB，而不是「曲线平缓」**

- 96KB 与 128KB 的覆盖率**完全相同（77/81）**——128KB 是「达到满覆盖的最小值」，
  再往下没有任何收益，只会削弱对内核/代理缓冲的防御；
- 假阳性风险可控：`early_stop=true` 是**写错误（对端主动关闭）**，不是缓冲区吃满后的
  阻塞超时（后者会撞 12s 预算、被 `ms < budget*2/3` 挡掉）。早停写入量呈双峰
  （约 140–180KB 与 200–220KB 两簇），说明是真实的关闭点，不是缓冲；
- 128KB 与 `ms < 8s`、`kbps ≥ 85` 两个条件组合后，仍能挡住「先吞缓冲再阻塞」的线。

**改动**：`config.DeepMinBytes` 默认 `262144 → 131072`，注释补充上述依据。
环境变量 `ZCODE_PROXY_DEEP_MIN_BYTES` 不变，可单独覆盖。

**预期**：ok 率 8.8% → **29.3%**（725 + 1686 = 2411 条），真实成功线路判好率 51% → 95%。
只影响 shadow 信号，不改变任何删除/隔离判定（enforce 仍是 opt-in）。

## 三、改动 2（撤回）：`DeepBytes` 保持 1MiB

评审建议把单次写入降到 256KB（省 25% 流量）。复核后**不做**，原因不是「省得少」，
而是它会改变判据语义、并且本次日志里就有反例。

**关键恒等式**：`DeepBytes=1MiB` + `DeepBudget=12s` ⇒ 写满即隐式要求
`1MiB/12s ≈ 85KB/s`，正好等于 `DeepMinKbps=85`。两个默认值不是独立的：
满写分支不受 `kbps/ms` 约束，所以**写入量就是速率底线**。

降到 256KB 后，满写分支的底线变成 `256KB/12s ≈ 21KB/s`（弱 4 倍），而且探针会在
「突发后卡死」发生之前就停止写入。本窗口里有 **78 条探针写到 ≥256KB 后耗时仍 ≥8s**，
其中只有 12 条速率达标——这些正是 `probe.go` 注释里点名要抓的
「内核缓冲先吞几百 KB、之后对端不读、写阻塞到超时」的线。降到 256KB 会让它们全部翻成 OK。

要同时保住语义和省流量，正确做法是给满写分支补 `kbps ≥ 85` 并把 `size` 降到 256KB
（回放：2412 条 / 29.3%，与原判据几乎完全一致）。但那是**代码语义变更**，不该和
「只调一个门槛」混在同一版；留 v2.10.30 单独做，并配「写到 300KB 后阻塞」的用例。

**本版结论**：`DeepBytes` 不动。25% 的流量收益留到下一版与速率门一起做；
更大的流量杠杆其实是「只探近期有流量的线」（活跃线 4973 次/616 MiB，其余 3248 次/388 MiB），
同样留观察。

## 四、改动 3：3009 并发准入「换号」实验开关（sync 路径）

**背景**：5 条 3009 分布在 5 个不同账号/线路，且同样内容之后都成功。但 `engine.go:53`
的设计假设是「3010 是模型级准入、换号无用」，且 5 条里有 2 条是同号延迟后成功——
证据不足以直接推翻，只能做对照实验。本窗口 75 条 3009 告警全部来自 sync 路径，
async 格式 0 条，所以只改 sync 即覆盖全部观测。

**开关**：`ZCODE_BUSY_SWITCH_AFTER`（int，默认 `0` = 现行为）。

| 值 | 行为 |
|---|---|
| `0` | 原地重试至 `BusyRetryDelays` 用尽，然后原样透传 429（当前行为） |
| `N>0` | 原地重试 N 次后改用 `switchAccount`（不冷却账号，靠外层 `tried` 避免重复选中） |

- 只改 `engine.go` 的 `IsModelConcurrencyLimit` 分支；日志
  `模型并发准入受限 N 次，换号重试`；
- async（`errModelBusy` → `attemptUpstream` 循环）不动：需要新增跨层错误类型，等实验结论；
- 请求级上界仍由 `MaxAccountAttempts`（5）兜住。

**度量（至少 7 天，预期样本约 40 条）**：

| 指标 | 口径 |
|---|---|
| 主 | 3009 请求端到端 **p50** 延迟 + 每条 429 消耗的账号数 |
| 次 | 3009 请求最终成功率 |
| 备注 | 样本量小，**p90 会抖**，不作为判据；客户端 101s 是 new-api 累计值，网关内最长 87.9s，比较时分开 |

## 五、测试

| # | 用例 | 断言 |
|---|---|---|
| 1 | 早停 150KB、500KB/s、300ms | `minBytes=128KB` → OK；`256KB` → 失败（表驱动） |
| 2 | 早停 100KB、500KB/s | 两个阈值都失败（下限仍有意义） |
| 3 | 阻塞到预算超时（ms≈12s） | 失败（时间条件仍生效） |
| 4 | 写到 300KB 后阻塞到预算 | 失败（**锁住 `DeepBytes=1MiB` 的理由**，防止以后有人只降 size） |
| 5 | `BUSY_SWITCH_AFTER=0` | 两个账号时：第一个账号重试 2 次 → 返回 429，第二个账号未被尝试 |
| 6 | `BUSY_SWITCH_AFTER=1` | 第一个账号重试 1 次 → 换第二个账号 → 成功；`attempts=2` |
| 7 | 换号不冷却 | 第一个账号 status 仍为 active、无 cooling |
| 8 | 既有回归 | deep_probe 全部用例、enforce/shadow/off 三模式、async 路径不变 |

## 六、风险与回滚

| 风险 | 处置 |
|---|---|
| 128KB 放宽后，靠缓冲「假装能写」的线被判好 | 时间条件 `ms < 8s` 仍拦阻塞型；该信号当前不参与删除（shadow） |
| 有人后续只降 `DeepBytes` 而不补速率门 | 用测试 #4 与本节说明锁住：`1MiB + 12s` 是 85KB/s 底线的载体 |
| 3009 换号变成「换号风暴」 | 默认关；实验期只开 `=1`，上界 `MaxAccountAttempts`；账号不冷却、无状态变更 |
| 3009 真是模型级限制 | 实验会直接体现为「换号后仍 429、延迟更高」，按数据回退到 0 |

## 七、验收（离线回放，无需上线）

1. 用本窗口 8221 条 shadow 记录按 `DeepMinBytes=128KB` 重算：ok = **2411（29.3%）**，
   真实成功线路判好率 **77/81（95%）**；
2. `DeepBytes` 不变 ⇒ 写入总量仍为 1004.2 MiB（本版不承诺流量下降）；
3. 3009 实验：上线 7 天后看 3009 请求 p50 与账号消耗数，对比本窗口基线
   （5 条、单条最长 87.9s、5 个账号）。

## 八、明确不做

- **不降 `DeepBytes`**：会把满写分支的速率底线从 85KB/s 降到 21KB/s，本窗口 78 条
  「突发后卡死」样本会被翻成 OK；留 v2.10.30 与速率门一起做；
- 不切 `enforce`：标定修好只是让信号可信，删除路径的相关性仍要另一轮验证；
- 不做探针频率治理（活跃 4973 次/616 MiB vs 其余 3248 次/388 MiB，数据已备）；
- 不改 async 的 3009 处置；
- 不动断流出口闸、带宽选线、内容级 405 折扣（v2.10.30 候选）。
