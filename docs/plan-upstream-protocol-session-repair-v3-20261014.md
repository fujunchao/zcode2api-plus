# 第三版修复方案：严格淘汰已判定的异常代理，覆盖全部自动机制

> 本文保留原会话冻结的设计状态与历史基线；后续仓库实施及明确未部署的边界见 [v3 实施说明](implementation-v3-strict-proxy-20261014.md)。下文“尚未实施”等表述对应制定计划时，不代表当前代码状态。

日期：2026-10-14，Asia/Shanghai。版本：**v3**。状态：**设计稿，尚未实施、删除代理或修改服务器。**

本地代码基线：`go-rewrite @ 3af19719821ae441a11b1bbef189b86b7eea8741`。服务器实际镜像版本仍需核对。

**本版是累计修复方案，不是仅替换成代理专项。** v1/v2 的问题与保护要求按第 13 节逐项继承；本轮补齐此前在第 8 节压缩为概述的非代理细则。旧版与本版冲突的代理处置，以用户明确要求的“判定后删除、无代理可直连”为准。

## 1. 用户已明确的策略

1. **严格针对“经过判定，与 405 异常相关、达到淘汰标准的代理”**：判定成立后立即删除，不停留在观察或降权。
2. **不禁止直连**：自动路径没有合格代理时，保留直连回退；自动补充代理机制继续工作。
3. 自动补充有容量、探测、来源可用性等条件，不能保证永远不直连；应如实记录实际出口。
4. 优化覆盖所有自动选代理、自动改派、自动删除后的再分配及订阅补充入口，不只修模型 405 分支。
5. 正常情况下不覆盖人工指定代理/显式直连；但已通过严格淘汰判定的地址不能通过换配置 ID、重新导入或裸 URL 绕过禁止再次使用的规则。

本版替代 v2 的“以观察/优先级为最终上线策略”和“只覆盖模型入口”的范围。**严格的是判定成立后的执行，不是见到任何 405 都删除。**

## 2. 已有证据与判定边界

- 服务端样本为 80 个 New API 请求、95 个网关入口、82 次真实上游尝试；11 次 405/3012 集中在 5 个代理配置，其余 26 个配置没有 405。
- 原始日志行 59、363 证实，自动改派曾选择其他账号已经观察到 405 的线路；当前历史仅按账号保存。
- 同一 session 跨账号及 trace 每入口变化已实证；82 次 request ID 均不同，头体 session 与双鉴权检查均一致。
- 27 次 503 是本地重放保护，零出站；6 次 429/3009 经同号退避后成功，不应计为代理 405。
- 用户确认是两个客户端共用一个 New API 用户，代理自动分配；不能据此确认多用户串线。
- MITM 文件为空，现有材料没有完整 HTTPS 请求或实际出口 IP 证据。五个配置只是优先核查候选，**不因这份计划自动追溯删除**。

严格淘汰使用可审计的本地决策规则，不把统计关联写成供应商已确认的科学因果。

## 3. 如何判定代理相关的 405

### 3.1 先通过证据有效性检查

每条证据必须满足：实际出口为 proxy；目标接口和 provider 明确；请求/账号凭据版本/代理 URL 版本可关联；响应确为模型端点的 HTTP 405 且业务码为 3012；不是重复日志或本地合成错误。

- 同一次 HTTP 的 start、headers、response_body 只计一次。
- 同一逻辑请求的多号重试不能假装成多个独立输入。
- 内容多样性使用独立的规范化语义摘要：排除已知请求/设备/会话归因字段，保留模型、system、messages、tools 和实际生成参数。仅改变 ID 不算新内容。
- 不修改现有重放键语义来实现这个摘要；两者用途不同。
- 头体不一致、鉴权构造错误、凭据已替换、错误目标/方法等已知请求问题先分类，不能用于惩罚线路。
- `official_identity_match=false` 不是请求非法的判据，它只是与本地嵌入文本比较。
- CONNECT 阶段的拒绝、普通 HTTP 405、401/403、3009、取消、超时分别分类，不混入模型 3012 计数。

### 3.2 严格淘汰的两条证据路径

以下为拟定工程门槛，需通过合成回归和影子验算固定版本；不是供应商提供的阈值。满足任一路径即可产生淘汰决定。

**路径 A：可比请求的线路对照。**

- 同一账号凭据版本、设备、逻辑会话、模型和请求语义/协议档案可比，主要变化是线路及每次必须更新的 request ID、时间。
- 在目标线路至少两次独立出现 405/3012；在替代线路出现对应的完整成功，不能只看 HTTP 200 响应头。
- 对照发生在有界时间窗口内，排除期间重新登录、模型/请求形态变化、平台整体故障等已知混杂因素。
- 必须能够引用成对的真实尝试，不能用不同账号、不同正文的一次成功伪称严格 A/B。

**路径 B：跨账号、跨内容的共享异常并有成功对照。**

- 建议观察窗口 10 分钟；目标线路至少涉及 3 个不同账号凭据版本、3 个不同入口、2 个不同语义内容的有效 3012。
- 同期至少两个曾失败的账号凭据版本在其他线路、相同模型与可比协议档案下有完整成功。
- 至少一种失败内容在其他线路有可关联的成功，避免把统一错误内容当线路问题。
- 目标线路在对应观察范围内没有相互矛盾的完整成功证据；有混合结果则进入复核，不自动宣称确认。
- 同期其他线路/目标服务正常；没有“所有线路一起失败”的平台/本机网络异常信号。

只有失败计数、没有成功对照时，状态为 **suspect（待核查）**，自动新增绑定优先避开，但不伪称已满足删除判定。证据窗口过期不会自动扩大证据量。

对照优先来自正常业务与已有记录。需要额外真实验证时另行授权、限制数量；不得关闭账号冷却、重放保护或扩大换号预算来凑证据。

### 3.3 状态与动作

```text
eligible → suspect → decision_confirmed → retiring → removed
                    判定成立后立即进入删除流程
```

- suspect 的新观察不等于永久封禁；条件不足继续收集/复核。
- decision_confirmed 必须附规则版本、证据引用、目标范围、代理身份和配置版本。
- **成立后不再等待下一轮巡检或冷却结束，不只是降权**：立即阻止新选用，并执行删除事务。
- 这里的 confirmed 指“本地严格淘汰规则成立”，不对外声称供应商确认代理根因。

## 4. 删除必须形成完整闭环

### 4.1 统一事务

1. 校验决定针对的代理 URL/配置版本未被并发修改。
2. 标记该代理身份为 retiring，阻止新的选择和派发许可。
3. 原子提交：淘汰证据/禁止再次导入记录、删除池内对应配置、解除或改派受影响绑定、订阅来源状态更新。
4. 发布新的内存状态；释放已退役端点的空闲连接和所有超时变体缓存。
5. 记录真正成功提交的删除、改派、直连回退数量；重复决定幂等处理。

不能先把账号指向新线路再发现删除提交失败，也不能只删代理表而留下账号仍引用旧地址。

### 4.2 代理身份与重复配置

- 使用统一规范化身份，不按显示名称、地区或配置 ID 判断同一代理。
- 认证代理保留认证身份分区：同一 host:port 下不同凭据可能对应不同路由，不能粗暴合并；秘密只用于内部摘要，不写日志。
- 无认证订阅端点与当前订阅 Fingerprint 建立一致映射。
- 同一已判定路由的重复配置、改名或重建 ID 不能重新成为候选。
- URL 或认证身份真实改变视为新版本，旧请求结果不得误删新版本；不得把仅改名当成身份变化。

### 4.3 在途请求和持久化失败

- “立即”指决定生效后不再发放新派发许可；已取得许可的请求属于在途，日志记录代次与许可。
- 已正常向用户输出的 SSE 不因池中配置删除而强行重放。未交付内容的请求可按明确取消规则处理，但取消不证明上游未执行，不能因此无条件补发。
- 删除失败不得报告成功；本进程保持 retiring 阻断并告警、按有界策略重试事务。
- 严格跨重启要求持久化决定/删除意图能够恢复，不能仅靠内存禁用。无法可靠恢复时须暂停相关自动代理调度并明确报错；允许的直连仍按直连策略处理，不能把旧代理当成默认健康。
- 多副本必须有共享状态与代次检查，未支持前明确限定单副本，不宣称全局即时删除。

## 5. 统一所有自动选择机制

### 5.1 共用准入契约，而不是复制条件

所有自动入口通过同一个候选决策 Module（模块）：

```text
操作用途 + 实际目标 + 排除集合 + 账号/登录快照 + 当前路由策略
    → 合格代理 / 允许的直连 / 明确失败
```

统一过滤已删除/retiring/禁止回流/已停用/陈旧版本/本次已失败候选；再按对应用途的健康证据、空闲优先、最少绑定等规则选择。

**判定按用途，淘汰按项目策略生效。** 不能把单次模型 3012 判为登录故障；但一旦模型 405 淘汰规则成立，按用户要求从项目代理池移除，此后任何用途都不能重新选它。这不代表该代理对互联网所有服务都不可用。

## 6. 无代理时允许直连，与自动补充衔接

### 6.1 保留直连，不扩大为另一种严格策略

- 自动分配/改派没有合格代理时允许 `direct_fallback`，继续按现有认证、额度、账号冷却和重放规则工作。
- 必须记录原因：无启用线路、候选待核查、全部已淘汰、补充尚未完成等，不能把实际直连记成账号旧绑定的代理。
- 直连请求发生 405，不计入任何代理失败历史，不删除账号之前绑定过的线路。
- 人工显式直连、异步强制直连继续被尊重；它们不是自动选择失败。
- 手工指定的无效/已淘汰裸 ProxyURL 应明确提示选定路由不可用，不能悄悄换成另一条代理；用户可选择自动或直连。

### 6.2 区分直连来源

为恢复补绑记录 `auto_pending_proxy` 与 `explicit_direct` 等必要意图，不只看 ProxyID 是否为空。

- 删除后自动回退直连：进入等待自动补绑集合。
- 人工要求直连：不进入该集合。
- 旧版本空绑定无法可靠区分来源，迁移时不能猜测；保留现状，由明确的自动操作或管理员选择建立新意图。
- 意图应能跨重启保存，不能靠内存临时标记导致重启后覆盖用户选择。

### 6.3 自动补充不被删除流程打成风暴

- 沿用订阅的容量、启用开关、来源过滤、探测预算和并发限制；删除后可合并通知现有补充机制，不为每个账号启动一轮导入。
- 同时最多一个相应用途的补充运行；失败按已有受控退避处理，不无限拉取或产生模型验证调用。
- 新代理导入且启用后，再原子/批量为等待集合补绑；实时检查账号是否被人工修改、线路是否仍合格。
- 补充失败或全部候选被拦时，保留允许的直连，并显示真实状态；不能承诺“有自动补充就绝不会直连”。

## 7. 严格删除后的禁止回流

- 严格 405 淘汰写入独立、持久的禁止记录，理由为实际自动规则，不能冒记“用户人工删除”。
- 该记录不依赖订阅功能当时是否启用，也不只保护订阅来源的代理；后来首次开订阅仍必须生效。
- **不沿用自动淘汰 24 小时后自行清除的逻辑**：严格淘汰记录须人工明确解除并重新验证，测活成功本身不能解除模型 405 判定。
- 换名称、换配置 ID、刷新订阅、进程重启不能绕过；同一身份的自动导入和自动启用都拒绝。
- [proxy_subscription.go](D:/augment-projects/zcode2api-plus/internal/store/proxy_subscription.go)当前已有 Blocks/ImportPaused 和提交时复核，应扩展理由与严格禁止语义，而非另建一套互不相知的黑名单。
- 禁止记录达到容量预算时暂停相关导入并告警，不静默忘记旧淘汰记录来腾位置。
- 恢复需显式管理动作、保留审计，并重新通过准入；恢复不是回滚整个数据库或取消账号冷却。

## 8. 保留并完善其他修复线

### 8.1 跨层重试

同时覆盖首次达到本地恢复上限的 405，以及后续 risk_control_cooldown 的 503。给出范围明确的停止立即重试/剩余等待建议，必要时附 Retry-After，读取等待时间不续期。

网关单方面增加字段不等于 New API 会遵守；必须核对实际 New API 版本和配置能力，分别验收。保留原始错误关联，不关闭本地重放保护，不全局禁止普通 503/3009 的正常恢复。

继承的执行细则：

- 保留既有 HTTP 状态、各客户端错误结构；新增有限的机器可读原因与等待建议，不依赖中文错误文案判定。
- 尚未发送响应头时，Retry-After 按真实剩余时间向上取整；不能每次重投重新给完整窗口。
- 异步已接受票据后，通过票据终态/错误事件表达，不回头修改已经发送的 HTTP 状态；SSE 已输出后不悄悄重放。
- 同一外层请求收到明确停止建议后，不再立即投到同一个网关保护范围；新的外层请求仍由网关原重放保护兜底。
- 保留原始上游错误与本地拒绝的内部关联，不暴露其他用户的请求引用、正文摘要、账号或线路信息。
- New API 的配置或兼容修改须针对实际版本单独验收；未验证消费端行为时，只能称网关契约完成。

回归保留：首次两账号合成 3012 → 网关停止 → 分发层决定是否重投 → 客户端新请求重提；检查零出站、剩余时间递减、其他正常重试不受影响。

### 8.2 trace 与会话

先对照客户端 → New API → 网关入站 → 出站的字段存在性/脱敏值。明确责任层后优先修精确透传；多用户隔离仍缺可信作用域，不先全局重写 session/trace。

健康条件下的会话粘号和托管身份作为独立显式模式；不能固定到已删除线路、无效账号或不支持当前模型的账号。换号后的 session/query/trace 生命周期单列决策，流已交付不能重放。

继承的执行细则：

- **透明与托管分开：** 透明模式保留合法来值，不静默重写全部 ID；托管模式必须具备受认证链保护的 CallerScope（调用者范围），显式启用。
- 一个共享 GatewayKey、IP、UA、工具数量或正文摘要不能替代 CallerScope；当前两个客户端共用一个用户的数据，不足以批准多用户自动隔离默认开启。
- 缺少 session 时每入口新建、只给 session 时 trace 重新生成、调用者固定 query，以及头/正文 session 优先级、前缀别名，均须单列契约与合成回归，不能当作随机 UUID 撞号。
- 托管模式按可信范围与逻辑对话维护 session/trace；新轮次更新 query，每次实际 HTTP 尝试更新 request。query 不是可信幂等授权，不能据它返回其他请求的缓存结果。
- 同一会话第一次并发访问时，绑定必须原子创建；有容量上限、空闲 TTL、取消/超时释放及凭据版本检查，不能驱逐活跃绑定或串写归因快照。
- 同会话切模型、账号不可用、凭据更新、重启与多副本一致性分别定义；不为粘号绕过权益、额度或冷却，不声称尚未实现的集群一致。
- 是否在换号时重建上游 session/query/trace 仍是待确认决策；没有官方对应场景证据时，不将正常样本外推为强制规则。
- trace 观察仅保留存在性与限时 HMAC；同一层先比较入参/出参。跨层密钥不同不能直接比较，密钥不进入日志或模型请求。

### 8.3 协议小改

合法可选 query-source 恢复；缺失不统一伪造 main_turn。默认桌面 system 首块缓存布局与真实 Gen UI 能力说明独立修正；保留调用者上下文和工具，不为了让本地匹配指标变 true 而覆盖用户内容。

**A. query-source 的明确规则：** 在 Attribution 表示可选 QuerySource，大小写不敏感读取；按已核实的 `^[A-Za-z0-9_.:-]{1,128}$` 验证。合法显式值由归因构造恢复，其他未知 x-zcode 字段继续过滤；空值/非法值不发送、不回显、不惩罚账号。同一请求的重试保持用途，request ID 每次刷新。

**B. system/cache 的明确规则：** 已核实的桌面默认生成路径，首个固定前缀块不附 cache_control，后续稳定块保留 ephemeral；环境注入保持原默认开关。调用者已提供的官方 system、显式空值、消息内 system/MCS 继续保真；不就地修改共享 map/切片，不用模糊关键词删除用户内容。CLI 等其他 profile 不借此批扩大改动。

**C. 桌面能力的明确规则：** 仅为网关自行生成的 desktop fallback 使用真实的“无 Gen UI 输出目录/能力”说明；调用者的完整 GUI 上下文不覆盖，非 desktop 不追加该段。不复制采集机目录，也不注入不能执行的 Read/PDF、Agent 等工具。

- 各协议的正文转换不自动复制任意 metadata；明确允许的 session 来源、头体冲突处理和保留字段。

- 旧票据读取、缺省字段、存储迁移及回滚要有合成回归，不能通过重启后清空队列规避兼容问题。
