# 方案：断流止血第二阶段 —— 线路断流闸门 + 重试感知选线（v2.13.4-go）

> 状态：**已获批准并实施（v2.13.4-go，2026-11-07）**。原计划的 v2.13.3 已被并行会话的发布审核修复占用，本阶段顺延为 v2.13.4。上阶段成果见 `docs/plan-truncate-resilience-20261107.md` 与 `docs/releases/v2.13.2-go.md`。
> 本阶段**不改请求字节形态、不改协议**，只改「选哪条线」与「什么时候把线摘掉」。

---

## 0. 为什么还要做

v2.13.2 把「断流 → 整轮判死」改成了「断流 → 客户端自动重试」。代价从**失败**变成了**重跑**：

| 今日实测（58 个请求） | 数值 |
|---|---|
| 请求耗时 | 中位 17s，p90 185s，最长 920s |
| 请求体 | 中位 478KB，p90 2.33MB |
| 4 次断流丢失的生成时间 | 185s + 99s + 546s + 58s ≈ **15 分钟** |

一次长流断流 = 用户白等一遍思考时间 + 上游白烧一遍额度。所以下一步不是「断流后怎么补救」，
而是**「别让它落到坏线上」**。

---

## 1. 现状与两个盲区（代码级）

现有止损两层：

1. **line-guard**（`internal/gateway/classify.go:244-254`）：同一线路**连续** N 次断流（默认 2）→ 摘线并改派；
2. **proxy-soft**（`internal/store/proxy_soft_failure.go:156-188`）：三个判据
   - probation（观察期内首败）
   - consecutive（连续 2 次软失败）
   - rate（窗口内 `attempts≥3 且 failures≥3 且 rate≥50%`）

**盲区 A：断流与传输超时共用阈值。**
断流（`upstream_truncate`）比连接失败贵一个数量级——连接失败在**请求内**就能换线重试，
断流只能等**客户端重跑**。但它们在软失败统计里是同一份 `Failures`，rate 判据要求 3 次才触发。

**盲区 B：重试没有任何「这是重试」的信号。**
客户端重试时重放同一份内容，我们只能靠「账号 600s 回避 + 线路隔离 30min」间接避让。
若坏线尚未达到阈值，**重试大概率落回同一条线上的另一个账号**——今天 `订阅-1e2559` 一条线上
挂了 4 个账号，正是这个形状。

**今日轨迹实证**（BJ）：

```
17:27:49  1e2559  断流 #1（首跳）
18:12:49  1e2559  断流 #2（首跳）           ← 与 #1 间隔 45 分钟，中间有成功，连击被清零
18:25:06  94da8751 断流 #3（换线后仍断）
18:32:49  1e2559  断流 #4  → 此时 consecutive=2 才隔离
```

## 2. C1：断流专用闸门（truncate strikes）

**规则**：同一线路 **60 分钟内累计 2 次 `upstream_truncate` → 立即隔离 30 分钟 + 改派**。
不要求连续、不看失败率分母。

- 为什么单独计数：断流的代价与 transport_timeout 不同级；用同一阈值只能二选一——要么对断流太宽松（现状），要么把健康线因超时误杀。
- 为什么是 2 次 / 60 分钟：一次断流已经让用户损失一整次生成；同一条线一小时内第二次，就是「没吸取教训」。窗口取 60 分钟而不是 30，是因为今天两次同线断流相隔 45 分钟，30 分钟窗口刚好漏掉。
- 计数**不因成功清零**（这点与 consecutive 相反）：坏线的典型形状就是「夹着成功」。
- 隔离动作复用现有 `quarantine` 路径：strikes 递增、改派绑定账号、入网络复核队列、日志 `trigger=truncate_strikes`。
- 误杀边界：隔离不是删除，30 分钟自动到期并进入观察期；一次完整成功即清档位。

**今日可量化收益**：18:12 那一次（第 2 次、距第 1 次 45 分钟）就会隔离 1e2559 → 18:32 的第 4 次被打掉。
**诚实口径：今天只省 1 次**；这条规则真正防的是「成功掩蔽型坏线」（未来形状），不是今天这一天。

## 3. C2：重试感知选线（本阶段的主要收益）

**键**：`contentKey`（既有 `ContentKey(model, body)`，模型 + 内容指纹）。
**记忆**：断流收尾时，把该线路 identity 记入 `truncateGuard[contentKey]`，TTL 120s。
**使用**：新请求进入 `RunMessages` 时，若同 contentKey 在 TTL 内出现过断流，把这些线路加入**请求级 avoid**
（既有机制 `SelectAvoiding` 会跳过绑定在这些线路上的账号）。

- 为什么用 contentKey 而不是 sessionId：客户端重试**原样重放请求体**（今天 4 次失败的重试体与首请求逐字节一致），
  contentKey 天然命中；sessionId 更宽，会把同会话的其它请求也带偏。
- 与现有机制的分工：账号级 `TruncateAvoidUntil`(600s) 管「这个账号别再用这条线」；
  C2 管「**整条线**别再用」——同线的其它账号也跳过，这正是今天「一条线 4 个账号」场景需要的。
- 边界：entries 上限 256，过期即删；TTL 0 = 关闭（行为回到 v2.13.2）。
- 范围：只接 sync `/v1/messages`（ZCode 走这条）。async 池不接——它的消费方是票务轮询，没有「同内容重试」语义。

**预期收益**：今天 17:27 的断流后，客户端几秒内重试；有 C2 时重试必然避开 1e2559（4 个账号整体跳过），
大概率不会再有 18:12 那次（同一线路、同一请求体）。**这是本阶段真正值钱的一项。**

---

## 4. 明确不做

- **不做 deep 探针纳入**：今天全池 872 次 deep 探针 87.3% 是 ok=false，跑通 920s 长流的线路也是 100% false——
  探针分辨不出「能连通但中途掐断」，把它当判据只会误杀健康线。
- **不做网关内续写（P4）**：要改请求字节形态（assistant prefill），踩 3012/风控红线，且 thinking/tool_use 不可续。
- **不改请求字节、不改协议、不动计费口径**。

## 5. 开关与回滚

| 变量 | 默认 | 作用 | 回滚 |
|---|---|---|---|
| `ZCODE_PROXY_SOFT_TRUNCATE_STRIKES` | 2 | C1：60 分钟内 N 次断流即隔离；0 = 关闭 | 设 0 |
| `ZCODE_PROXY_SOFT_TRUNCATE_WINDOW_SECONDS` | 3600 | C1 统计窗口 | — |
| `ZCODE_TRUNCATE_RETRY_AVOID_SECONDS` | 120 | C2：重试避让 TTL；0 = 关闭 | 设 0 |

两者可独立关闭；全部关闭后行为 **等价于 v2.13.2**。

## 6. 验收

**单测（新增）**
- C1：同线断流 ×2（中间夹一次成功）→ 隔离，`trigger=truncate_strikes`；transport_timeout 两次**不**触发该判据；阈值 0 = 关闭；窗口过期不累计。
- C2：同 contentKey 第二次请求跳过断流线路（双线路夹具，断言第二次 attempt 的 route ≠ 首跳）；TTL 过期后恢复可选；不同 contentKey 互不影响；关闭开关后行为回到原状。

**CI**：14 任务全绿（含 `-race`）。

**线上**：断流后 10 分钟内同 session 重试的 `[attempt]` 行，route 必须与首跳不同；
`proxy-soft` 日志出现 `trigger=truncate_strikes` 时，`reassigned` 与绑定账号数吻合。
