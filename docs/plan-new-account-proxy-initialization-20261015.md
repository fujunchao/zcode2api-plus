## 1. 目标、基线与范围

### 1.1 已确认的目标

1. 取消“新账号领取前后两次空额度，就删除整条共享代理并改派其他账号”的规则。
2. 代理页可以配置一个默认业务代理。符合条件的新账号在实际获得额度后，自动绑定该代理。
3. 初始化过程中使用独立的取额候选池；可重试情况下换下一个候选，每次换线执行一轮取额流程。
4. 不把已有账号重新登录、重复添加、额度耗尽当成新账号，不批量迁移原有账号。

### 1.3 本计划采用的建议口径

以下细节是为让计划可以直接实施而提出的默认值，不冒充已经存在的功能：

- 新功能默认关闭；“空额度不再删除代理”是独立修正，不受新开关控制。

## 2. 已核对的现有调用链

### 2.1 后台 OAuth 登录

```text
handleLoginStart
  → resolveLoginProxy：auto / direct / 命名代理 / 手工 URL
  → exchangeLoginWithFailover：授权码兑换期间的传输故障切换
  → saveOAuthAccountContext
      → Store.SaveOAuthAccount：user_id → email → 凭据判重，返回 isNew
      → applyLoginProxy：自动模式重登不覆盖老号绑定
      → ExchangeAPIKeyContext：兑换结果回填该账号
      → RefreshAccountsObserved：首查
      → scheduleNewAccountClaim：真正新建账号
          → claimUnderGateWithInitial
          → AutoClaimAllPlans：激活上报、资格预览、领取全部可领套餐
          → applyClaimOutcome：保存领取结果与冷却，处理领取代理故障
          → finishNewAccountQuotaCheck：强制补查
          → PurgeEmptyNewAccountProxy：当前的共享代理删除规则
```

老号走 `RefreshAccounts + scheduleAutoClaim`，不进入新号双查淘汰流程。登录会话另有 `createdAccountID`，防止“已建号但后续保存失败”的回调重试丢失新号初始化。

**不能复用 OAuth 换线循环来实现取额轮询。** 授权码可能已经被消费；初始化应在 JWT 入库后进行，不重新兑换同一个授权码、不伪造新的登录会话。

## 3. 不能只在旧流程外加一个循环的原因

### 3.1 删除共享代理的入口不止一处

- `PurgeEmptyNewAccountProxy`：两次空额度后删除代理；**本次取消这项判据**。
- `quotaRequestFailure → proxyguard.Purge`：额度查询遇到明确代理端点故障，会直接删除并改派。
- `applyClaimOutcome / handleClaimPreview / claimCLIAccount → ApplyClaimFailures`：领取不可达或可疑请求也可能删除共享代理。
- OAuth 兑换故障、巡检、断流、严格模型 3012 另有各自判据。

因此初始化请求必须有明确的用途作用域：失败先成为该任务的结构化结果，而不是直接修改全局代理池。不能只绕开 `finishNewAccountQuotaCheck`，也不能关闭全局健康保护来换取轮询成功。

非初始化请求的既有真实故障与严格退役规则继续保留；这些规则真的删除固定节点时，托管账号转为等待固定出口，而不是无条件放行被禁止的节点。

### 3.2 现有领取状态不能充当初始化状态

- `ClaimState.ClaimedAt` 表示至少一个领取操作成功，不证明实际配额到账。
- `NextAt` 混合上游下次可领时间与本地失败冷却，不能清零后继续高速换线。
- `StartPlanObservation.Missing=false` 不等于存在可用额度：已有套餐、耗尽及未知数值需要分别判定。
- `LastCheckedAt` 失败时也可能更新，不能用它证明有效额度查询。
- 当前任务是进程内 goroutine；等待和进度不能跨重启恢复。

### 3.3 调度和代理更新还有旁路

- `Account.IsSelectable` 对没有额度快照的健康账号可以放行，`ModelAvailability=unknown` 可以进入后备池。
- 只在首查后登记初始化会留下“入库到首查之间已被选中”的窗口。
- `RotateAccountProxyAt`、`removeProxiesAvoidingLocked`、`retireStrictIdentityLocked`、`rebindStrictPendingLocked` 都可能重新分配线路。
- `SelectForDirect + async_force_direct` 会绕过原代理选择；新规则必须在选号与真正派发两处执行。
- 手工资格预览会先上报激活事件；手工领取的激活上报目前位于领取槽位之外。只抢槽位不能阻止它们与初始化相撞。
- 短流探测直接借用绑定账号发模型请求，不能拿初始化账号当探测账号。

### 3.4 现有持久化接口不能直接保存新状态

`commitProxyBundleStrictLocked` 虽然会持久化账号副本，提交后目前只向内存发布 `ProxyID / ProxyURL`。把新状态塞进副本直接调用它，会造成数据库与内存不同步。

`UpdateForRequest` 主要校验凭据身份，不能代替“任务版本、代理配置代次、绑定代次、人工意图”的联合校验。新流程需要专用事务，不能先标完成、再调用 `AssignProxyProfile`。

## 4. 行为契约

### 4.1 “新账号”的可执行定义

新建候选由 Store 在判重锁内确定，不接受客户端传入 `is_new=true`：

1. 本次确实新插入账号，而不是命中相同 `user_id / email / 凭据`。
2. 来自允许的新增入口，模式为 Z.AI JWT，代理选择为自动，新功能已启用。
3. 首次有效额度结果决定下一步，不能由空字段或请求错误推断未获额度。

| 首次有效证据 | 行为 |
| --- | --- |
| 已有可用模型额度 | 不再激活或轮询，直接进入固定代理绑定 |
| 完整成功响应确认无套餐、无已分配/已使用额度，且无本地使用/领取历史 | 可以开始初始化尝试 |
| 有历史套餐、分配量或用量，但当前耗尽 | 不按新号重领；结束初始化接管，保留正常耗尽语义 |
| 查询失败、缺字段、结构未知、重复查询 405 | 等待有效证据，不认定零额度，也不直接开始领取 |

“首次入库”不等于“在平台注册时间很短”。当前没有可靠平台注册时间或“从未领取”专用标记；不能通过删除重加账号来证明资格。已有上游账号首次粘贴入库且有可用额度，按“本系统新入库、无需取额”处理，会绑定默认代理；备份导入例外，仍不接管。

对已经删除且没有保留身份历史的重新添加，本期不能声称能识别其平台注册年龄；仍需按有效上游证据保守处理，不提供清除资格记录或将旧号强制标成新号的入口。

### 4.2 固定出口与人工优先级

- 每个任务创建时记录默认代理 ID 和配置版本，完成后保持该目标 ID；不受最少绑定算法影响。
- 更换全局默认 ID 不迁移已开始任务和已完成账号；等待账号可显式选择“改用当前默认代理”。
- 任务冻结目标和预算，不因另一份无关配置保存而失效；总开关、账号健康与节点准入实时检查。任务修订号与全局策略修订号不能混为一谈。
- 编辑同一代理 ID 的地址属于明确的管理员操作，沿用既有地址更新语义，但代次改变使旧请求失效。
- 固定节点不存在、停用、退役或未通过绑定准入时，账号进入等待；不回退直连，不改绑取额池中的其他节点。
- 对托管账号，`async_force_direct` 不覆盖固定出口；对非托管账号保留原行为。前端清楚说明这个优先级。
- 模型风控仍记录原有冷却、失效和证据；只禁止托管账号自动换到其他业务出口，不清除风险状态。
- 手动指定代理或直连可以解除托管。解除托管、取消未完成任务、改变绑定及撤销旧任务版本必须是同一个事务。
- 仅暂停任务或关闭功能不能解除调度保护，更不能把最后一个临时代理自动当成业务代理。

### 4.3 取额候选池

- 默认取全部启用且通过现有严格准入的命名代理，也支持显式选定代理 ID 集合。
- 排除固定目标代理及其同规范化路由的别名；不把固定业务出口浪费在初始化尝试上。
- 复用 `CanonicalRoute` 的身份规范化与认证分区，不直接用原始 URL 文本去重。
- 每轮冻结候选范围，维护已尝试集合；订阅补充不能让一个正在运行的轮次无限增长。
- 每次实际尝试前重新校验启用状态、配置代次和退役记录；不使用旧快照恢复被删除的节点。
- 跨账号使用独立的取额轮转游标，不仅依赖账号绑定数；否则成功账号都迁出后，每个新号会再次从同一节点开始。
- 取额记录不是模型健康证据，不写入严格 3012 对照、全局禁止记录或模型风险换线历史。
- 代理配置身份不等于公网出口 IP；已有订阅 IP 字段只作观察值，不能承诺独立出口数量或固定激活容量。

### 4.4 一轮尝试与停止条件

“一条代理尝试一次”指一轮业务流程，不是仅发送一个 HTTP 请求：

```text
持久化本次尝试和临时绑定
  → 真实额度查询（防止上次实际成功但回包丢失）
  → 必要时激活上报
  → 资格预览
  → 领取当前可领取套餐
  → 同出口强制额度复查
  → 保存到账证据 / 失败分类
  → 原子绑定固定代理，或等待 / 下一候选
```

首查可复用“同一任务、同一绑定代次、本轮刚完成”的独立证据，不能直接复用普通额度缓存。激活、预览、领取与额度复查使用同一份冻结账号及路由快照。

| 结果 | 后续动作 |
| --- | --- |
| 完整成功额度响应确认至少一个模型有正的当前可用量 | 保存已到账事实，停止任何取额 POST，尝试固定绑定 |
| 无可领套餐 / 完整复查仍无初始额度，且没有明确账号资格拒绝 | 本轮记录该候选无结果，预算允许时转下一个 |
| 领取返回成功、1003 已领过、或 POST 响应丢失 | 先进入待核验，不能立刻重发领取；仍未查清则等待 |
| 1004 不符合条件、1001 不存在、1002 活动结束 | 终止本轮并展示原因；不把它们当作坏代理 |
| 1005 今日名额用完、429 或上游给出明确等待时间 | 遵守上游等待；不能仅凭这些码断言是该 IP 的容量限制 |
| 验证码不可用 / 3007 | 保留现有有界换码能力；仍失败则等待验证码，不扫完整代理池 |
| 代理连接失败、407、未取得派发许可 | 初始化作用域只记录原因；连接类可换下一个，配置失效则重选，均不删除共享代理 |
| 领取风控或未知业务拒绝 | 保存证据并进入冷却/待人工检查，不把所有拒绝都解释为可换线重试 |
| 取消、停用、归档、身份改变 | 中止旧任务；迟到结果不得绑定或恢复账号 |

建议默认预算：每轮最多 32 个不同候选、单候选最多 120 秒、整轮自首次执行起最多 900 秒；后两项包含查询、验证码等待与补查，整轮截止时间跨重启保留。预算可配置，但都有上限。上游指定等待时间优先于本地预算配置。

正常空结果最多进行有界的同出口补查（例如最多 3 次、间隔 2 秒）；若上游要求更长等待则退出本轮等待。额度等待不应产生额外领取 POST。

默认只自动执行一轮。候选耗尽或预算耗尽后保留账号和进度，由管理员“重试初始化”启动新一轮；暂时没有任何候选且尚未开始的任务，可在新增代理后唤醒。不得因周期额度刷新、服务重启、订阅更新而不断重新开轮。

## 5. 模块与数据设计

### 5.1 初始化模块

建议新增 `internal/initialization/`，将选线、步骤推进、预算、恢复和结果分类放在同一个 Module（模块）内。

- 对后台和 CLI 暴露小型 Interface（调用约定）：启动/停止、唤醒已登记任务、查询进度、请求重试/暂停。
- 网络操作通过已有 claim/quota 能力的 Adapter（具体实现）接入；测试使用本地 HTTP 和受控时钟。
- Store 负责所有持久状态与事务，模块不直接改账号指针、不直接执行 SQL。
- 任务入口只传账号 ID / 任务版本；不持有 Store 的内部账号对象，也不把 JWT 再存进任务。
- 不为这个功能另建一套 HTTP 传输、代理池或验证码求解系统。

### 5.2 配置与管理接口

建议通过独立的 `GET / PUT /admin/api/proxies/new-account-policy` 管理，复用现有管理员鉴权。配置保存在内部 `meta` 键，不让普通 `SetSettings` 任意覆盖其内部版本。

| 字段 | 建议默认值 / 语义 |
| --- | --- |
| `enabled` | `false` |
| `default_proxy_id` | 未选择；启用时必须指向合法、启用且未退役的命名代理 |
| `pool_mode` | `all_enabled`；另支持 `selected` |
| `proxy_ids` | 自选模式的 ID 列表；去重且排除固定目标 |
| `max_attempts` | `32`，建议允许 1–1000 |
| `attempt_timeout_seconds` | `120`，建议允许 10–300 |
| `round_budget_seconds` | `900`，建议允许 60–3600，且不小于单候选预算 |
| `revision` | 乐观并发版本；陈旧提交返回 409，不覆盖另一管理员的修改 |

校验与保存必须在 Store 同一把锁内完成，不能先由 Handler 校验代理存在、再无条件写设置。所选节点稍后被删时不丢弃配置意图：展示“目标已不可用”，任务等待。

`claim_auto_enabled` 仍是自动领取总开关。新策略开着但该开关关闭时，新任务可以登记，但等待、不开取额请求；重新开启只恢复已登记且预算允许的任务，不追溯扫描老账号。

手动暂停与开关导致的暂停分别记录；重新打开开关不得恢复管理员明确暂停的任务。运行过程耗尽、资格拒绝也不能被配置更新自动清零。

### 5.3 持久任务及只读投影

建议新增 SQLite 表 `account_initializations(account_id TEXT PRIMARY KEY, data TEXT NOT NULL)`，与账号/严格代理状态使用同一数据库事务。状态按账号存储，避免每个步骤重写全池任务大 JSON。

任务至少包含：

- 状态版本、来源、创建时间、任务修订号。
- 凭据代次、任务拥有的绑定代次、当前候选代理 ID/配置代次。
- 固定目标代理 ID、创建时策略修订号、是否仍由初始化模块托管。
- 本轮候选摘要、已尝试路由摘要、尝试序号、截止时间、下次允许检查时间。
- 当前步骤、已经发出的领取意图及相关 plan ID、结构化结果、最近脱敏错误。
- 已确认到账时间/必要证据摘要，与单纯“领取接口曾成功”分开。

不保存明文 JWT、代理认证、验证码、完整上游响应。规范化路由包含认证信息，只存内部摘要，不输出原文。

`Account` 可以增加 `json:"-"` 的只读初始化/路由约束投影，Store 加载和事务提交后同步发布，`Clone` 显式复制。数据库任务是唯一真相源；不改变现有 `accounts.data` 和备份 version 1 的键集，也不使用 `Enabled=false` 冒充初始化锁。

对外账号视图增量增加 `initialization`（阶段、尝试计数、当前/目标代理 ID、原因、下次检查时间）和路由策略说明；旧客户端仍可读取既有字段。

### 5.4 状态与恢复

```text
无任务：原有账号，不接管

queued → checking
             ├─ 已有可用额度 → awaiting_default
             ├─ 确认未获初始额度 → attempting → verifying
             ├─ 历史配额耗尽 → skipped
             └─ 不明 / 暂不可执行 → waiting

verifying
  ├─ 实际到账 → awaiting_default → completed
  ├─ 完整空结果且允许换线 → 下一候选的 attempting
  └─ 不确定 / 受限 / 耗尽预算 → waiting

人工接管 → cancelled（同时写入人工绑定意图）
```

- `awaiting_default` 已经确认到账；后续只处理固定绑定，不再领取。
- `completed` 保留固定路由归属，不因普通余额归零、重登或重启重新变成新号。
- `skipped` 只用于确认不应初始化的历史配额等情形，退出托管后沿用账号正常健康状态。
- 单独暂停任务仍保持调度阻断；`cancelled` 只有伴随明确人工路由接管才解除阻断。
- 重启遇到 `attempting / verifying`，先用仍有效的凭据和路由复查，不盲重发领取；响应成功但存储失败也按不确定结果处理。
- 任务数据损坏/未知版本不能当成“无任务”放行，按现有内部状态加载风格报告错误或隔离受影响账号。
- 不承诺跨上游 HTTP 与本地 SQLite 的严格恰好一次；通过预写意图、幂等查询、已领记录及保守等待避免盲目重复。

### 5.5 必须原子化的操作

1. **新建账号 + 登记任务 + 建立调度阻断**：扩展三个入库入口的受控选项，仍由 Store 内的 `isNew` 判定是否创建任务。备份导入不传该选项。
2. **开始候选尝试**：任务修订号、临时 `ProxyID / ProxyURL`、严格绑定代次、尝试预算一起提交。
3. **保存到账事实**：与该次有效额度/领取结果需要落盘的补丁一起提交，保留既有健康与人工状态。
4. **完成固定绑定**：校验最新任务、凭据、路由、目标代理与人工意图，提交固定绑定、托管意图和 `completed`，然后才允许选号。
5. **人工接管/停用/归档/删除**：撤销旧任务执行权；单条与批量入口都覆盖。删除账号同事务清理任务，不留孤儿任务。
6. **代理变动**：删除/退役/启停时同步更新任务等待状态，不能先通用改派、再在另一个事务里拉回。

所有新增事务使用副本，提交成功后一次发布；失败不提前修改内存。保留凭据、代理配置、绑定和任务四种代次，覆盖 A→B→A 回到相同字节的场景。

## 6. 领取与查询的接入方式

1. 为初始化增加结构化取额结果，保留激活结果、HTTP 状态、业务码、下次可领时间、各套餐结果和是否存在结果不确定的 POST。不能只解析日志或拿 `outcomes[0].message` 决策。
2. 旧 `AutoClaimAllPlans` 及管理接口可以继续投影成现有结果数组，避免顺手改掉老号手工/每日领取契约。
3. 新额度查询入口接受冻结的账号、路由与任务执行令牌，返回明确的“未知 / 未分配 / 已分配但不可用 / 当前可用”等判定。当前 `FetchQuotaFresh` 会重新读取账号，不能直接把修改过代理的克隆传进去就假定它走临时代理。
4. 新入口和原查询共用解析/传输 Implementation（内部实现），但请求用途参与在途查询的兼容性检查；不能将普通查询的副作用结果复用到初始化。
5. 初始可用量优先采用有效的 `available_units`，缺省时再取 `remaining_units`；至少存在合法模型项及正的有限数值。`total_units>0`、只有套餐名称或 `Missing=false` 不足以确认当前可用。
6. 初始化请求的失败处置为记录任务结果，不调用共享代理删除；使用显式参数/请求作用域，不给共享 `quota.Service` 设置临时的可变“禁删”开关。
7. 普通额度监控、手工刷新、预览与每日领取跳过未完成任务；显式单号操作返回清楚的初始化占用原因，批量操作逐条报告跳过。初始化自己的查询使用专用执行权限，不能被同一通用过滤条件误拦。
8. 领取槽位要复用，不能产生第二套独立并发上限。将现有槽位抽到可注入的共享协调位置；每个账号最多执行一个步骤组后释放，换线后排到队尾，避免一次吞掉整池代理使其他新号饥饿。
9. 等待任务放在持久队列，不每号起一个长期睡眠 goroutine。首版单工作者，退出随主进程 context 取消；CLI 在独占 Store 的进程内同步驱动同一模块，退出保留未完成任务。

解析与提交还需要处理两个现有契约：完整但空的 balance 目前可能同时返回 `balance` 和 `error`，所以不能用 `error` 键存在与否判断查询证据是否有效；`quota.apply` 的旧回写又不向调用方报告持久化失败。初始化入口应返回不可变观测及待提交补丁，由专用 Store 事务与任务进度一起保存，不能先走旧回写、再单独宣布任务完成。普通查询路径保留原接口。

### 验证码能力边界

当前 `captcha.Manager.GetVerifyParam(ctx)` 不接受代理；公开配置、浏览器求解池与人工缓存也不是按账号出口划分。自动求解结果不缓存，但人工令牌按 TTL 共享。

本期保证激活与计费请求同出口，不宣称验证码浏览器也同出口。每次真实领取仍获取有效验证码；遇到 3007 沿用有界换码，失败等待，不因换线无限重复。若后续证据证明验证码绑定求解出口，需要另立按路由隔离求解池和人工令牌的专项设计；本期不盲改浏览器指纹、设备身份或全局验证码缓存。

## 7. 固定业务代理的全路径保护

采用 Store 内部统一的路由意图判断，区分：普通旧策略、初始化临时代理、托管固定代理、人工指定/直连。初始化表是托管目标的真相源，严格代理意图只承载对应准入标记，不独立猜测目标。

| 路径 | 必须落实的行为 |
| --- | --- |
| `Select / SelectForDirect / IsSelectable` | 所有未完成任务不可选号；固定代理不满足准入也不可用 |
| `BeginProxyAttempt` | 接入模型专用最终准入，在同一锁内检查任务与路由约束，再取得既有严格许可；检查应先于 `custom_client` 豁免，不能把普通 quota/claim 一并拦死 |
| 同步、OpenAI、Responses、异步 | 复用该模型准入；不能只改其中一类 HTTP 入口 |
| 异步强制直连 | 非托管账号仍按原开关；托管账号保持固定代理，最终派发再核验，不能用检查后改设置绕过 |
| `RotateAccountProxyAt` | 托管固定账号记录/保留模型风险与冷却，但不换到取额池或直连；初始化账号不参与模型换线 |
| 通用删除与严格退役事务 | 普通账号沿用旧改派；初始化账号等待重选；固定账号等待原目标或人工换目标 |
| `rebindStrictPendingLocked / AutoAssignProxies` | 不能将专用等待任务当成普通 `auto_pending_proxy` 补到任意节点 |
| 订阅新增、启用、更新 | 只唤醒允许的任务，不恢复严格禁止节点、不自动新开耗尽轮次 |
| 手工短流探测 | 排除未初始化完成账号；取得模型路由许可后再出站，避免绕过固定出口保护；仅接许可，不擅自增加业务记账或严格模型证据 |
| `PoolStats / LocalSchedulingBarrier / PoolStatusDetails` | 增加初始化等待与固定代理不可用原因，不能显示“账号健康可用”却永远选不出 |
| 模型额度汇总 | 继续代表上游快照，不伪造额度为零；和“当前是否可调度”分开展示 |

已经取得许可的在途模型流不因配置删除被重放；本功能不放宽严格证据、发布门禁、账号风控冷却或重放保护。

## 8. 前端与接口契约

### 8.1 代理页

- 增加“新账号初始化”独立配置区：开关、默认业务代理、全部/自选取额池、预算。
- 固定代理显示用途标记，候选与固定目标冲突时说明被排除原因。
- 保存采用独立草稿和修订号；代理同时被删除时不报告保存成功，不覆盖别的设置组。
- 默认代理不可用、自动领取总开关关闭时展示明确状态。
- 删除代理确认框区分普通账号改派与托管账号等待；响应增加等待计数，不把等待伪报为直连。

### 8.2 账号页

- 显示初始化阶段、尝试序号/上限、当前取额代理、固定目标、最后原因。
- `login/complete` 既有 `status=ready` 只表示授权入库成功。保留兼容字段，增量返回初始化状态；提示改为“已登录，正在初始化”，不声称已可调用。
- 等待状态提供受控的“重试初始化 / 暂停”；已到账等待绑定时提供“重试绑定 / 改用当前默认代理”，不重新领取。
- 按钮仅对有任务的账号开放；重复请求幂等、陈旧任务版本返回 409，不允许通过重试接口把老账号强行转成新号。
- 手动编辑代理说明将解除托管，并与后台事务语义一致。
- `frontend/src/lib/types.ts` 增量扩展，既有账号 `status` 枚举不滥加业务流程阶段。

建议动作接口：`POST /admin/api/accounts/{id}/initialization/{retry|pause|bind-default}`，请求携带任务修订号；等待时间和资格错误不能被普通“重试”按钮无条件清零。

`bind-default` 默认仅重试任务原目标；只有显式的 `use_current_default=true` 才将目标改为目前配置。两种操作都只允许已确认到账的等待任务执行，并原子校验新目标，不触发新的取额流程。

实施分支为 `codex/new-account-proxy-initialization`；计划阶段未创建分支，用户批准实施后才创建并推送。

| 阶段 | 工作与文件落点 | 可验收产物 |

旧测试中“删除共享代理才正确”的断言需要按新需求替换；同时保留取消、ABA、事务失败、老号、未知额度与重复领取保护。不是删除整组测试或降低覆盖率来获得绿灯。

## 10. 回归验收矩阵

全部自动化使用隔离 SQLite、合成 JWT/验证码、`httptest` 代理/上游和可控时钟；不访问真实套餐服务。

| 类别 | 场景 | 必须证明 |
| --- | --- | --- |
| 旧规则替换 | 同一代理前后两次完整空额度 | 代理仍存在，共享老号的绑定/状态完全不变 |
| 兼容 | 新策略关闭 | 保留一次领取与真实补查，仅取消空额度删除 |
| 新旧识别 | 老号重登、重复 Token、批量重复、备份导入、API Key | 不创建初始化任务、不迁移到默认代理 |
| 新旧识别 | 新入库即有可用额度 | 零领取 POST，直接固定绑定 |
| 新旧识别 | 历史套餐耗尽、总量已分配、曾使用 | 不当作未激活新号轮询 |
| 有效证据 | 缺字段、无效数值、405 缓存、HTTP 错误、旧在途查询 | 不当成到账或无资格的确证 |
| 正常流程 | A 空结果，B 确认到账，C 为固定代理 | 请求阶段与出口顺序正确，A/B 不删除，之后模型只经 C |
| 部分成功 | 一个套餐成功，后续领取失败但余额已到账 | 不因失败重开轮次；保存额度并固定绑定 |
| 不确定成功 | POST 超时、服务退出、成功回包后落盘失败 | 恢复先查询；查不清就等待，不盲重领 |
| 业务分类 | 1003 / 1004 / 1005 / 3007 / 429 / 3012 / 401 | 各按分类停止、查询或等待，不统一扫池 |
| 用途隔离 | 初始化 balance/claim 连接失败、407、可疑请求 | 不触发 `proxyguard` 共享删除；普通非初始化既有真实故障测试保持 |
| 候选池 | 默认别名、停用、退役、修改代次、多个同 URL 配置 | 不重复尝试或绕过严格准入，固定目标被排除 |
| 多账号公平 | 大量新增、轮询期间还有手工/每日领取 | 槽位有界、每号单任务、下一次尝试让出队列，不饿死其他账号 |
| 有界执行 | 空池、32 次上限、轮次超时、订阅持续补线 | 明确等待；重启/监控不清零预算或无限新开轮次 |
| 创建原子性 | 账号创建后、后台首查前同时请求模型 | 同步、异步和兼容入口均不会选中新号 |
| 最终派发 | 选号后任务/目标被变更、强制直连开关切换 | 最终准入阻止错误出口，不统计成上游失败 |
| 默认不可用 | 删除、停用、严格退役、巡检淘汰固定代理 | 托管账号等待；普通旧账号仍按旧策略改派 |
| 自动补线 | 新代理新增/启用，默认目标尚未恢复 | 不把固定等待账号塞到任意新代理 |
| 管理变更 | 手动改绑、直连、停用、归档、删除、换凭据 | 旧任务不覆盖人工意图；单条与批量都成立 |
| ABA 与迟到 | 凭据/代理/绑定 A→B→A，旧成功晚到 | 旧任务无法绑定新状态，不能仅比较 URL 或令牌字节 |
| 事务与重启 | 创建、尝试、到账、最终绑定分别注入 SQL 失败 | 内存/数据库一致；重开后不会重复领取或提前放行 |
| API 与 UI | 重复点击、409、删除目标、关闭开关、加载旧账号视图 | 提示与真实阶段一致，失败不显示已完成，不泄露认证材料 |
| 探测旁路 | 临时代理上只有初始化账号时请求短流探测 | 不借用该账号，不发送模型请求 |
| CLI | 新号、重登、未完成后退出再 serve、API Key 与导入 | 复用同一任务，不重复创建，不误接管非目标入口 |
| 资源生命周期 | 取消时等待槽位/HTTP/验证码/队列 | 任务退出、许可释放、Store 关闭顺序正确 |

### 10.1 远端验证执行规则

- 本地只阅读、修改、格式化、检查差异；不运行 `go test`、`go vet`、Go 构建、竞态或前端自动化检查。
- 前端修改后允许本地构建，仅用于生成必须提交的 `frontend/dist`，不作为通过依据。
- 通过 `gh run watch <run-id> --exit-status` 等待本次提交；失败读取对应运行日志，修复后推送复验。
- CI 新增初始化专项重复回归，沿用当前 Go 全量、race、前端检查/测试/产物一致性、工作流检查、SDK、New API 合同、交叉编译、镜像构建及既有 Windows 专项。
- 不削弱发布复用完整 CI 的门禁。不因单个专项通过、旧 SHA 成功或本地产物生成成功宣布完成。

## 11. 上线准备与明确不做的事项

1. 新策略默认关闭；启用前通过管理页选择固定代理和取额候选，确认远端服务器能连接所配置代理。代理服务部署、认证和网络连通性不是本次代码修改自动完成的事项。
2. 不扫描历史零额度账号补任务，不自动恢复之前已经删除的代理，不解除严格禁止记录，不读取/修改运行数据库做迁移实验。
3. 关闭策略只停止新自动流程并暂停未完成任务；已有固定绑定继续保持。暂停任务不误变成可调用账号。
4. 完整数据库备份保留任务表；现有账号导出格式不是任务备份，导回时按备份导入路径处理，不自动重跑初始化。
5. 旧程序不了解初始化表，直接回退旧二进制可能把临时绑定账号当可用。回退前必须通过支持本功能的管理入口暂停并停用未完成账号；或者使用保留初始化准入保护的修复版本，不通过手改运行数据绕过。
6. 合成回归证明请求顺序、出口、预算和状态一致性，不证明供应商一定再次发放配额，也不证明 405 永久消失。若资格在首次 OAuth 或其他上游步骤即被固定，重复激活并不保证可改变结果。
7. 真机试运行另行取得明确授权；本次实施默认不提交真实账号、网关密钥、代理密码或抓包材料到 CI。
